保存した直後にジョブへ ID を渡しただけなのに、なぜジョブは「レコードが見つからない」で落ちるのか？

注文を保存したら確認メールをジョブで送る。モデルの after_create に OrderMailerJob.perform_later(id) と書くだけの、何度も書いてきたコードだ。ところが本番のエラー通知には、ときどき ActiveRecord::RecordNotFound: Couldn't find Order with 'id'=42 が届く。保存は成功していて、DB を見れば id=42 の行はちゃんとある。ジョブはなぜ、存在する行を「無い」と言ったのだろうか。

🎯 3 行まとめ
  • トランザクションの中で INSERT した行は、COMMIT するまで他の DB 接続からは見えない。ジョブのワーカーは別の接続で読むので、COMMIT 前に走ると 0 行を引く。
  • キュー（Redis など）は DB の外にあるため、perform_later はトランザクションの成否と無関係にその場でジョブを積む。直し方は「COMMIT の後に積む」で、Rails・Sidekiq ともにその仕組みを持っている。
  • それでも COMMIT と enqueue の間でプロセスが落ちればジョブは消える。取りこぼしも許せないなら、メッセージを同じ DB の outbox テーブルに書いて後から送る（代わりに重複配送への備えが要る）。

前提: COMMIT 前の行は、他の接続からは存在しない

まず DB 側の約束を確認する。トランザクションとは、複数の読み書きを「全部反映されるか、全部無かったことになるか」の一単位にまとめる仕組みだ。途中の状態を他人に見せると、後でロールバックされる幻のデータを他人が使ってしまう。そこで DB は、COMMIT されていない変更を他のトランザクションに見せない。

他人の変更をどこまで見せるかの段階を分離レベル（isolation level）と呼ぶ。PostgreSQL の既定は Read Committed で、名前の通り「COMMIT 済みのデータだけを見る」。PostgreSQL では最も緩い Read Uncommitted を指定しても Read Committed と同じに扱われるので、他人の未確定の行を読む（ダーティリード）ことはそもそも起きない。

Rails の Order.create! は、単体で呼べば保存と同時に COMMIT まで済ませる。問題になるのは、ActiveRecord::Base.transaction do ... end の中や、モデルの after_save / after_create コールバックの中でジョブを積んだときだ。これらのコールバックは保存処理と同じトランザクションの中で動くので、そこで積んだ時点では行はまだ COMMIT されていない。

ジョブはトランザクションより先にゴールする

次にキュー側を見る。Sidekiq なら perform_later は Redis にジョブ（クラス名と引数の id）を書き込んで即座に返る。Redis は DB とは別のシステムなので、DB のトランザクションが後で COMMIT されるかロールバックされるかを知る手段がない。積んだ瞬間に、ジョブはワーカーから取り出せる状態になる。

 Web プロセス       Redis      ワーカー
 ───────────       ─────      ────────
 BEGIN
 INSERT orders
  → id=42(未確定)
 perform_later(42)
   ──────────▶ [42] ─────▶ 取り出す
                            find(42)
                              │
 メール送信など               ▼
 残りの処理      他の接続には未確定行が
   …            見えない → 0 行
                RecordNotFound で失敗
 COMMIT
  → ここで初めて id=42 が見える

ワーカーは待機中ならすぐにジョブを拾い、自分の DB 接続で Order.find(42) を実行する。このとき Web プロセス側のトランザクションが、残りの処理や外部 API 呼び出しのせいでまだ COMMIT していなければ、ワーカーの接続から id=42 は見えず RecordNotFound になる。人間が後で DB を覗くと行があるのは、その時点では COMMIT が終わっているからだ。

手元で再現しにくい理由もここにある。これは「COMMIT」と「ワーカーの読み取り」のどちらが先に着くかの競争（レースコンディション）で、ワーカーが暇で待ち構えている本番ほど負けやすく、トランザクションが長いほど負ける確率は上がる。逆方向の事故もある。トランザクションがロールバックされても積んだジョブは消えないので、「作られなかった注文」の処理が走る。引数に id ではなくメールアドレスなどの中身を渡していれば、存在しない注文の確認メールが実際に届いてしまう。

🍱 たとえるなら

賃貸契約書にまだ判を押していないのに、引越し業者へ「荷物を新居に運んで」と電話してしまうようなものだ。業者は仕事が早いので先に新居に着くが、契約が成立していない部屋の鍵は開かない。少し待てば契約が済んで鍵は開くのに、業者は「部屋が無い」と言って帰ってしまう。契約が流れたら、そもそも運ぶ先が無い。正しい順番は「判を押してから業者に電話する」である。

直し方 1: COMMIT の後に積む

素直な解決は、ジョブを積むタイミングを COMMIT の後へずらすことだ。モデルのコールバックなら after_create ではなく after_create_commit（after_commit on: :create と同じ）を使う。これは COMMIT が成功した後にだけ呼ばれ、ロールバック時には呼ばれない。

class Order < ApplicationRecord
  # NG: 同じトランザクションの中で積まれる
  # after_create { OrderMailerJob.perform_later(id) }

  # OK: COMMIT 成功後にだけ積まれる
  after_create_commit { OrderMailerJob.perform_later(id) }
end

呼び出し側を全部書き換えずに済ませる仕組みもある。Rails 7.2 で Active Job に enqueue_after_transaction_commit が入り、有効にするとトランザクション中の perform_later は COMMIT まで保留され、ロールバックされればジョブは捨てられる。この設定の既定値と全体設定の扱いはその後のバージョンで何度か変わっているので、自分の Rails のバージョンのガイドで確認したい。Rails ガイドは、迷ったら ApplicationJob で明示的に有効にするのが最も安全だとしている。Sidekiq の API を直接使っているなら、イニシャライザに Sidekiq.transactional_push! を書くと同じ効果になる（Rails 7.2 未満では after_commit_everywhere gem が要る）。

# app/jobs/application_job.rb
class ApplicationJob < ActiveJob::Base
  self.enqueue_after_transaction_commit = true
end

# config/initializers/sidekiq.rb（Sidekiq API 直利用の場合）
Sidekiq.transactional_push!

それでも残る穴: COMMIT と enqueue の隙間

これで解決したように見える。しかし順番を入れ替えただけで、「DB への書き込み」と「キューへの書き込み」という別々のシステムへの 2 回の書き込みである点は変わっていない。これを二重書き込み（dual write）問題と呼ぶ。COMMIT が成功した直後に Pod が kill されたり Redis への接続が瞬断したりすると、注文はあるのにメールのジョブはどこにも無い状態が残る。「ジョブが先走る」失敗が、「ジョブが消える」失敗に変わっただけなのだ。

確認メール程度なら、この低確率の取りこぼしは許容して監視で拾う判断も十分ありうる。許せない処理（決済後の在庫引当や他サービスへのイベント通知など）では、Transactional Outbox パターンを使う。メッセージをキューに直接積むのではなく、業務データと同じ DB の outbox テーブルに「送るべきメッセージ」として INSERT する。業務データと outbox の行は同じトランザクションに入るので、両方が残るか両方が消えるかのどちらかになる。別プロセス（リレー）が outbox を読んでキューへ送り、送ったものに印を付ける。

代償は重複だ。リレーがキューに送った直後、印を付ける前に落ちると、再起動後に同じメッセージをもう一度送る。そのため受け手は、同じメッセージを 2 回処理しても結果が変わらない冪等な作りにしておく必要がある（処理済みのメッセージ ID を記録して 2 回目を捨てる、など）。なお Solid Queue のようにジョブ自体を同じ DB のテーブルに書くバックエンドでは、enqueue が業務データと同じトランザクションに入るので outbox に近い性質が得られる。ただし Rails 8 は Solid Queue を既定で別 DB に置く構成にしており、その場合この性質は無い。

💼 実務でどう出会うか

典型は「エラー通知に RecordNotFound が散発的に出るが、リトライで成功しているので放置されている」状態だ。リトライ時には COMMIT が済んでいるので表面上は動くが、メールがリトライ間隔のぶん遅れる、ロールバック時に幽霊ジョブが走る、といった症状を抱えている。コードレビューでは、after_save / after_create の中の perform_later と、transaction do ブロック内の perform_later を探すとよい。もう 1 つの定番は、トランザクション内から決済や Webhook 送信などの外部 API を呼ぶコードで、これもロールバックしても取り消せない二重書き込みである。

⌨️ 手を動かす（5 分）

2 つの DB 接続を開き、片方のトランザクション中の行がもう片方から見えないことを確かめる。ジョブのワーカーが置かれている立場をそのまま再現する実験だ。まず PostgreSQL を起動してテーブルを作る。

docker run -d --name pg -e POSTGRES_PASSWORD=pw postgres:17
sleep 5
docker exec pg psql -U postgres -c "CREATE TABLE orders (id serial PRIMARY KEY, item text);"

ターミナル A（Web プロセス役）でトランザクションを開き、COMMIT せずに止めておく。

docker exec -it pg psql -U postgres
BEGIN;
INSERT INTO orders (item) VALUES ('book') RETURNING id;

ターミナル B（ワーカー役）で、その id を読む。

docker exec pg psql -U postgres -c "SELECT * FROM orders WHERE id = 1;"

A では id=1 が返ったのに、B は (0 rows) になるはずだ。これがジョブの find が見ている景色である。A で COMMIT; を打ってから B を再実行すると行が見える。A で代わりに ROLLBACK; を打てば id=1 は永久に現れず、それを指すジョブだけが残る。終わったら docker rm -f pg で片付ける。

🙅 よくある誤解
  • 「create! が例外なく返ったのだから、行はもう誰からでも見える」 — 外側にトランザクションがある、またはコールバックの中にいる場合、成功は「自分のトランザクションの中で INSERT が通った」という意味でしかない。他の接続から見えるのは外側の COMMIT が終わってからだ。
  • 「リトライで最終的に成功するから問題ない」 — 先走りはリトライで隠れるが、ロールバックされた場合のジョブは消えずに走るし、引数にデータそのものを渡していれば存在しない注文の処理が実際に行われる。リトライは順序の問題を直していない。
  • 「after_commit にすればジョブは失われない」 — 先走りと幽霊ジョブは防げるが、COMMIT 後・enqueue 前にプロセスが落ちればジョブは失われる。取りこぼしまで防ぐには、outbox のように同じトランザクションに記録を残す必要がある。
📖 用語ミニ辞典
分離レベル（isolation level）
実行中の他トランザクションの変更をどこまで見せるかの段階。PostgreSQL の既定 Read Committed は COMMIT 済みのデータだけを見せる。
after_commit
トランザクションの COMMIT が成功した後にだけ呼ばれる Active Record のコールバック。ロールバック時は呼ばれない。
enqueue_after_transaction_commit
トランザクション中の perform_later を COMMIT まで保留し、ロールバック時は捨てる Active Job の設定。Rails 7.2 で導入。
二重書き込み（dual write）
DB とキューのような別々のシステムへ順に書くこと。片方だけ成功する中途半端な状態が起こりうる。
Transactional Outbox
送るべきメッセージを業務データと同じトランザクションで DB に書き、別プロセスが後から送るパターン。
冪等（idempotent）
同じ処理を何回実行しても 1 回実行したのと同じ結果になる性質。重複配送への備えになる。
