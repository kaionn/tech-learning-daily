.gitignore に書いたのに、なぜそのファイルは git status に出続けるのか？

うっかりコミットしてしまった .env や config/database.yml を、慌てて .gitignore に書き足した経験はないだろうか。ところが次に編集すると、git status には相変わらず modified: .env と出る。ignore と書いたのに、git はなぜ無視してくれないのか。

🎯 3 行まとめ
  • git が「追跡しているファイル」とは、.git/index（index）に載っているファイルのことである。
  • .gitignore は「まだ index に無いファイルを、新たに載せないための規則」であり、既に載っているファイルには一切効かない。
  • 追跡をやめるには git rm --cached で index から外してコミットする。ただし過去のコミットには残るので、秘密情報なら先に失効・ローテーションする。

git はファイルを 3 か所で管理している

git の手元のリポジトリには、ファイルの置き場所が 3 つある。1 つ目は作業ツリー（working tree）で、エディタで開いているディスク上の普通のファイル群だ。2 つ目は index（ステージングエリアとも呼ぶ）で、「次のコミットに入れるファイルの一覧と中身」を記録した .git/index という 1 つのバイナリファイルである。3 つ目は HEAD、つまり今いるブランチの最新コミットだ。

git add はファイルの中身を git のオブジェクトとして保存し、index のそのパスの行を更新する。git commit は index の内容をそのまま固めてコミットにする。コミットが作業ツリーではなく index から作られるため、「add したものだけがコミットされる」という挙動になる。

ここから「追跡されている（tracked）ファイル」の定義が出てくる。tracked とは index に行があるファイルのことであり、index に行が無いファイルが untracked（未追跡）だ。この区別がそのまま、冒頭の疑問の答えになる。

 作業ツリー（ディスク上のファイル）
 ┌──────────────────────────┐
 │ app.rb   .env   tmp/x.log│
 └──────────────────────────┘
       │ git add        ▲ checkout
       ▼                │
 index（.git/index）＝追跡リスト
 ┌──────────────────────────┐
 │ app.rb   .env            │
 └──────────────────────────┘
       │ git commit
       ▼
 HEAD（最新コミット）
 ┌──────────────────────────┐
 │ app.rb   .env            │
 └──────────────────────────┘

 .gitignore が見るのは index に無い物だけ
   tmp/x.log → 無視される
   .env      → index に居るので素通り

.gitignore は「新規登録お断り」の規則にすぎない

名前からは「このファイルを git の世界から消す設定」のように思える。しかし公式ドキュメントは冒頭で、gitignore は「意図的に未追跡にしておくファイル」を指定するものであり、「既に git が追跡しているファイルは影響を受けない」と明言している。効く範囲は最初から untracked なファイルに限られている。

具体的には、ignore 規則が参照される場面は 2 つだ。git status が untracked ファイルを列挙するときに一覧から除くことと、git add . のようなディレクトリ単位の add で該当ファイルを拾わないことである。どちらも「index に無いファイルをどう扱うか」の判断で、index に既に行がある .env はこの判断の対象にならない。

git status がやっている比較を分解すると理由がはっきりする。git-status は「index と HEAD の差」「作業ツリーと index の差」「追跡されておらず、かつ ignore されていないファイル」の 3 種を表示する。編集した .env は 2 番目の「作業ツリーと index の差」に該当し、この比較には ignore 規則が登場しない。だから modified として出続ける。

なぜ git は「ignore に書いたら追跡もやめる」と自動でやってくれないのか。gitfaq は追跡中ファイルの変更を無視する方法は「無い」と答え、理由として checkout などでファイルを上書きする必要が出たとき、その変更が大事なものか捨ててよいものか git には判断できないことを挙げている。追跡状態を変えるのは利用者の明示的な操作に限る、という安全側の設計だ。

🍱 たとえるなら

index は会社の入館者名簿で、.gitignore は受付に貼られた「この業者は今後入館登録しないこと」という張り紙だ。張り紙は新規の登録を止めるだけで、すでに名簿に載って入館証を持っている人は今日も普通に出入りする。止めたいなら、名簿からその人の行を消す（git rm --cached）しかない。

追跡をやめる正しい手順と、その副作用

追跡をやめるには、index からだけ行を消す git rm --cached を使う。--cached は「index からのみ取り除き、作業ツリーのファイルは変更の有無にかかわらず残す」オプションだ。付け忘れると git rm は作業ツリーのファイルも消すので、手元の .env が無くなる。

# 1. .gitignore に規則を追加（再追加を防ぐ）
echo ".env" >> .gitignore

# 2. index からだけ外す（手元のファイルは残る）
git rm --cached .env
#   ディレクトリごとなら: git rm -r --cached tmp/

# 3. 「.env を削除した」コミットとして記録
git add .gitignore
git commit -m "Stop tracking .env"

手順 3 のコミットは、git から見れば「.env を削除した」変更である。このため、他のメンバーがこのコミットを git pull すると、そのメンバーの作業ツリーから .env が消える。各自のローカル設定が入ったファイルを外すときは、事前にバックアップを取ってもらうか、.env.example のようなテンプレートを追跡し、実ファイルは各自コピーして作る運用に切り替えるのが gitfaq の勧める形だ。

もう 1 つの落とし穴は、git rm --cached が過去のコミットには何もしないことだ。.env の中身は外す前のコミットにそのまま残り、git log -p や GitHub の履歴から読める。GitHub のドキュメントは、機密データをコミットした場合はまず秘密を失効・ローテーションすることを最初の手順に挙げており、履歴の書き換え（git-filter-repo）はクローン済みの全員と調整が必要な重い作業として扱っている。鍵を差し替えれば履歴に残った値は使えなくなる、という順番で考える。

「効かない」ときに規則を疑う前に確かめること

ignore が効かない原因は、追跡済みであることのほかに、規則の書き方そのものにもある。どちらなのかを切り分けるのが git check-ignore -v <path> だ。マッチした規則の「ファイル名:行番号:パターン」とパスを表示してくれる。ただし追跡済みファイルは ignore 規則の対象外なので、既定では何も表示されない。--no-index を付けると index を見ずに規則だけで判定するので、「規則は合っているが追跡済み」の状態が見分けられる。

規則の書き方でつまずきやすいのは次の 3 点である。末尾に / を付けたパターン（tmp/）はディレクトリにだけマッチする。先頭または途中に / があるパターン（/config/local.yml）はその .gitignore の置き場所からの相対パスに固定され、/ を含まないパターン（*.log）は配下のどの階層にもマッチする。そして、親ディレクトリを丸ごと除外すると、その中のファイルを ! で再び含めることはできない。git は性能のために除外されたディレクトリの中を見に行かないからだ。

# NG: logs/ 自体を除外しているので !keep は効かない
logs/
!logs/.keep

# OK: 中身だけを除外し、.keep を戻す
logs/*
!logs/.keep

規則の置き場所も 1 つではない。優先度の高い順に、コマンドラインで渡したパターン、各ディレクトリの .gitignore、リポジトリ内の .git/info/exclude、そして core.excludesFile で指定したファイルである。core.excludesFile の既定は $XDG_CONFIG_HOME/git/ignore（未設定なら ~/.config/git/ignore）だ。.DS_Store やエディタの一時ファイルのような「自分の環境だけの都合」はここに書けば、チームの .gitignore を汚さずに済む。

💼 実務でどう出会うか

典型は、プロジェクト初期に .gitignore を用意する前に git add . してしまい、node_modules/・log/・.env がまとめて追跡されたケースだ。後から規則を書いても差分に出続け、PR に巨大な diff が混ざる。git ls-files | grep 対象 で追跡済みかを確かめ、git rm -r --cached で外すのが正攻法になる。もう 1 つは「ローカルで値を書き換える設定ファイル」をコミットしてしまったケースで、ここで git update-index --assume-unchanged を使う記事がよく見つかる。しかし gitfaq はこの用途での assume-unchanged / skip-worktree の利用を「正しく動かないので使うべきでない」としており、テンプレートを追跡して実ファイルを ignore する構成へ直すほうが後で困らない。

⌨️ 手を動かす（5 分）

使い捨てのリポジトリで、追跡済みファイルに ignore が効かないことと、git rm --cached で状態が変わることを確かめる。

cd "$(mktemp -d)" && git init -q
echo "SECRET=1" > .env
git add .env
git -c user.name=me -c user.email=me@example.com commit -qm "add env"

echo ".env" > .gitignore
echo "SECRET=2" > .env
git status --short

git check-ignore -v .env; echo "exit=$?"
git check-ignore -v --no-index .env
git ls-files --stage

git rm --cached .env
git status --short
ls .env

最初の git status --short では M .env（作業ツリーと index の差）と ?? .gitignore が出て、.env が ignore されていないことが分かる。git check-ignore -v .env は追跡済みのため何も出さず exit 1 で終わり、--no-index を付けると .gitignore:1:.env と規則自体はマッチしていることが表示される。git ls-files --stage には index の中身（モード・blob のハッシュ・ステージ番号・パス）が 1 行ずつ見える。git rm --cached の後は D .env（削除がステージ済み）に変わり、ls でファイル自体は手元に残っていることが確かめられる。

🙅 よくある誤解
  • .gitignore に書けば、そのファイルは git の管理から外れる — 外れるのは「これから追跡されるかもしれない」未追跡ファイルだけだ。追跡済みのファイルは git rm --cached で index から外すまで、変更が検出され続ける。
  • git rm --cached で外してコミットすれば、漏れた秘密は消える — 消えるのは以後のコミットからだけで、過去のコミットには中身が残る。秘密情報ならまず失効・ローテーションし、必要なら履歴の書き換えを検討する。
  • assume-unchanged を立てれば追跡中ファイルの変更を安全に無視できる — gitfaq はこの用途での利用を否定している。checkout などで git がファイルを扱う場面で期待どおりに動く保証が無く、テンプレートを追跡して実ファイルを ignore する構成が推奨される。
