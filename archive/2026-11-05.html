アプリは一度も落ちていないのに、なぜ ALB はたまに 502 を返すのか？

Node.js の API を ALB の後ろに置いた。負荷は軽く、エラーログは空、プロセスも再起動していない。それなのに CloudWatch の 502 が 1 時間に数件ずつ、思い出したように増える。再現しようとしても手元では一度も出ない。アプリが何も記録していない 502 は、いったい誰が返しているのだろうか。

🎯 3 行まとめ
  • ALB はバックエンドへの TCP 接続を使い回す（HTTP keep-alive）。無通信の接続をいつ閉じるかは、ALB とアプリがそれぞれ別のタイマー（idle timeout）で決めている。
  • アプリ側のタイマーが短いと、アプリが接続を閉じた瞬間に ALB が同じ接続へ次のリクエストを送る「すれ違い」が起き、ALB は 502 を返す。アプリにはそのリクエストが届いていないのでログにも残らない。
  • 対策は「接続を使い回す側より、受ける側のタイマーを長くする」こと。ALB の既定 60 秒に対し、Node.js の既定は 5 秒なので、何もしなければこの条件を満たさない。

ALB はリクエストごとに接続を張り直していない

ALB はクライアントからリクエストを受けると、ターゲット（バックエンドのサーバー）へ別の TCP 接続で転送する。毎回 3-way ハンドシェイクからやり直すと遅いので、一度張った接続を次のリクエストにも使い回す。これが HTTP keep-alive（持続的接続）で、1 本の TCP 接続の上でリクエストとレスポンスを何往復もさせる HTTP/1.1 の標準的な動作だ。

使い回すということは、リクエストの合間に「何も流れていない接続」が開いたまま残るということだ。開きっぱなしの接続はメモリやファイルディスクリプタを消費するので、両端はそれぞれ「この時間だけ無通信なら閉じる」というタイマーを持つ。これを idle timeout と呼ぶ。ALB の idle timeout は既定 60 秒（1〜4000 秒で変更可）だ。

問題は、このタイマーが接続の両端で独立していることだ。HTTP/1.1 の仕様（RFC 9112 §9.5）も、持続的接続のタイムアウトの長さについてクライアントにもサーバーにも何も要求していない。つまり「どちらが先に切るか」は、設定の組み合わせ次第で決まる。

閉じる合図とリクエストがすれ違う

アプリが idle timeout を迎えると、OS は相手に FIN（「こちらからはもう送らない」という TCP の終了合図）を送る。ALB は FIN を受け取ればその接続を使わなくなるので、普通は何も起きないように思える。しかし FIN はネットワークを渡って届くまでに時間がかかる。その短い隙間に ALB がちょうどその接続を選んでリクエストを送り出すと、両者が線路の上ですれ違う。

  ALB                       App
   │                         │
   │──── GET /a ────────────▶│
   │◀─────────── 200 ────────│
   │                         │
   │                         │ 5 秒 無通信
   │                         │ → 接続を閉じる
   │──── GET /b ──▶ ◀── FIN ─│
   │                         │
   │◀─────────────── RST ────│ /b は届かず
   ▼
 クライアントに 502

すでに閉じたソケットにデータが届くと、アプリ側の OS は RST（「その接続は存在しない」という強制切断の合図）を返す。GET /b はアプリのコードに一度も渡らないので、アプリのログには何も残らない。ALB は応答を受け取れないまま接続を失ったので、自分で 502 Bad Gateway を作ってクライアントに返す。AWS のトラブルシューティング文書も 502 の原因として「ALB がリクエストを送っている最中にターゲットが RST か FIN で接続を閉じた」を挙げ、ターゲットの keep-alive 時間が ALB の idle timeout より短くないか確認せよと書いている。

「たまに」しか起きないのは、すれ違いの窓が狭いからだ。トラフィックが多いと接続は 5 秒も黙らないのでタイマーが満了しない。逆に誰も来なければ送るリクエストが無い。ちょうど 5 秒前後の間隔でリクエストがぽつぽつ来る、夜間や低負荷時間帯に一番起きやすい。

🍱 たとえるなら

駅のタクシー乗り場で、配車係（ALB）は「60 分待っても客が付かない車は帰していい」というルールで車を並べている。ところが運転手（アプリ）は自分の判断で「5 分客が来なければ帰る」と決めていて、黙って発車する。配車係が発車に気づく前に客を案内すると、客の目の前には空のスペースしかない。運転手が配車係より長く待つと決めておけば、帰る判断は常に配車係が先に下すので、この事故は起きない。

ルールは「受ける側のタイマーを長く」

すれ違いを防ぐには、接続を閉じる判断を、使い回す側（ALB）に先にさせればよい。ALB は自分で閉じる接続には次のリクエストを送らないので、アプリ側のタイマーが ALB より長ければ、アプリが黙って閉じる場面がそもそも来ない。AWS も、アプリの idle timeout を ALB より大きく設定するよう推奨している。主なサーバーの既定値は次のとおりで、ALB の 60 秒を下回るものがある。

サーバー                既定値      ALB 60 秒より
Node.js keepAliveTimeout   5 秒        短い ✗
Puma persistent_timeout    65 秒(7.0+) 長い ✓
                           20 秒(6.x)  短い ✗
nginx keepalive_timeout    75 秒       長い ✓

Node.js は既定のままだと 5 秒で切るので、明示的に延ばす。値は新しい接続にだけ効くので、サーバー起動前に設定する。

const server = http.createServer(app);
server.keepAliveTimeout = 65_000; // ms。ALB の 60 秒より長く
server.listen(3000);

Puma は 7.0.0 で既定が 65 秒に引き上げられたが、6 系の既定は 20 秒だ。古い Puma を使っているなら config/puma.rb に persistent_timeout 65 を書く。Go の http.Server は IdleTimeout が 0 なら ReadTimeout の値を使い、両方 0 なら無期限になる。何も設定しなければ問題は起きないが、遅いクライアント対策で ReadTimeout: 30 * time.Second だけを入れると、idle も 30 秒になって 502 の条件を満たしてしまう。IdleTimeout も明示しておくのが安全だ。

srv := &http.Server{
    ReadTimeout: 30 * time.Second,
    IdleTimeout: 120 * time.Second, // 明示しないと 30 秒になる
}

逆方向の変更にも注意がいる。長時間のアップロード対策で ALB の idle_timeout.timeout_seconds を 300 に上げたなら、アプリ側も 300 秒より長くしないと、今まで安全だった組み合わせが崩れる。

同じ構図はアプリの外向き通信にもある

このすれ違いは ALB 固有の話ではない。接続を使い回すクライアントと、黙って閉じるサーバーの組み合わせならどこでも起きる。アプリが HTTP クライアントのコネクションプール（張った接続を貯めて再利用する仕組み）で外部 API を呼ぶときは、立場が入れ替わってアプリが「使い回す側」になる。Go の標準 http.DefaultTransport はアイドル接続を 90 秒保持するので、相手のサーバーがそれより短く切ると、たまに ECONNRESET を受け取る。

この方向では相手の設定を変えられないことが多いので、クライアント側のアイドル保持時間を相手より短くするか、再試行で吸収する。Node.js の公式ドキュメントも、再利用した接続が切られて失敗したリクエストを request.reusedSocket で見分け、冪等なリクエストだけ再試行する例を載せている。冪等（何度送っても結果が同じ）でない POST を無条件に再試行すると、サーバーが実は処理していた場合に二重実行になるので、再試行は GET などに限るのが原則だ。

💼 実務でどう出会うか

CloudWatch で HTTPCode_ELB_5XX_Count（ALB 自身が生成したエラー）だけが増え、HTTPCode_Target_5XX_Count（アプリが返したエラー）は増えていない。ALB のアクセスログを見ると、elb_status_code が 502 で、target_status_code が -（ターゲットから応答を受け取れなかった）になっている。この組み合わせが見えたら、アプリのコードを疑う前にアプリサーバーの keep-alive 設定と ALB の idle timeout を並べて比べる。デプロイ直後や Pod の終了時に出る 502 は別の原因（接続中のターゲットの停止）なので、発生時刻がデプロイと重なるかも確認する。

⌨️ 手を動かす（5 分）

5 秒で接続を閉じるサーバーに対し、同じ接続で「3 秒後」と「6 秒後」に 2 回目のリクエストを送り、タイマーを過ぎた接続へ送ると応答が返らないことを確かめる。python3 だけで動く（追加パッケージ不要）。

mkdir ka && cd ka
cat > server.py <<'EOF'
from http.server import ThreadingHTTPServer, BaseHTTPRequestHandler

class H(BaseHTTPRequestHandler):
    protocol_version = "HTTP/1.1"  # keep-alive を有効にする
    timeout = 5                    # 5 秒アイドルで接続を切る

    def do_GET(self):
        self.send_response(200)
        self.send_header("Content-Length", "3")
        self.end_headers()
        self.wfile.write(b"ok\n")

    def log_message(self, *a):
        pass

ThreadingHTTPServer(("127.0.0.1", 8080), H).serve_forever()
EOF
cat > client.py <<'EOF'
import socket, sys, time

def get(s):
    s.sendall(b"GET / HTTP/1.1\r\nHost: localhost\r\n\r\n")
    buf = b""
    while not buf.endswith(b"ok\n"):
        chunk = s.recv(1024)
        if not chunk:
            return "応答なし（相手はもう接続を閉じていた）"
        buf += chunk
    return buf.split(b"\r\n")[0].decode()

idle = float(sys.argv[1])
s = socket.create_connection(("127.0.0.1", 8080))
print("1 回目:", get(s))
time.sleep(idle)
try:
    print(f"{idle} 秒後の 2 回目:", get(s))
except OSError as e:
    print(f"{idle} 秒後の 2 回目:", type(e).__name__)
EOF
python3 server.py &
sleep 1
python3 client.py 3
python3 client.py 6
kill %1

3 秒後の 2 回目は HTTP/1.1 200 OK が返り、6 秒後の 2 回目は「応答なし」か ConnectionResetError になるはずだ。6 秒のケースでも sendall 自体は失敗しない点に注目してほしい。送る側は相手が閉じたことを送信時点では知らず、応答を待って初めて失敗に気づく。ALB が 502 を返すのはこの瞬間だ。server.py の timeout を 10 に変えて再実行すると、6 秒後も 200 が返る。

🙅 よくある誤解
  • 502 が出ているならアプリが落ちたかエラーを返した — このケースの 502 は ALB が自分で作ったもので、リクエストはアプリに届いていない。アプリのログやエラー監視が静かなのはそのためで、ALB 側のメトリクス（HTTPCode_ELB_5XX_Count）で見分ける。
  • TCP keepalive を有効にすれば idle timeout で切られなくなる — TCP keepalive は OS が空のパケットで相手の生存を確かめる別の仕組みで、HTTP のデータは流さない。ALB の文書も、TCP keep-alive を送っても idle timeout は防げないと明記している。
  • タイムアウトは短いほど資源を早く解放できて安全 — 使い回される側のタイマーを使い回す側より短くすると、このすれ違いを自分で招く。短くするなら、接続を使い回す側（LB やクライアントのプール）のタイマーも合わせて短くする。
📖 用語ミニ辞典
HTTP keep-alive（持続的接続）
1 本の TCP 接続を閉じずに、複数のリクエスト・レスポンスで使い回す HTTP/1.1 の動作。
idle timeout
無通信の接続をこの時間で閉じる、という接続の各端が持つタイマー。両端で独立に設定される。
FIN
「こちらからはもう送らない」と伝える TCP の正常な終了合図。
RST
「その接続は存在しない」と伝えて接続を強制的に打ち切る TCP の合図。閉じたソケットにデータが届くと返される。
502 Bad Gateway
中継役（プロキシや LB）が、後ろのサーバーから正しい応答を受け取れなかったときに返すステータス。
コネクションプール
張った接続を閉じずに貯めておき、次のリクエストで再利用する仕組み。
