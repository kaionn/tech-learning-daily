巨大なログを rm したのに、なぜ df の空き容量は 1 バイトも増えないのか？

「ディスク使用率 98%」のアラートで本番サーバーに入り、20GB に育った production.log を見つけて rm した。ところが df -h を打ち直しても使用率は 98% のままで、du で数えるとディレクトリは空っぽだ。消したはずの 20GB はどこにいるのだろうか。

🎯 3 行まとめ
  • rm が消すのはディレクトリ内の「名前」だけで、ファイルの実体（inode とデータ）は別に存在する。
  • 実体が解放されるのは、名前が 1 つも無くなり、かつそのファイルを開いているプロセスも 1 つも無くなった時である。
  • 書き込み中のログは rm せず中身を空にするか、アプリにファイルを開き直させる。logrotate の create と copytruncate はこの 2 つの戦略に対応する。

ファイル名とファイルの実体は別の場所にある

Linux のファイルシステムでは、ファイルの実体を inode が表す。inode とは、ファイルの所有者・パーミッション・サイズ・データブロックの位置といったメタデータを持つ管理構造で、ファイルシステム内で一意な番号が付く。ここで意外なのは、inode が持つ情報の中にファイル名が無いことである。

名前を持っているのはディレクトリの側だ。ディレクトリは「名前 → inode 番号」の対応表であり、この表の 1 行を ディレクトリエントリと呼ぶ。同じ inode を指す行を 2 つ作ればそれが ハードリンクで、inode は自分を指す行の数を リンクカウント（stat の st_nlink、ls -l の 2 列目）として数えている。

この構造の上で rm がしているのは、unlink(2) システムコールで対応表の 1 行を消し、リンクカウントを 1 減らすことだけである。データを消去する命令はどこにも出していない。データブロックを手放すかどうかは、カーネルが別の条件で判断する。

実体が消えるのは「名前」と「開いている人」が両方いなくなった時

その条件を unlink(2) の man ページはこう書いている。最後の名前が消されても、まだそのファイルを開いているプロセスがあれば、ファイルは「それを参照する最後のファイルディスクリプタが閉じられるまで存在し続ける」。ファイルディスクリプタ（fd）とは、プロセスが open したファイルを指す番号で、カーネルは fd ごとに inode への参照を握っている。

 ディレクトリ /var/log/app (名前の表)
 ┌─────────────────────┐
 │ production.log -> #2│ ◀ rm が消すのは
 └─────────────────────┘   この行だけ
            │
            ▼
 ┌─────────────────────┐
 │ inode #2   nlink: 0 │
 │ data: 20 GB         │ ◀ まだ残っている
 └─────────────────────┘
            ▲
            │ fd 5 (open したまま)
 ┌─────────────────────┐
 │ process: puma       │
 └─────────────────────┘

 解放 = nlink が 0 かつ 開いている fd が 0

冒頭の現象はこれで説明が付く。Rails の Puma はログを開いたまま追記し続けているので、rm 後も inode #2 への参照が残り、20GB はディスク上に居座る。しかもプロセスは自分の fd に書き続けるので、名前の無いファイルはなお太っていく。

du と df の数字が食い違う理由も同じ構造から来る。du はディレクトリを辿って名前の付いたファイルのサイズを足し合わせるので、名前を失ったファイルは数えようがない。df はファイルシステムに使用中ブロック数を直接尋ねるので、名前の有無に関係なく残っている実体を数える。「du の合計より df の使用量がずっと大きい」は、削除済みで開かれたままのファイルを疑う典型的なサインである。

この挙動は不具合ではなく意図された設計だ。もし rm の瞬間にデータが消えるなら、読み込み中の動画プレイヤーや実行中のプログラムが、別の誰かの rm 1 つで足元を崩される。名前を外すことと実体を捨てることを分けたおかげで、使っている人は最後まで安全に使い続けられる。

🍱 たとえるなら

図書館の目録カードと本の関係に近い。目録からカードを抜くと、その本は棚を探しても見つからなくなる（du に映らない）。しかし貸出中の本は利用者の手元にあり、廃棄されるのは返却され、かつ目録にも載っていないと確認できた時だけだ。ディスクを圧迫している「消したはずの本」は、まだ誰かが借りっぱなしにしている本である。

犯人の見つけ方と、再起動せずに空ける方法

削除済みなのに開かれているファイルは lsof で一覧できる。+L1 は「リンクカウントが 1 未満、つまり unlink 済みの開いているファイル」を選ぶ指定で、NLINK 列が 0、NAME 列の末尾に (deleted) が付いた行が出る。lsof が無い環境でも、/proc/<PID>/fd/ のシンボリックリンクを ls -l で見れば同じ (deleted) 表示を確認できる。

# 削除済みで開かれたままのファイルを探す
sudo lsof +L1
# COMMAND  PID ... NLINK ... NAME
# puma    4123 ...     0 ... /var/log/app/production.log (deleted)

# 該当プロセスの fd 番号を確かめる
sudo ls -l /proc/4123/fd | grep deleted

容量を取り戻す手はいくつかある。プロセスを再起動すれば fd が閉じて実体は解放されるが、本番の Web サーバーをすぐ止められるとは限らない。止めずに済ませたい場合は、/proc/<PID>/fd/<N> を経由して中身を 0 バイトに切り詰める。この経路は名前を失った inode そのものを指しているので、: > のリダイレクトでファイルを空にでき、データブロックがその場で解放される。

# fd 5 が指す削除済みファイルを 0 バイトにする
sudo sh -c ': > /proc/4123/fd/5'

次からの予防策は単純で、書き込み中のログを片付けたい時は rm ではなく : > production.log や truncate -s 0 production.log で中身だけを消す。名前も inode も残るので、プロセスはそのまま同じファイルに書き続け、容量は即座に戻る。

logrotate の create と copytruncate は何が違うのか

ログを定期的に切り替える logrotate も、この「名前と実体は別」という性質と向き合っている。既定の方式では、現在のログを production.log.1 のようにリネームし、create 指定があれば同じ名前で新しい空ファイルを作る。ところがリネームは名前の表を書き換えるだけで inode は変わらないので、アプリは何も知らずに古い inode、つまり .1 の方へ書き続ける。新しい production.log は空のまま、という状態になる。

そこで create 方式では、ローテーション後にアプリへファイルを開き直させる。nginx の場合は公式ドキュメントが手順を定めており、ログをリネームしてからマスタープロセスに USR1 シグナルを送ると、新しいファイルを開いて古いファイルを閉じる。postrotate スクリプトにこの合図を書くのが定石だ。

/var/log/nginx/*.log {
    daily
    rotate 7
    create 0640 www-data adm
    sharedscripts
    postrotate
        kill -USR1 $(cat /run/nginx.pid)
    endscript
}

開き直しの合図を持たないアプリには copytruncate を使う。これは元のファイルをコピーした後、元ファイルをその場で 0 バイトに切り詰める方式で、inode が変わらないのでアプリは何もしなくてよい。代わりに、logrotate の man ページが注意している通り、コピーと切り詰めの間のわずかな隙間に書かれたログは失われうる。また合図なしで create を使い続けると、rotate 7 で古い世代が削除された時に、それをまだ開いているアプリがいれば、冒頭と同じ「消したのに空かない」が再発する。

💼 実務でどう出会うか

典型は深夜のディスク逼迫アラートで、焦って大きなログを rm した結果、使用率が変わらず慌てる場面である。df と du の合計が大きく食い違ったら、まず lsof +L1 を打つ。自作アプリや Sidekiq をファイルにログ出力させている環境で logrotate を設定する時は、そのプロセスにログを開き直させる手段（シグナルや再起動）があるかを確認し、無ければ copytruncate を選ぶ。コンテナ環境でログを標準出力に出す構成が勧められる理由の一つも、アプリ側がファイルの開き直しを気にしなくて済むことにある。

⌨️ 手を動かす（5 分）

容量 100MB の tmpfs を付けたコンテナで、50MB のファイルを開いたまま rm し、df の数字が戻らないこと、/proc 経由で空にすると戻ることを確かめる。

docker run --rm --tmpfs /data:size=100m alpine sh -c '
dd if=/dev/zero of=/data/app.log bs=1M count=50 2>/dev/null
sleep 300 < /data/app.log &
sleep 1
rm /data/app.log
echo "--- rm 直後"; df -h /data; ls -l /proc/$!/fd/0
: > /proc/$!/fd/0
echo "--- /proc 経由で空にした後"; df -h /data
'

rm 直後の df は Used が 50.0M のままで、/proc/7/fd/0 -> /data/app.log (deleted) のように削除済みの印が付いたリンクが見えるはずだ。sleep の標準入力（fd 0）が inode を握っているためである。切り詰めた後は Used が 0 に戻る。: > の行を kill $!; sleep 1 に差し替えると、プロセス終了で fd が閉じて同じように解放されることも確かめられる。

🙅 よくある誤解
  • rm はファイルのデータを消去するコマンドだ — rm は名前（ディレクトリエントリ）を外してリンクカウントを減らすだけである。データブロックの解放は、名前も開いている fd も無くなった時にカーネルが行う。
  • df と du は同じものを別の方法で数えているので一致するはずだ — du は名前を辿って数え、df はファイルシステムの使用ブロックを数える。削除済みで開かれたままのファイルは df にだけ現れる。
  • ログを mv してリネームすれば、アプリは新しいファイルに書き始める — リネームでは inode が変わらないので、アプリは開き直すまで旧ファイルに書き続ける。開き直しの合図を送るか、copytruncate を使う必要がある。
📖 用語ミニ辞典
inode
ファイルのメタデータとデータの位置を持つ管理構造。ファイル名は持たない。
ディレクトリエントリ
ディレクトリ内の「名前 → inode 番号」の対応 1 行。rm が消すのはこれ。
リンクカウント
inode を指すディレクトリエントリの数（st_nlink）。0 になると名前の無いファイルになる。
ファイルディスクリプタ
プロセスが開いたファイルを指す番号。開いている間は inode への参照を保持する。
copytruncate
logrotate の方式の一つ。コピー後に元ファイルをその場で 0 バイトにし、inode を変えずに切り替える。
