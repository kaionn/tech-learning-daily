b に append しただけなのに、なぜ別の変数 c の中身まで変わるのか？

Go で再帰を書き、途中の経路 path に要素を足しながら結果を res = append(res, append(path, x)) と集めた。期待したのは [[1] [2] [3]] なのに、出力は [[3] [3] [3]] だった。append は「新しい slice を返す関数」のはずではなかったか。

🎯 3 行まとめ
  • Go の slice は「配列へのポインタ・長さ・容量」の 3 つ組にすぎない。slice をコピーしたり切り出したりしても、指している配列は同じままだ。
  • append は容量に空きがあれば既存の配列にそのまま書き込み、足りないときだけ新しい配列を確保する。空きがあると、同じ配列を指す別の slice の中身まで書き換わる。
  • 共有させたくないときは s[low:high:max] や slices.Clip で容量を長さに揃えるか、slices.Clone でコピーしてから append する。

slice は配列そのものではなく「配列の窓」である

Go 公式ブログの解説によれば、slice は配列の一区間を表す小さな記述子で、配列へのポインタ・長さ（len: いま見えている要素数）・容量（cap: ポインタの位置から配列の末尾までの要素数）の 3 つを持つ。この 3 つ組を slice ヘッダ と呼ぶ。要素の実体は、ヘッダの外にある 基底配列（underlying array: slice が指す実際のメモリ領域）に並んでいる。

そのため t := s と代入したり s[1:3] で切り出したりしても、コピーされるのはヘッダだけだ。同ブログは「slicing does not copy the slice's data」と明言している。t[0] = 9 と書けば、同じ配列を指す s からも 9 が見える。

s := make([]int, 3, 4)
t := s

 s ヘッダ  ptr ─┐ len=3 cap=4
                │
 t ヘッダ  ptr ─┤ len=3 cap=4
                ▼
 基底配列      ┌──┬──┬──┬──┐
               │0 │0 │0 │  │◀ 空き
               └──┴──┴──┴──┘
  （ヘッダは 2 つ、配列は 1 つ）

関数に slice を渡したときも同じである。公式ブログの言い方では、関数が受け取るのは「slice ヘッダのコピー」だ。中の要素を書き換えれば呼び出し元にも見えるが、呼び出し先で長さを伸ばしても、呼び出し元のヘッダの len は変わらない。

append は容量に空きがあれば上書きする

言語仕様は append の挙動を 2 つに分けて書いている。容量が足りなければ「新しい、十分な大きさの基底配列を確保」する。そうでなければ「基底配列を再利用する」。append は新しい slice ヘッダを返す。しかし、その中のポインタが新しい配列を指すとは限らない。

冒頭のバグはこの「再利用」の側で起きている。path は make([]int, 0, 4) で長さ 0・容量 4 だった。append(path, 1) は空きの先頭、つまり配列の 0 番目に 1 を書いて、長さ 1 のヘッダを返す。次の append(path, 2) も、path の長さは 0 のままなので同じ 0 番目に 2 を書く。res に入った 3 つの slice は全部同じ配列の 0 番目を見ているので、最後に書いた 3 が 3 回並ぶ。

path := make([]int, 0, 4)
for _, x := range []int{1, 2, 3} {
    res = append(res, append(path, x))
}
fmt.Println(res) // [[3] [3] [3]]

直感では「append は配列を伸ばす操作」に見える。しかし実際に append がしているのは「len の位置に書き、len を 1 つ増やしたヘッダを返す」ことだけだ。その位置が他の slice からも見えるかどうかを、append は気にしない。

🍱 たとえるなら

1 冊のノートを複数人で共有し、各自が「自分は何ページ目まで書いたか」を付箋で持っている状態だ。付箋（slice ヘッダ）は人ごとに別々でも、ノート（基底配列）は 1 冊しかない。A さんの付箋が 3 ページ目、B さんの付箋も 3 ページ目なら、2 人とも「次は 4 ページ目」に書き込み、後から書いたほうが残る。ノートが最後のページまで埋まったときだけ、書き手は新しいノートに全部写してから書き足す。

「たまにしか壊れない」のは再確保が起きるかどうかで分かれるから

この種のバグが厄介なのは、容量が足りなくなった瞬間に症状が消えることだ。容量を超える append は新しい配列に要素を写すため、そこから先は元の slice と縁が切れる。同じコードでも、元の slice の容量にたまたま空きがあれば共有が起き、ちょうど満杯なら起きない。

再確保のときに容量をいくつにするかは、言語仕様では決まっていない。Go 1.18 のリリースノートも「append が新しい配列を確保するときの成長の計算式を少し変えた」と書くだけで、式そのものは仕様として約束していない。そのため「容量は毎回 2 倍になるから、ここでは必ず再確保される」という前提でコードを書くと、バージョンや要素数が変わったときに挙動が変わりうる。

共有は切り出しでも起きる。head := s[:2] の容量は s の末尾までなので、append(head, 99) は s[2] を上書きする。「先頭 2 件だけ取り出して加工したつもりが、元のデータの 3 件目が消えていた」という形で表に出る。

容量を絞れば、次の append は新しい配列に書く

言語仕様には full slice expression（3 つ目の添字で容量まで指定する切り出し）がある。a[low:high:max] は a[low:high] と同じ要素を持ち、容量を max - low にする。max を high と同じにすると容量が長さに一致し、空きがゼロになる。空きがなければ次の append は新しい配列を確保するので、元の配列には触れない。

// 容量 = 長さ にしてから渡す
res = append(res, append(path[:len(path):len(path)], x))

// Go 1.21+ の slices パッケージなら
res = append(res, append(slices.Clip(path), x))

// 呼び出し先に渡す前に丸ごと複製する
safe := slices.Clone(head)

slices.Clip(s) の中身は s[:len(s):len(s)] だと公式ドキュメントに書かれている。slices.Clone は要素をコピーした別の slice を返す。ただし「浅いコピー」なので、要素がポインタや slice なら、その先は共有されたまま残る。

どちらを使うかは目的で決まる。「この slice に後から足されても元を壊さないでほしい」なら Clip で容量を絞れば足りる。「受け取った側が要素を書き換えるかもしれない」なら、Clone で配列ごと分けるしかない。

💼 実務でどう出会うか

典型は 3 つある。1 つ目は冒頭のような再帰・バックトラックで、経路の slice を使い回して結果に追加するときに起きる。2 つ目は「共通のベース設定に項目を足す」処理で、base := []string{"-v", "-x"} を元に append(base, "a") と append(base, "b") を作ると、base の容量に空きがある場合だけ互いを上書きする。3 つ目はメモリで、Go 公式ブログは大きなファイルを読み込んだ []byte から数バイトだけ切り出して返すと、ファイル全体の配列が GC されずに残り続けると注意している。対策はどれも同じで、必要な分だけ新しい slice に copy（または slices.Clone）してから返す。

⌨️ 手を動かす（5 分）

容量に空きがある slice に 2 回 append したときと、容量を絞ってから append したときの違いを確かめる。Go が入っていれば次をそのまま貼り付けて実行できる（入っていなければ Go Playground に main.go の中身を貼ってもよい）。

mkdir -p /tmp/slicedemo && cd /tmp/slicedemo
cat > main.go <<'EOF'
package main

import "fmt"

func main() {
	a := make([]int, 3, 4)
	b := append(a, 1)
	c := append(a, 2)
	fmt.Println("b:", b, "c:", c)

	d := append(a[:3:3], 1)
	e := append(a[:3:3], 2)
	fmt.Println("d:", d, "e:", e)

	s := []int{1, 2, 3, 4}
	head := s[:2]
	head = append(head, 99)
	fmt.Println("s:", s, "head:", head)
}
EOF
go run main.go

b: [0 0 0 2] c: [0 0 0 2] と出るはずだ。b に入れたはずの 1 が、後の append(a, 2) に上書きされている。容量を 3 に絞った d と e は [0 0 0 1] と [0 0 0 2] に分かれる。最後の行では s が [1 2 99 4] になり、切り出しへの append が元の 3 件目を書き換えたことが分かる。

🙅 よくある誤解
  • append は常に新しい slice（新しい配列）を作って返す — 返るのは新しいヘッダだが、容量に空きがあれば中のポインタは元と同じ配列を指す。新しい配列が確保されるのは容量が足りないときだけだ。
  • slice は参照型だから、関数内で append すれば呼び出し元にも要素が増える — 関数が受け取るのはヘッダのコピーなので、呼び出し元の len は伸びない。だから s = append(s, x) のように戻り値を受け取る必要がある。
  • 容量は毎回 2 倍に増えるので、再確保のタイミングは予測できる — 成長の計算式は仕様で決まっておらず、Go 1.18 でも変更された。共有の有無を再確保のタイミングに頼らず、Clip や Clone で明示する。
📖 用語ミニ辞典
slice ヘッダ
基底配列へのポインタ・長さ・容量の 3 つ組。代入や関数呼び出しではこれだけがコピーされる。
基底配列
slice が指している要素の実体が並ぶメモリ領域。複数の slice が同じ基底配列を共有しうる。
容量（cap）
slice の先頭から基底配列の末尾までの要素数。append が再確保せずに書き込める上限を決める。
full slice expression
a[low:high:max] の形の切り出し。結果の容量を max - low に制限する。
slices.Clip
slice の容量を長さに揃えて返す関数。中身は s[:len(s):len(s)]。
