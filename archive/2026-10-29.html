Puma のワーカーを 4 つ fork したのに、なぜメモリは 4 倍にならないのか？

config/puma.rb に workers 4 と書いて本番に出したことがあるはずだ。top を見ると各ワーカーの RSS は親とほぼ同じなのに、合計してもコンテナのメモリ使用量はその 4 倍には届かない。では、その「届かない分」はどこへ消えたのか。そして、なぜデプロイ直後は軽かったワーカーが数時間でじわじわ重くなるのか。

🎯 3 行まとめ
  • fork は親のメモリを即座に複製せず、同じ物理ページを親子で共有し、どちらかが書き込んだページだけをその時点でコピーする（Copy-on-Write）。
  • RSS は共有ページを各プロセスに重複して数えるので、合計すると実際より大きく見える。実使用量は PSS や Private_Dirty で見る。
  • Ruby では GC 自身がヒープに書き込むため共有が剥がれていく。preload_app! と fork 前の Process.warmup で剥がれにくくできる。

fork は「コピー」ではなく「共有の約束」

fork は、呼び出したプロセスとそっくり同じ子プロセスを作る Linux のシステムコールだ。Puma のクラスタモードでは、master プロセスがアプリを読み込んだあと fork でワーカーを生み、各ワーカーがリクエストを処理する。man ページによれば、親の仮想アドレス空間はまるごと子に複製され、fork 直後の両者の中身は同じだが、以後は互いの書き込みが相手に影響しない別々のメモリ空間になる。

ここで素朴に考えると、「中身が同じで互いに独立」なら、親の 200MB を子にも 200MB 丸ごとコピーしているように思える。しかし実際は違う。man ページは Linux の fork が Copy-on-Write（CoW: 書き込まれるまでコピーを遅らせる方式）のページで実装されており、fork のコストは主に親のページテーブルの複製にかかると書いている。ページテーブルとは、プロセスが見ている仮想アドレスをどの物理メモリ（ページ単位の区画）に対応させるかを記録した表のことだ。

つまり fork 直後の子は、親と同じ物理ページを指すページテーブルを受け取っただけで、データ本体は 1 部しかない。共有ページは書き込み禁止の印が付き、どちらかが書き込もうとした瞬間に CPU が違反を検出してカーネルに制御を渡す。カーネルはそのページだけを複製し、書き込んだ側のページテーブルを新しいコピーに付け替える。

[fork 直後]
 親のページ表 ──┐
                ├──▶ 物理ページ A
 子のページ表 ──┘     （書込禁止で共有）

[子が A に書き込んだ瞬間]
 1. CPU が書込禁止違反を検出
 2. カーネルが A を複製して A' を作る
 3. 子のページ表を A' に付け替える

 親のページ表 ─────▶ 物理ページ A
 子のページ表 ─────▶ 物理ページ A'

コピーが「書き込まれたページだけ」「書き込まれた時に」起きるので、読むだけのページ（アプリのコード、起動時に作った設定やクラス定義など）は何個ワーカーを作っても物理的には 1 部で済む。これが 4 倍にならない理由だ。

🍱 たとえるなら

4 人の新人に同じマニュアルを渡すとき、最初から 4 冊コピーせず、1 冊を回し読みさせる。誰かが書き込みをしたくなったら、そのページだけをコピーしてその人専用にする。書き込みの多い人ほど手元のコピーが増え、全員がすべてのページに書き込めば、結局 4 冊分の紙が要る。

RSS を足すと嘘になる: PSS と Private_Dirty

top や ps が出す RSS（Resident Set Size: いま物理メモリに載っている量）は、共有ページもそのプロセスの分として丸ごと数える。親と 4 ワーカーが同じ 180MB を共有していれば、5 プロセスすべての RSS に 180MB が含まれ、足すと 900MB に見えるが、物理的には 180MB しか使っていない。

Linux の /proc/PID/smaps には、これを補正した PSS（Proportional Set Size: 共有ページを共有しているプロセス数で割って按分した量）がある。カーネルのドキュメントは PSS を「そのマッピングに対するプロセスの比例配分の取り分」と定義し、ページが 1 プロセスからしか参照されていなければ private として数えると書いている。全プロセスの PSS を足すと実際の物理使用量に近づく。/proc/PID/smaps_rollup はこれらをプロセス全体で合計したものだ。

CoW の剥がれ具合を見るには Private_Dirty（そのプロセスだけが持ち、書き込みで変更済みのページ量）が直接の指標になる。fork 直後のワーカーはこれがほぼ 0 で、時間とともに増えていく分が「コピーされてしまった分」だ。

何もしていないのに剥がれる: GC が書き込む

アプリのコードは読むだけなので共有され続けそうに思える。しかし Ruby のオブジェクトはヒープ上に並んでおり、GC（ガベージコレクタ: 不要になったオブジェクトを自動回収する仕組み）は生きているオブジェクトを調べる過程で管理情報を書き換える。書き込み先が共有ページなら、たとえアプリが値を変えていなくてもそのページはコピーされる。

Ruby 1.9 までの GC は「生きている」印（マークビット）を各オブジェクトの中に直接書き込んでいたため、子で GC が 1 回走るだけでヒープのほぼ全ページが汚れた。Ruby 2.0 で中村成洋さんの Bitmap Marking GC が入り、マークビットをオブジェクトとは別のビットマップ領域に移したことで、マークのたびにオブジェクトのページを汚すことはなくなった。Ruby 2.0 の解説記事は、Bitmap Marking なしで fork すると GC が何度か走るうちにメモリ使用量が大きく増えうると述べている。

それでも GC の書き込みがゼロになったわけではない。Ruby 3.3 で入った Process.warmup のドキュメントは、この API が「起動完了」を VM に伝え、major GC・ヒープのコンパクション・生き残ったオブジェクトの old 世代への昇格・空きページの解放などを行うと説明し、pre-fork 型のサーバーでは最初の fork の前に呼ぶよう勧めている。fork 後のワーカーでやると共有ページを汚す後始末を、fork 前の親で済ませておく発想だ。下の手を動かすの実験では、fork 前に何もしないと子で GC.start を 1 回呼んだだけで Private_Dirty が 0 から 159MB に跳ね、Process.warmup を挟むと 27MB で止まった。

Python ではこの問題がさらに鋭い。Instagram のエンジニアリングブログによれば、Python はオブジェクトを参照するたびに参照カウントを書き換えるため、読むだけでもページがコピーされる。彼らは GC を止め、のちに gc.freeze() を CPython に入れて fork 前のオブジェクトを GC の追跡対象から外した。言語ランタイムの設計が、OS の CoW の効き方を左右している。

Puma の設定: preload_app! と Process.warmup

CoW の恩恵を受けるには、そもそもアプリを fork の前に親で読み込んでおく必要がある。Puma の README は、preload_app! がアプリのコードを fork 前に読み込み、Copy-on-Write によって総メモリ使用量を減らすと説明している。preload しないと各ワーカーが fork 後に自分でアプリを読み込むので、同じクラス定義がワーカーの数だけ別々に作られ、共有できない。

README によれば、ワーカー数が 1 より大きい場合は preload がデフォルトで有効になる（--prune-bundler 指定時を除く）。明示しておくと意図が読み手に伝わる。

# config/puma.rb
workers 4
preload_app!

before_fork do
  # fork 前に GC・昇格・コンパクションを親で済ませる
  Process.warmup if Process.respond_to?(:warmup)
end

代償もある。README は preload と phased restart（ワーカーを 1 つずつ再起動して新しいコードに入れ替える無停止再起動）は併用できないと明記している。preload したワーカーは master が持つ古いコードのコピーなので、ワーカーだけ再起動しても新しいコードにならないからだ。メモリを取るか、ワーカー単位の無停止入れ替えを取るかの選択になる。

💼 実務でどう出会うか

「Puma のワーカーを増やしたらコンテナが OOMKilled した」とき、各ワーカーの RSS × ワーカー数で見積もると過大になり、逆に fork 直後の使用量で見積もると時間が経って Private_Dirty が育った後に足りなくなる。容量計画はデプロイから数時間後の PSS 合計で行うとよい。ワーカーが日に日に重くなる現象には、CoW の剥がれと、2026-10-26 の記事で扱った malloc の断片化の 2 つが重なっていることが多く、Private_Dirty が育っているのか、ヒープの空きが返っていないのかを分けて見ると原因に近づける。Sidekiq や Unicorn、Python の gunicorn など、pre-fork 型のサーバーすべてに同じ構造がある。

⌨️ 手を動かす（5 分）

Docker の Linux コンテナ内で 300 万個の文字列を作ってから fork し、子の RSS・PSS・Private_Dirty が fork 直後と GC 後でどう変わるかを見る。2 回目は fork 前に Process.warmup を呼ぶ。

mkdir -p ~/cowtest && cat > ~/cowtest/cow.rb <<'EOF'
def mem(label)
  r = File.read("/proc/self/smaps_rollup")
  mb = ->(k) { r[/^#{k}:\s+(\d+)/, 1].to_i / 1024 }
  puts format("%-11s Rss=%4dMB Pss=%4dMB Private_Dirty=%4dMB",
    label, mb["Rss"], mb["Pss"], mb["Private_Dirty"])
end
data = Array.new(3_000_000) { |i| "item-#{i}" }
Process.warmup if ENV["WARMUP"]
mem("parent")
pid = fork do
  mem("child:fork")
  GC.start
  mem("child:GC")
end
Process.wait(pid)
EOF
docker run --rm -v ~/cowtest:/w ruby:3.3 ruby /w/cow.rb
docker run --rm -e WARMUP=1 -v ~/cowtest:/w ruby:3.3 ruby /w/cow.rb

手元で実行した例では、1 回目は child:fork で RSS が親とほぼ同じ 188MB なのに PSS は半分の 94MB、Private_Dirty は 0MB だった（親子 2 プロセスで共有しているので PSS は半分になる）。child:GC では Private_Dirty が 159MB に増え、何も書き換えていないのに大半がコピーされた。2 回目は child:GC の Private_Dirty が 27MB で止まり、共有が保たれた。数値は環境で変わるが、この差の傾向は観察できるはずだ。

🙅 よくある誤解
  • fork すると親のメモリが丸ごとコピーされる — 複製されるのはページテーブルで、データ本体は書き込まれたページだけがその時点でコピーされる。
  • ワーカーの RSS を足せば実使用量になる — RSS は共有ページを各プロセスに重複計上する。按分した PSS を足す方が実際の物理使用量に近い。
  • コードを書き換えないなら共有は崩れない — Ruby の GC や Python の参照カウントのように、ランタイム自身がオブジェクトのあるページに書き込むため、アプリが値を変えなくてもコピーは起きる。
