-p 3000:3000 と書いたのに、なぜコンテナのアプリに繋がらないのか？

Rails アプリを Docker に載せ、docker run -p 3000:3000 で起動した。ログには Listening on http://127.0.0.1:3000 と出ていて、アプリは確かに動いている。それなのにブラウザで localhost:3000 を開くと応答が無い。ホストの localhost とコンテナの localhost は、同じ場所を指しているのだろうか。

🎯 3 行まとめ
  • コンテナは自分専用のネットワーク空間（network namespace）を持ち、そこにはホストとは別の lo（127.0.0.1）と eth0 がある。コンテナ内の localhost はコンテナ自身だけを指す。
  • -p のポート転送は、ホストに来た通信をコンテナの eth0 側のアドレスへ届ける。アプリが 127.0.0.1 だけで待っていると、その通信を受け取れない。
  • コンテナ内のアプリは 0.0.0.0（全アドレス）で待たせる。外部への公開範囲を絞りたいときは、アプリ側ではなく -p 127.0.0.1:3000:3000 のようにホスト側で絞る。

「どのアドレスで待つか」もサーバーの設定である

サーバーがポートを開くとき、OS に渡しているのはポート番号だけではない。「どの IP アドレス宛ての接続を受け付けるか」も一緒に指定している。この操作を バインド（bind: ソケットにアドレスとポートを結びつけること）と呼ぶ。127.0.0.1 にバインドすれば、同じマシンの内部から 127.0.0.1 宛てに来た接続だけを受ける。0.0.0.0 にバインドすれば、そのマシンが持つ全てのアドレス宛ての接続を受ける。

127.0.0.1 は ループバックアドレス（loopback: 外に出ずに自分自身へ戻ってくる仮想的な宛先）で、lo という仮想インターフェースに割り当てられている。開発用サーバーの多くは、安全のためにこちらを既定にしている。Rails は 4.2 から rails server の既定を 0.0.0.0 から localhost に変えた。Vite の server.host も既定は 'localhost' だ。

Mac で直接動かしている限り、この既定で困ることはない。ブラウザもサーバーも同じマシンの上にいて、どちらの「localhost」も同じ lo を指すからだ。困るのは、サーバーを箱に入れて別の場所へ移したときである。

コンテナの中にはもう 1 つの localhost がある

コンテナは Linux の network namespace（ネットワーク名前空間）の中で動く。Linux の man ページによれば、network namespace はネットワークデバイス・IP プロトコルスタック・ルーティングテーブル・ファイアウォールルール・ポート番号を名前空間ごとに分離する。コンテナから見えるのは、自分専用の lo と、ホストと仮想ケーブル（veth ペア）でつながった eth0 だけだ。

つまりコンテナ内の 127.0.0.1 は、コンテナ自身にしか届かない。ホストの 127.0.0.1 とは名前が同じだけの、別の部屋の別の内線である。-p 3000:3000 を付けると、Docker はホストの 3000 番に来た通信を NAT（宛先アドレスを書き換えて転送する仕組み）でコンテナへ流す。このときの宛先はコンテナの eth0 のアドレスであって、コンテナの lo ではない。

［Mac ホスト］
  curl localhost:3000
      │
      ▼ -p 3000:3000 で受付
  Docker のポート転送（NAT）
      │ 宛先をコンテナの eth0 へ
      ▼
［コンテナ = 別の network namespace］
  ├ eth0 <コンテナの IP>  ◀ ここに届く
  └ lo   127.0.0.1        ◀ 内部専用

  127.0.0.1:3000 で listen
      → eth0 宛てを受け取れない ✗
  0.0.0.0:3000 で listen
      → eth0 も lo も受け取れる ✓

アプリが 127.0.0.1:3000 で待っていると、eth0 宛てに届いた接続を引き受けるソケットがコンテナ内に存在しない。転送の仕組みは正しく動いているのに、最後の 1 歩で行き場を失う。アプリのログにリクエストが 1 件も出ないのはこのためだ。

🍱 たとえるなら

マンションの各部屋に「内線 1 番」がある。302 号室（コンテナ）の住人が「内線 1 番にかかってきた電話だけ取る」と決めていると、管理人室（ホスト）が外線を 302 号室の部屋番号宛てに転送しても、住人は出ない。管理人室の内線 1 番と 302 号室の内線 1 番は番号が同じだけで別の回線だからだ。住人が「この部屋に来た電話は全部取る」（0.0.0.0）と決めて初めて、転送された外線がつながる。

直し方はアプリ側の 1 行

コンテナで動かすサーバーは 0.0.0.0 にバインドする。主なサーバーの指定方法は次のとおりで、どれも「指定しないと何で待つか」が違う。

# Rails: 既定は localhost
bin/rails server -b 0.0.0.0

# Vite: 既定は 'localhost'。--host 単独でも全アドレス
npx vite --host 0.0.0.0

# Python http.server: 既定で全インターフェース
python -m http.server 8000

Go の net/http ではアドレス文字列の書き方で決まる。ホスト部を空にした ":8080" は全アドレスで待ち、"localhost:8080" や "127.0.0.1:8080" はループバックだけで待つ。手元では動いていたのに、コンテナに入れた途端に繋がらなくなる Go アプリは、たいていこの文字列にホスト名が入っている。

// コンテナ内で外から受けるならホスト部を空に
http.ListenAndServe(":8080", mux)       // ✓
http.ListenAndServe("localhost:8080", mux) // ✗

Dockerfile の CMD に -b 0.0.0.0 を書いておけば、起動のたびに指定し忘れることもない。EXPOSE 3000 は「このポートを使う」という記録で、それだけではバインド先もポート公開も変わらない点に注意する。

0.0.0.0 にすると危ないのでは？

0.0.0.0 は「全世界に公開する」という意味に聞こえるので、ためらう人が多い。しかしコンテナ内の 0.0.0.0 が指すのは、そのコンテナの network namespace にあるアドレス全部、つまり lo と eth0 だけだ。ホストの外から直接届く経路は、-p で開けない限り存在しない。

本当に気にすべきなのはホスト側だ。Docker の公式ドキュメントは「コンテナのポート公開は既定では安全ではない」と明記している。-p 3000:3000 のようにホストのアドレスを省略すると、Docker はホストの全アドレス（0.0.0.0 と [::]）でポートを公開するので、同じネットワークにいる他のマシンからも届く。自分の Mac からだけ見たい開発用の DB などは、ホスト側のアドレスを書いて絞る。

# ホストの loopback だけで公開する
docker run -p 127.0.0.1:5432:5432 postgres

# compose.yaml でも同じ書き方
ports:
  - "127.0.0.1:5432:5432"

アプリのバインドは「コンテナの中で、どの入口から受けるか」、-p のアドレスは「ホストの、どの入口で公開するか」を決める。役割が違う 2 つの設定なので、アクセス範囲の制御はホスト側に任せ、コンテナ内は 0.0.0.0 にしておくのが素直な分担である。

💼 実務でどう出会うか

docker compose で Rails と Vite を立ち上げたら Rails だけ繋がらない、Go の API をコンテナ化したら手元の curl が通らない、といった形で出会う。docker logs で 127.0.0.1 や localhost で listen していると出ていたら、まずバインド先を疑う。逆方向の失敗も多い。コンテナ内のアプリから localhost:5432 で Mac 上の Postgres に繋ごうとしても、それはコンテナ自身の 5432 番を叩くだけで届かない。Docker Desktop ではホストのサービスに host.docker.internal という名前で到達できる。

⌨️ 手を動かす（5 分）

同じ Python サーバーを、127.0.0.1 だけで待たせた場合と全アドレスで待たせた場合で比べる。

# 1) loopback だけで待つ
docker run --rm -d --name lo-only -p 8000:8000 \
  python:3-slim python -m http.server 8000 --bind 127.0.0.1
sleep 2
curl -v http://localhost:8000/

# コンテナの内側からは届く
docker exec lo-only python -c \
  "import urllib.request as u;print(u.urlopen('http://127.0.0.1:8000/').status)"

# コンテナの eth0 のアドレスを確認
docker exec lo-only hostname -i
docker rm -f lo-only

# 2) 全アドレスで待つ（--bind なし）
docker run --rm -d --name all -p 8000:8000 \
  python:3-slim python -m http.server 8000
sleep 2
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:8000/
docker rm -f all

1) では Mac からの curl がエラーで終わる一方、docker exec で内側から叩くと 200 が返る。サーバーは動いていて、届かないのは外から来た分だけだと分かる。hostname -i で表示されるのが転送先の eth0 のアドレスだ。2) では Mac からも 200 が返る。1) の curl が「接続拒否」ではなく、いったん繋がってから切られるような表示になることが多いのも観察してほしい。ホスト側の 8000 番は Docker が受け付けているので、失敗するのはその先のコンテナへの転送だからだ。

🙅 よくある誤解
  • コンテナ内で 0.0.0.0 にバインドすると、インターネットに公開されてしまう — コンテナ内の 0.0.0.0 はそのコンテナの network namespace のアドレスだけを指す。ホスト外への公開範囲を決めるのは -p のホスト側アドレスで、こちらは省略すると全アドレスで公開される。
  • -p や EXPOSE を書けば、アプリに通信が届く — -p はホストからコンテナの eth0 までの経路を作るだけで、アプリがそのアドレスで待っていなければ受け取れない。EXPOSE は記録で、それ自体は公開もバインドもしない。
  • コンテナから localhost と書けば Mac 上のサービスに繋がる — コンテナ内の localhost はコンテナ自身を指す。Docker Desktop ではホスト上のサービスに host.docker.internal で繋ぐ。
