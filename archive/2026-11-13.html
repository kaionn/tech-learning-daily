ユーザーはもう画面を閉じたのに、なぜサーバーの重い処理は最後まで走り続けるのか？

集計画面が重いので、ユーザーは待ちきれずにタブを閉じた。ところがサーバーのログを見ると、その 30 秒後に「集計完了」が出ていて、DB には重いクエリが最後まで走った痕跡が残っている。受け取る相手がもういないのに、サーバーはなぜ仕事をやめなかったのだろうか。

🎯 3 行まとめ
  • Go の r.Context() はクライアントが切断すると「キャンセル済み」になるが、それは合図を出すだけで、実行中の処理を強制停止はしない
  • 止まるのは、ctx を受け取って ctx.Done() を見ている関数だけ。QueryContext や NewRequestWithContext に渡し続けて初めて、下流の DB や外部 API まで止まる
  • context.WithTimeout で上限時間を足し、返ってきた cancel は必ず defer で呼ぶ。DB 側でクエリが本当に止まるかはドライバと DB の設定にも依存する

サーバーは「もういらない」をどうやって知るのか

HTTP サーバーから見ると、ユーザーがタブを閉じたことは「TCP 接続が閉じられた」という出来事として届く。Go の net/http は、この出来事をハンドラに伝える窓口として r.Context() を用意している。公式ドキュメントによれば、受信リクエストの context は「クライアントの接続が閉じたとき、（HTTP/2 で）リクエストがキャンセルされたとき、または ServeHTTP が戻ったとき」にキャンセルされる。

ここで context（context.Context）とは、「この処理はもう不要になったか」「いつまでに終えるべきか」をリクエスト単位で運ぶ値である。中心にあるのは Done() というチャネルで、キャンセルされた瞬間にこのチャネルが close される。Err() はその理由を返し、明示的にキャンセルされたなら context.Canceled、期限切れなら context.DeadlineExceeded になる。

つまり、サーバーは切断にちゃんと気づいている。それでも処理が走り続けたのなら、気づいた後の伝わり方に問題がある。

キャンセルは「強制終了」ではなく「お知らせ」である

context がキャンセルされれば、ハンドラの goroutine も止まりそうに思える。しかし実際は、Go にはある goroutine を外から強制終了する手段がそもそも無い。context のキャンセルがすることは Done() のチャネルを close することだけで、そのチャネルを誰も見ていなければ何も起きない。この方式を協調的キャンセル（cooperative cancellation）と呼ぶ。止まる側が自分で合図を確認して、自分で処理を切り上げる方式である。

// ctx を見ていない：切断されても 5 秒寝続ける
time.Sleep(5 * time.Second)

// ctx を見ている：切断されたらすぐ抜ける
select {
case <-time.After(5 * time.Second):
case <-ctx.Done():
	return ctx.Err() // context.Canceled
}

冒頭の事故は、ハンドラの中で db.Query(...) のように context を受け取らない関数を呼んでいたことが原因であることが多い。database/sql の Query は内部で context.Background() を使う。これは決してキャンセルされない空の context なので、HTTP 側のキャンセルとの接点がどこにも無い。

ctx をバケツリレーで下流まで運ぶ

キャンセルを DB や外部 API まで届けるには、受け取った ctx を呼び出しの連鎖に沿って引数で渡し続ける。context は親子関係を持ち、WithTimeout や WithCancel で作った子 context は、親がキャンセルされると自動的にキャンセルされる。

ブラウザ ─ TCP 切断 ─▶ net/http
                        │ cancel
                        ▼
          ┌─────────────────────┐
          │ r.Context()  (親)  │
          └──────────┬──────────┘
          ┌──────────┴──────────┐
          ▼                     ▼
  ┌──────────────┐     ┌──────────────┐
  │ WithTimeout  │     │ NewRequest-  │
  │ QueryContext │     │ WithContext  │
  └──────┬───────┘     └──────┬───────┘
         ▼                    ▼
   DB の待ちを中断      外部 API を中断

  ctx を渡さない枝 ▶ 合図が届かず完走

公式のチュートリアルにある書き方はこうなる。

func report(ctx context.Context) error {
	ctx, cancel := context.WithTimeout(ctx, 5*time.Second)
	defer cancel()
	rows, err := db.QueryContext(ctx, "SELECT ...")
	...
}

この ctx に HTTP リクエストの context を渡すと、クエリは「リクエストがキャンセルされたとき」と「5 秒を超えたとき」のどちらか早いほうで止まる。WithTimeout を付けないと、上限はクライアント任せになる。切断しないクライアントや、タイムアウトを持たない内部呼び出しでは、処理は終わるまで走り続ける。外向きの HTTP 呼び出しも同じで、http.NewRequestWithContext(ctx, ...) で作ったリクエストは、接続の取得からレスポンスボディの読み取りまでがその context に縛られる。

Go のドキュメントは、context を構造体に保存せず、関数の第 1 引数 ctx として明示的に渡すよう求めている。構造体に入れると、どのリクエストの寿命に縛られているのかが呼び出し側から見えなくなるためである。

🍱 たとえるなら

レストランで客が注文を取り消して帰った場面である。ホール係は取り消しを知っているが、厨房に伝える手段は「注文伝票に赤い取り消し印を押す」ことだけだ。伝票を見ながら作業するコックは手を止めるが、伝票を見ずに覚えた注文を作り続けるコックは、皿を出すまで気づかない。context は伝票、ctx.Done() は取り消し印、ctx を受け取らない関数は伝票を見ないコックにあたる。

cancel を呼ばないと何が漏れるのか、DB 側で本当に止まるのか

WithTimeout は context と一緒に cancel 関数を返す。ドキュメントは「CancelFunc を呼ばないと、親がキャンセルされるまで子とその子孫が漏れる」と書いている。親が長寿命の context なら、タイマーや親子の紐付けが処理の終了後も残り続ける。このため defer cancel() を直後に書くのが定石で、go vet も cancel がすべての分岐で呼ばれているかを検査する。

ctx を正しく渡しても、DB サーバー上のクエリが即座に止まるとは限らない。キャンセル時の動作はドライバごとに違う。たとえば pgx（PostgreSQL 用の Go ドライバ）の既定の動作は、ネットワーク接続に期限を設定して待ちを打ち切るもので、別途 PostgreSQL に「このクエリを中止せよ」と送る cancel request 方式も選べる。前者の場合、Go 側は待つのをやめて接続を捨てるが、PostgreSQL は既定ではクエリ実行中に接続の生死を確かめない。

# postgresql.conf（Linux / macOS など）
client_connection_check_interval = 5s

この設定は、クエリ実行中にソケットを定期的に確認し、接続が閉じていればクエリを早めに中止させる。既定値は 0（確認しない）で、その場合サーバーが切断に気づくのは、次にソケットで送受信しようとしたときになる。結果を返す段になって初めて気づくので、重い集計はそこまで走りきってしまう。アプリ側の ctx と DB 側の設定は、両方そろって初めて「ユーザーが去ったら DB も止まる」になる。

💼 実務でどう出会うか

典型は、遅いエンドポイントにユーザーがリロードを連打し、そのたびに前の重いクエリが置き去りのまま走り、DB の CPU とコネクションプールが埋まる障害である。コードレビューでは「ctx を受け取っているのに下で context.Background() や Query（Context なし版）を使っていないか」を見る。逆に、レスポンス後も必ず完了させたい監査ログの書き込みなどでは、リクエストの ctx をそのまま渡すと切断で一緒に中断される。Go 1.21 で追加された context.WithoutCancel(ctx) は、値は引き継ぎつつ親のキャンセルだけを切り離すので、この用途に使える。ログに context canceled が大量に出るのは、多くの場合クライアントが先に去っただけで、サーバーの故障ではない。

⌨️ 手を動かす（5 分）

ctx を見ないハンドラと見るハンドラを並べ、クライアントが 2 秒で切断したときにサーバー側の処理が続くかを比べる。Go が入っていれば Mac でそのまま動く（go build で先にバイナリを作り、起動待ちを短くしている）。

mkdir -p /tmp/ctxdemo && cd /tmp/ctxdemo
cat > main.go <<'EOF'
package main

import (
	"fmt"
	"log"
	"net/http"
	"time"
)

func main() {
	http.HandleFunc("/ignore", func(w http.ResponseWriter, r *http.Request) {
		for i := 1; i <= 5; i++ {
			time.Sleep(time.Second)
			log.Printf("ignore: step %d", i)
		}
		fmt.Fprintln(w, "done")
	})
	http.HandleFunc("/respect", func(w http.ResponseWriter, r *http.Request) {
		ctx := r.Context()
		for i := 1; i <= 5; i++ {
			select {
			case <-time.After(time.Second):
				log.Printf("respect: step %d", i)
			case <-ctx.Done():
				log.Printf("respect: stopped: %v", ctx.Err())
				return
			}
		}
		fmt.Fprintln(w, "done")
	})
	log.Fatal(http.ListenAndServe("127.0.0.1:8080", nil))
}
EOF
go build -o ctxdemo main.go
./ctxdemo &
sleep 1
curl --max-time 2 http://127.0.0.1:8080/ignore
curl --max-time 2 http://127.0.0.1:8080/respect
sleep 5; kill %1

curl はどちらも 2 秒でタイムアウトする。しかしサーバーのログを見ると、/ignore は接続が切れた後も step 5 まで出力し続け、そのログが 2 本目の /respect のログに混ざって出てくる。/respect は切断の時点で stopped: context canceled を出して即座に抜ける。両者の差は、ctx.Done() を見ているかどうかだけである。

🙅 よくある誤解
  • context がキャンセルされれば goroutine は自動で止まる — キャンセルは Done() チャネルを close するだけで、goroutine を外から殺す仕組みは Go に無い。ctx.Done() を見る関数を呼んでいる箇所でだけ止まる。
  • QueryContext に ctx を渡せば DB サーバー上のクエリも即座に止まる — Go 側の待ちは打ち切られるが、サーバー上の実行が止まるかはドライバのキャンセル方式と DB 側の設定（PostgreSQL なら client_connection_check_interval など）による。
  • 親の ctx にタイムアウトがあるなら cancel は呼ばなくてよい — 呼ばないと、親がキャンセルされるまで子 context とそのタイマーが残る。defer cancel() は省略しない。
📖 用語ミニ辞典
context.Context
キャンセルの合図・期限・リクエスト単位の値を、関数呼び出しの連鎖に沿って運ぶ Go の標準型。
ctx.Done()
context がキャンセルされた瞬間に close されるチャネル。これを見ている処理だけが止まれる。
協調的キャンセル
外から強制終了するのではなく、止まる側が合図を確認して自分で処理を切り上げる方式。
context.WithTimeout
親から派生し、指定時間の経過か親のキャンセルのどちらか早いほうでキャンセルされる子 context を作る関数。
CancelFunc
派生 context を明示的にキャンセルして資源を解放する関数。呼ばないと親のキャンセルまで子が残る。
client_connection_check_interval
PostgreSQL がクエリ実行中にクライアント接続の生死を確認する間隔。既定 0 で確認しない。
