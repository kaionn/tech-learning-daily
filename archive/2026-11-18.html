import と書いただけなのに、なぜ Node は「Cannot use import statement outside a module」で落ちるのか？

TypeScript でもフロントエンドでも毎日 import を書いている。ところが Node でスクリプトを直接動かした途端、1 行目の import を指して SyntaxError: Cannot use import statement outside a module と怒られる。JavaScript の正式な構文を書いただけなのに、なぜ「モジュールの外」扱いされるのか。

🎯 3 行まとめ
  • Node には CommonJS（require）と ES Modules（import）という 2 つのモジュールローダーがあり、同じ .js をどちらで読むかを決める必要がある。
  • 判定に使うのは拡張子（.mjs/.cjs）と最寄りの package.json の "type" で、"type": "commonjs" の下の .js に import を書くと冒頭のエラーになる。
  • Node 22.12 / 20.19 以降は require() で ESM を読めるが、top-level await を含むモジュールは同期的に評価できないので今も import() が必要だ。

同じ .js に 2 つの読み方がある

Node が生まれた当時、JavaScript には標準のモジュール構文が無かった。そこで Node は CommonJS（CJS）という独自方式を採った。CJS はファイルの中身を関数で包んで実行し、その関数の引数として require・module・exports・__dirname を渡す方式だ。require() は普通の関数呼び出しなので、実行中のどこからでも同期的に呼べる。

のちに言語仕様に ES Modules（ESM）が入った。ESM は import/export を構文として持ち、ブラウザと共通の仕組みで動く。ESM では require も __dirname も定義されていない。代わりに import.meta.dirname と import.meta.filename がある（v21.2.0 / v20.11.0 で追加）。

問題は、どちらの形式も拡張子 .js を使うことだ。CJS として読むなら import 文は文法エラーで、ESM として読むなら require は未定義になる。つまり Node はファイルを実行する前に「どちらのローダーに渡すか」を決めなければならない。冒頭のエラーは、import を含むファイルが CJS ローダーに渡されたときに出る。

判定するのは中身ではなく「ファイルの外」

Node は書かれた構文を見て賢く判断してくれるように思える。しかし判定の主役はファイルの外にある情報だ。.mjs は常に ESM、.cjs は常に CJS として読まれる。.js の場合は、カレントから親ディレクトリへ遡って最初に見つかった package.json（node_modules かルートで探索は止まる）の "type" フィールドを見る。

{
  "name": "my-app",
  "type": "module"
}

"type": "module" にすると、そのパッケージ配下の .js はすべて ESM になり、require を書いた古いスクリプトは require is not defined で落ちるようになる。"type": "commonjs" なら .js はすべて CJS で、import を書けば冒頭のエラーになる。中身が ESM でも、明示された "type" が優先される。

"type" を書かなかった場合だけ、構文の検出が働く。Node はまず CJS として解析し、失敗して import/export などの ESM 構文が見つかれば ESM として読み直す。この検出は v22.7.0 と v20.19.0 で既定で有効になった。ただし 2 回解析する分のコストがあり、package.json があるのに "type" が無いと MODULE_TYPELESS_PACKAGE_JSON の警告が出る。公式ドキュメントは、すべて CJS のパッケージでも "type" を明示するよう勧めている。

🍱 たとえるなら

同じ形の封筒が、国内便の窓口と国際便の窓口のどちらかに振り分けられる郵便局だ。振り分け係は封筒を開けて中身を読まず、封筒の色（拡張子）か、差出人の住所録に書かれた「この事業所の封筒は全部国際便」という登録（"type"）で決める。国際便の書式で書いた手紙でも、国内便の窓口に回されれば「書式が違う」と突き返される。登録が無いときだけ、係が一度開けて中を確かめるが、その分だけ遅くなる。

require で ESM を読めなかった本当の理由

CJS から ESM 専用ライブラリを require() すると、以前の Node は ERR_REQUIRE_ESM で拒否した。当時の公式ドキュメントは「ES モジュールは非同期に実行されるため」と説明していた。ESM の読み込みは、依存ファイルを全部集めて解析する段階、import と export を結び付ける段階、実際にコードを評価する段階の 3 つに分かれており、ローダーもこれを非同期処理として実装していたからだ。

ところが言語仕様上、評価が非同期になるのは依存グラフのどこかに top-level await（関数の外に書いた await）がある場合に限られる。Node のコア開発者 Joyee Cheung がこの点を指摘し、top-level await を含まない ESM だけを同期的に読む require(esm) を実装した。この機能は v22.12.0 と v20.19.0 でフラグ無しで使えるようになり、v25.4.0 で experimental が外れている。

// CJS から ESM を読む（Node 22.12+ / 20.19+）
const m = require("./lib.mjs");
m.hi();        // named export はそのまま使える
m.default;     // default export は .default にある

require() が返すのはモジュール名前空間オブジェクトで、default export は .default に入る。読み込む ESM の依存グラフに top-level await が 1 つでもあれば ERR_REQUIRE_ASYNC_MODULE になり、その場合は await import() で読むしかない。同期の require() は、終わるまで待つ必要のある処理を途中で止めて待つ手段を持たないからだ。

逆向きの import は「推測」で成り立っている

ESM から CJS を import する方向は昔から動く。このとき CJS の module.exports がまるごと default export になる。import { name } from "./cjs.cjs" のような名前付き import も多くの場合動くが、これは Node がコードを実行せずに静的解析で exports.name = ... のような典型パターンを拾っているだけだ。

解析で見えない書き方、たとえば exports[key] = ... のように計算したキーで足したプロパティは名前付き export にならず、SyntaxError: Named export 'c' not found で落ちる。CJS の中身は実行してみるまで確定しないが、ESM は実行前の結び付け段階で名前を確定させる必要があるので、推測に頼るしかない。迷ったら import pkg from "pkg" で default を受け取り、pkg.c と参照すれば、実行後の module.exports から値を取り出せる。

ライブラリ側は package.json の "exports" で、読み手ごとに入口を分けられる。"import" 条件は import から、"require" 条件は require() から解決されたときに選ばれ、キーは書いた順に優先される。

"exports": {
  "import": "./dist/index.js",
  "require": "./dist/index.cjs"
}

この 2 つの入口が別々のファイルを指すと、同じライブラリが 2 回読み込まれて状態を共有しない、という事故が起こりうる。ESM 版と CJS 版を併せて配るパッケージを使うときは、この「二重読み込み」の可能性を頭に置いておくとよい。

💼 実務でどう出会うか

よくあるのは、依存ライブラリの新メジャー版が ESM 専用になり、CJS のままのアプリで ERR_REQUIRE_ESM が出る場面だ。まず node --version を見る。22.12 / 20.19 以降なら require(esm) で読める可能性が高く、それでも落ちるならライブラリ側の top-level await を疑う。もう一つは、TypeScript では動いていたのにビルド結果を node で直接動かすと落ちる場面だ。TypeScript は設定次第で import を require に変換して出力するため、ソース上の構文と実際に Node が受け取る形式がずれる。どちらも、最寄りの package.json の "type" と出力ファイルの拡張子を確認すれば原因の当たりが付く。

⌨️ 手を動かす（5 分）

Node 22.12 以降を入れた Mac で、"type" の有無で同じファイルの扱いが変わること、require(esm) の境界、名前付き import の推測の限界を確かめる。

cd "$(mktemp -d)"
echo '{"name":"modtest"}' > package.json
echo 'import { sep } from "node:path"; console.log("ESM として実行", sep);' > app.js
node app.js
echo '{"name":"modtest","type":"commonjs"}' > package.json
node app.js
echo 'export const hi = () => "hi";' > lib.mjs
echo 'console.log(require("./lib.mjs"));' > use.cjs
node use.cjs
printf 'await 0;\nexport const x = 1;\n' > tla.mjs
echo 'require("./tla.mjs");' > use2.cjs
node use2.cjs
printf 'exports.b = 2;\nconst k = "c";\nexports[k] = 3;\n' > c.cjs
echo 'import * as ns from "./c.cjs"; console.log(Object.keys(ns), ns.default);' > imp.mjs
node imp.mjs

1 回目の app.js は MODULE_TYPELESS_PACKAGE_JSON の警告付きで ESM として動き、"type": "commonjs" にした 2 回目は Cannot use import statement outside a module で落ちる。use.cjs は [Module: null prototype] { hi: [Function: hi] } を表示し、use2.cjs は ERR_REQUIRE_ASYNC_MODULE になる。最後の imp.mjs では名前付き export に b は現れるが c は現れず、default の中身には両方が入っていることが見えるはずだ。

🙅 よくある誤解
  • Node はファイルの中身を見て CJS か ESM かを判断する — 判定の主役は拡張子と最寄りの package.json の "type" だ。構文の検出が働くのは "type" が無いときだけで、明示された "commonjs" の下では import は文法エラーになる。
  • CJS から ESM は絶対に require できない — Node 22.12 / 20.19 以降は、top-level await を含まない ESM なら require() で同期的に読める。読めないのは依存グラフのどこかに top-level await がある場合だ。
  • CJS ライブラリでも名前付き import は常に使える — 名前付き export は静的解析による推測で、計算したキーなどで足したプロパティは拾われない。default import なら module.exports 全体を受け取れる。

CommonJS
Node が独自に採用したモジュール方式。ファイルを関数で包み、require() で同期的に読み込む。
ES Modules
言語仕様に定められたモジュール方式。import/export 構文を持ち、実行前に依存関係を結び付ける。
"type" フィールド
最寄りの package.json で .js を ESM（module）と CJS（commonjs）のどちらで読むかを決める設定。
require(esm)
top-level await を含まない ESM を require() で同期的に読む機能。Node 22.12 / 20.19 からフラグ不要。
top-level await
関数の外、モジュールの最上位に書いた await。これがあるとモジュールの評価が非同期になる。
