PgBouncer を挟んだだけなのに、なぜ「prepared statement "a1" does not exist」で落ちるのか？

Postgres の接続数が上限に近づいたので、アプリと DB の間に PgBouncer を入れた。接続先のポートを書き換えただけで、SQL は 1 行も変えていない。なのにデプロイ後、ときどき prepared statement "a1" does not exist が出てトランザクションごと失敗する。さっきまで存在していた文が、なぜ急に「無い」と言われるのか。

🎯 3 行まとめ
  • prepared statement や SET は PostgreSQL の「接続（セッション）」に保存される状態で、別の接続からは見えない。
  • PgBouncer の transaction pooling は接続をトランザクション単位で貸し替えるので、前の文で作った状態が次の文の接続には無い。
  • PgBouncer 1.21 以降はプロトコルレベルの prepared statement を肩代わりできるが、SQL の PREPARE・SET・advisory lock は今も壊れるので、ドライバ側の設定を合わせる。

prepared statement は「接続」に住んでいる

prepared statement は、SQL の構文解析と実行計画づくりを先に済ませ、名前を付けてサーバーに置いておく仕組みだ。2 回目以降は名前とパラメータだけを送ればよいので、同じ形のクエリを何度も投げる Web アプリでは解析の手間が省ける。Rails（Active Record）の PostgreSQL アダプタも pgx（Go）も、既定でこれを使う。

見落としやすいのは保存場所だ。PostgreSQL の公式ドキュメントは「prepared statement は現在のデータベースセッションの間だけ存在する」と明記している。セッションとは 1 本の接続の生存期間のことで、PostgreSQL は接続ごとにバックエンドプロセスを 1 つ立てて状態を持たせる。接続 1 で作った a1 は、接続 2 からは存在しない。

同じ性質を持つものはほかにもある。SET statement_timeout のようなセッション変数、LISTEN、セッションレベルの advisory lock（アプリが任意の番号で取る協調用ロック）、一時テーブルも、すべて接続にひも付く。アプリが接続を握り続けている限り、これらが問題になることはなかった。

transaction pooling は接続を「又貸し」する

PgBouncer にはプールモードが 3 つある。設定 pool_mode の既定値は session で、クライアントが接続している間ずっと同じサーバー接続を割り当てる。この場合は接続が減らないので、接続数対策として入れるなら transaction を選ぶことになる。

; pgbouncer.ini
[pgbouncer]
pool_mode = transaction
default_pool_size = 20   ; 既定値も 20

transaction モードでは、サーバー接続はトランザクションの間だけクライアントに貸し出され、終わった瞬間にプールへ返る。BEGIN を書かない単発クエリは自動コミットで 1 文 1 トランザクションなので、文ごとに別の接続へ行きうる。数百のアプリ側接続を、default_pool_size 本ぶんのサーバー接続で使い回せるのはこのためだ。

Rails          PgBouncer        Postgres
  │               │
  │ PREPARE a1 ──▶│──▶ 接続 1 に a1 作成
  │               │   (文が終わり接続 1 返却)
  │ EXECUTE a1 ──▶│──▶ 接続 2 へ転送
  │               │   接続 2 に a1 は無い
  │◀── ERROR: prepared statement
  │        "a1" does not exist

アプリから見れば接続は 1 本のままなので、「さっき作った文がある」と信じて名前で呼ぶ。しかし実際に届いた先は、別のクライアントが使い終えた接続 2 だ。冒頭のエラーはこうして出る。同じ接続にたまたま戻れば成功するため、症状は「ときどき」になる。

🍱 たとえるなら

ホテルのフロントに荷物を預け、預かり札をもらったとする。ところがこのホテルは用件が 1 つ済むたびに担当者が交代し、各担当者は自分の引き出しにしか荷物を入れない。次に札を出した相手が別の担当者なら「そんな荷物はありません」と言われる。荷物は消えていない。別の担当者の引き出しにあるだけだ。

1.21 で直ったはず、なのにまだ落ちる

PgBouncer 1.21.0（2023 年 10 月）は、プロトコルレベルの名前付き prepared statement に対応した。プロトコルレベルとは、SQL 文の PREPARE ではなく、ドライバが通信プロトコルの Parse メッセージで文を準備する方式を指す。設定 max_prepared_statements を 0 以外にすると、PgBouncer はクライアントが付けた名前を覚え、どのサーバー接続に行っても文が用意されているよう内部名に書き換えて転送する。既定値は 1.24.0 から 200 になり、何もしなくても有効だ。

これで解決したように思える。しかし実際には、新しい PgBouncer の前でも Rails が同じエラーで落ちる例がある。原因は文を捨てる側だ。Active Record は接続ごとに既定で最大 1000 個（statement_limit）の文を作り、上限を超えると古い文を捨てる。古い pg gem / libpq はこれを SQL の DEALLOCATE a1 で送る。PgBouncer の書き換えは SQL レベルのコマンドには効かず、そのまま Postgres へ素通しされるので、実在しない名前 a1 を消そうとしてエラーになり、トランザクション内なら全体が中断する。

ClickHouse の Managed Postgres ガイドによれば、pg gem 1.6 以降で libpq 17 以降を使う組み合わせなら、捨てる処理もプロトコルの Close メッセージで送られ、Rails の既定設定のまま動く。プリコンパイル版の pg 1.6 には libpq 18 が同梱されている。アップグレードできないなら、prepared statement を切るのが確実な回避策だ。

# config/database.yml
production:
  adapter: postgresql
  prepared_statements: false  # 毎回 SQL を送る
  advisory_locks: false       # マイグレーション用ロックを止める

prepared_statements: false にすると、クエリは毎回パラメータ付きで解析し直されるため、解析コストは戻ってくる。その代わり接続をまたいでも壊れない。Go の pgx も既定の cache_statement モードが prepared statement を使う。PgBouncer が 1.21 より古いか機能が無効なら、接続文字列に default_query_exec_mode=exec を足す。pgx のドキュメントは、describe_exec は準備と実行が別の接続に振られうるため transaction pooling では使わないよう注意している。

SET と advisory lock はもっと静かに壊れる

PgBouncer の機能表では、SET/RESET・LISTEN・SQL の PREPARE・セッションレベルの advisory lock は transaction pooling で「Never」（使えない）とされている。prepared statement はエラーで気づけるが、こちらはエラーにならないものがある分、たちが悪い。

たとえば単発の SET statement_timeout = '5s' を送ると、その設定は送った瞬間のサーバー接続に残る。続く重いクエリは別の接続に行ってタイムアウトが効かず、逆に設定が残った接続は、無関係な別クライアントのクエリを 5 秒で打ち切る。session モードなら返却時に server_reset_query（既定 DISCARD ALL）で状態を消すが、transaction モードではこのリセットは使われない。トランザクション内で SET LOCAL を使えば、効果はそのトランザクションの終わりで消えるので安全だ。Heroku のドキュメントも、database.yml の variables に書いたセッション変数は PgBouncer 越しでは効かないと注意している。

Rails のマイグレーションは同時実行を防ぐためにセッションレベルの advisory lock を取る。transaction pooling では解放の命令が別の接続に届きうるので、ロックが握られたまま残り、次のマイグレーションが失敗する。advisory_locks: false にするか、マイグレーションだけ PgBouncer を通さず Postgres に直接つなぐ。前者を選ぶなら、マイグレーションを走らせるデプロイが同時に 1 つだけになるよう運用で担保する。

💼 実務でどう出会うか

典型はマネージドの接続プーラーだ。Heroku Postgres の connection pooling は PgBouncer の transaction モードで動き、同じ構成のプーラーを提供するマネージド Postgres は多い。接続数対策でプーラー経由の URL に切り替えた直後に、prepared statement ... does not exist、マイグレーションの lock 取得失敗、statement_timeout の効きムラが出たら、まず pool_mode と PgBouncer のバージョン、ドライバの prepared statement 設定を確認する。DB 側のログに出るのは「名前が無い」というエラーだけなので、アプリのバグと見誤りやすい。

⌨️ 手を動かす（5 分）

PgBouncer を立てなくても、核心は再現できる。psql を起動し直すと新しい接続になるので、「別の接続に回された」状態を手で作れる。1 回の psql に複数の -c を渡すと、同じ接続で順に実行される。

docker run -d --name pg -e POSTGRES_PASSWORD=pw postgres:17
sleep 5
# 同じ接続: PREPARE して EXECUTE
docker exec pg psql -U postgres -c "PREPARE q1 AS SELECT 42;" -c "EXECUTE q1;"
# 別の接続: EXECUTE だけ
docker exec pg psql -U postgres -c "EXECUTE q1;"
# SET も接続にしか残らない
docker exec pg psql -U postgres -c "SET statement_timeout = '1s';" -c "SHOW statement_timeout;"
docker exec pg psql -U postgres -c "SHOW statement_timeout;"
docker rm -f pg

1 本目は 42 を返し、2 本目は ERROR: prepared statement "q1" does not exist になるはずだ。SET も同様で、同じ接続では 1s、新しい接続では既定の 0（無効）に戻る。transaction pooling は、この「接続の付け替え」をアプリに知らせずに毎トランザクション行っている。

🙅 よくある誤解
  • PgBouncer は透過的なので、接続先を変えるだけで導入できる — 透過的なのは session モードだけだ。接続数を減らせる transaction モードでは、接続にひも付く機能（prepared statement・SET・LISTEN・advisory lock）の前提が崩れるので、アプリ側の設定を合わせる必要がある。
  • PgBouncer を新しくすれば prepared statement の問題は全部消える — 1.21 以降が肩代わりするのはプロトコルレベルの準備と実行だけだ。SQL の PREPARE/DEALLOCATE は素通しなので、古い pg gem のように SQL で文を捨てるドライバはまだ壊れる。
  • エラーが出ていなければ transaction pooling に対応できている — SET で変えたセッション変数は、別の接続に行ってもエラーにならず単に効かないだけで、残った接続では別クライアントに効いてしまう。エラーの有無ではなく、接続にひも付く機能を使っていないかで判断する。
📖 用語ミニ辞典
prepared statement
解析済みの SQL に名前を付けてサーバーに置き、名前とパラメータだけで実行する仕組み。接続ごとに存在する。
セッション
1 本の DB 接続の生存期間と、その間に積み上がる状態（変数・準備済みの文・ロック）。
transaction pooling
PgBouncer がサーバー接続をトランザクションの間だけ貸し出し、終わるとプールへ戻すモード。
max_prepared_statements
PgBouncer がプロトコルレベルの prepared statement を追跡・書き換えする機能の設定。0 で無効、1.24.0 から既定 200。
advisory lock
アプリが任意の番号で取る PostgreSQL の協調用ロック。セッションレベルのものは接続にひも付く。
