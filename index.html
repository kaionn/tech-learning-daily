DB が数秒詰まっただけなのに、なぜ全部の Pod が一斉に再起動するのか？

「ちゃんと動いているか確かめたいから」と、/healthz の中で DB に SELECT 1 を投げるようにした。ある日、DB が重いクエリで数十秒詰まった。DB が戻ったあとも API はしばらく復旧せず、kubectl get pods を見ると全 Pod の RESTARTS が揃って増えていた。壊れていたのは DB なのに、なぜアプリの Pod が全部再起動されたのだろうか。

🎯 3 行まとめ
  • Kubernetes の probe は 3 種類あり、失敗したときの「罰」が違う。liveness と startup は失敗でコンテナを再起動し、readiness は Service の宛先から外すだけ。
  • liveness probe に DB などの外部依存を含めると、依存先の不調で全 Pod が同時に再起動され、障害が広がる。liveness は「このプロセスが自力で回復できない状態か」だけを確かめる。
  • 既定値は periodSeconds: 10・timeoutSeconds: 1・failureThreshold: 3。起動の遅いアプリは liveness を緩めるのではなく startupProbe で守る。

probe は kubelet が定期的に行う「健康診断」

probe とは、各ノードで Pod を管理するエージェントである kubelet が、コンテナに対して定期的に行う診断である。HTTP リクエスト（httpGet）、TCP 接続（tcpSocket）、gRPC のヘルスチェック、コンテナ内でのコマンド実行（exec）のいずれかで確かめる。httpGet ではステータスコードが 200 以上 400 未満なら成功、それ以外は失敗と判定される。

結果は成功・失敗・不明の 3 つで、kubelet は失敗にだけ反応する。probe を定義していない場合、kubelet は常に成功とみなす。つまり probe を何も書かなければ「プロセスが生きている限り健康」という扱いになり、プロセスが落ちたときだけ restartPolicy に従って再起動される。

ここで押さえておきたいのは、probe は 1 回の失敗では何もしないという点である。failureThreshold（既定 3）回連続で失敗して初めて「失敗」と判定される。既定の periodSeconds: 10 と組み合わせると、約 30 秒間ずっと失敗し続けたら反応する計算になる。

3 種類の probe は「失敗したときの罰」が違う

3 種類の probe は書き方がほぼ同じだが、失敗時に kubelet が取る行動がまったく違う。この違いが今日の問いの答えになる。

   ▼            ▼            ▼
startup     liveness     readiness
（起動時だけ） （ずっと）    （ずっと）

│を再起動│ │を再起動│ │宛先から外す│

                       プロセスは
                       そのまま動く

readiness probe は「いまリクエストを受けられるか」を表す。失敗すると、EndpointSlice コントローラが Service の宛先一覧（EndpointSlice）からその Pod の IP を外すので、新しいリクエストが届かなくなる。プロセスは殺されないため、状況が戻って probe が成功すれば自動で宛先に復帰する。readiness probe は起動時だけでなく、コンテナが動いている間ずっと実行される。

liveness probe は「このプロセスは生きているが、もう自力では立ち直れない状態か」を表す。公式ドキュメントが挙げる典型例はデッドロックで、プロセスは存在するのに処理が一歩も進まない状態である。失敗すると kubelet はコンテナを kill し、restartPolicy に従って再起動する。startup probe は起動完了の判定専用で、成功するまで liveness と readiness を実行させない。失敗した場合は liveness と同じく再起動になる。

🍱 たとえるなら

readiness は飲食店の「準備中」の札、liveness は店長を呼んで店員を交代させる判断である。仕入れ業者（DB）の配送が遅れて料理が出せないとき、正しい対応は札を「準備中」にして客を他店舗へ回すこと（readiness）だ。ここで店員を全員交代させても（liveness）、配送は早まらない。新しい店員が仕込みからやり直すぶん、配送が戻ったあとの再開もかえって遅れる。

DB を見る liveness が全 Pod を道連れにする仕組み

「DB に繋がらないアプリは不健康なのだから、再起動されて当然」と思える。しかし DB が詰まっている状況で再起動しても、DB は速くならない。しかも DB は全 Pod が共有しているので、全 Pod の liveness probe がほぼ同じタイミングで失敗する。結果として全レプリカが同時に再起動され、DB の不調だけだった障害が「アプリが全滅した」障害に広がる。

再起動はさらに復旧を遅らせる。再起動直後のアプリは接続プールの確立やキャッシュの温め直しから始めるため、DB が戻った瞬間に全 Pod が一斉に接続を張りに行き、DB に負荷の山を作る。加えて、繰り返し落ちたコンテナには再起動の待ち時間（バックオフ）が 10 秒、20 秒、40 秒…と倍々で入り、上限は 300 秒である。これが CrashLoopBackOff 状態で、DB が戻っても Pod がすぐには上がってこない理由になる。

負荷が原因の場合も同じ構造になる。timeoutSeconds の既定は 1 秒なので、高負荷で /healthz の応答が 1 秒を超えると probe は失敗する。忙しい Pod から順に再起動されると、残りの Pod に負荷が寄ってさらに遅くなり、次の Pod も再起動される。公式ドキュメントも、誤った liveness probe は高負荷時の再起動と残りの Pod への負荷集中という連鎖障害（cascading failure）を招くと注意している。

対策は、エンドポイントを役割で分けることである。liveness 用はプロセス内部だけで完結する軽い応答にし、外部依存は見ない。DB や下流サービスの状態を反映したいなら readiness 用のエンドポイントに入れる。そうすれば DB が詰まったときは全 Pod が宛先から外れ、そのあいだのリクエストはエラーになる。それでもプロセスと接続プールは生き残るので、DB が戻れば次の probe の成功で宛先に復帰し、仕込み直しは要らない。

livenessProbe:
  httpGet:
    path: /livez     # プロセス内部だけを見る
    port: 8080
readinessProbe:
  httpGet:
    path: /readyz    # DB 等の依存もここで見る
    port: 8080

設定値は「何秒で反応するか」で読む

probe の各フィールドは、組み合わせて「何秒失敗が続いたら反応するか」として読むと挙動が掴みやすい。読者が最初に触るべきものから順に並べる。

periodSeconds（既定 10、最小 1）は実行間隔で、短くするほど異常に早く反応するが、exec probe ではそのたびにプロセスが fork されるため、Pod 密度の高いノードでは CPU 負荷になる。failureThreshold（既定 3）は連続失敗の許容回数で、上げるほど一時的な遅延に強くなる代わりに、本当に固まったときの検出が遅れる。公式ドキュメントは、liveness と readiness に同じ軽いエンドポイントを使い、liveness 側だけ failureThreshold を高くするパターンを紹介している。こうすると、まず宛先から外れ、それでも戻らないときだけ再起動される。

timeoutSeconds（既定 1、最小 1）は 1 回の応答待ちの上限である。GC の停止や高負荷で 1 秒を超えうるアプリなら、ここを少し伸ばすほうが誤検知を減らせる。successThreshold（既定 1）は失敗後に何回連続成功したら戻すかで、liveness と startup では 1 以外を指定できない。initialDelaySeconds（既定 0）は起動後に probe を始めるまでの待ち時間である。

起動に時間がかかるアプリで liveness の initialDelaySeconds を大きくするのは筋が悪い。その秒数のあいだ liveness はまったく働かず、しかも起動時間がばらついて値を超えれば、結局起動途中で kill されるからだ。公式ドキュメントは、起動時間が initialDelaySeconds + failureThreshold × periodSeconds（既定なら 0 + 3 × 10 = 30 秒）を超えうるなら、liveness と同じエンドポイントを見る startupProbe を足し、その failureThreshold を十分高くするよう勧めている。

startupProbe:
  httpGet:
    path: /livez
    port: 8080
  failureThreshold: 30   # 30 × 10 秒 = 最大 300 秒待つ
  periodSeconds: 10
💼 実務でどう出会うか

典型的なのは、フレームワークのヘルスチェック機能（DB・Redis・外部 API を全部まとめて確認する /health）をそのまま liveness に設定しているケースである。障害時に kubectl describe pod の Events に Liveness probe failed と Killing が並び、全 Pod の RESTARTS が同時に増えていたら、このパターンを疑う。また、プロセスがエラーで自分から落ちるタイプのアプリなら、公式ドキュメントのとおり liveness probe 自体が不要なこともある。落ちれば restartPolicy で再起動されるからだ。

⌨️ 手を動かす（5 分）

kind で作ったローカルクラスタに、ファイルの有無で成否が決まる exec probe を持つ Pod を立て、readiness と liveness の失敗時の違いを観察する。

kind create cluster --name probe-lab

cat <<'YAML' | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: probe-demo
spec:
  terminationGracePeriodSeconds: 1
  containers:
  - name: app
    image: busybox:1.36
    command: ["sh", "-c", "touch /tmp/ready /tmp/alive; sleep 3600"]
    readinessProbe:
      exec: { command: ["cat", "/tmp/ready"] }
      periodSeconds: 2
    livenessProbe:
      exec: { command: ["cat", "/tmp/alive"] }
      periodSeconds: 2
YAML

kubectl wait --for=condition=Ready pod/probe-demo --timeout=60s

# 1) readiness を失敗させる
kubectl exec probe-demo -- rm /tmp/ready
sleep 10; kubectl get pod probe-demo

# 2) liveness を失敗させる
kubectl exec probe-demo -- rm /tmp/alive
sleep 15; kubectl get pod probe-demo
kubectl describe pod probe-demo | tail -n 8

kind delete cluster --name probe-lab

1) の後は READY が 0/1 になるが、RESTARTS は 0 のまま増えない。プロセスは動き続け、宛先から外れただけである。2) の後は RESTARTS が 1 に増え、Events に Liveness probe failed と、コンテナを kill して再起動した記録が出る。再起動したコンテナでは起動コマンドが両方のファイルを作り直すので、READY も 1/1 に戻る。terminationGracePeriodSeconds: 1 は kill 時の猶予（Pod の既定は 30 秒）を縮めて、再起動を待たずに観察するための指定である。

🙅 よくある誤解
  • liveness と readiness は同じヘルスチェックを 2 回書くもの — 失敗時の行動が「再起動」と「宛先から外す」で違う。外部依存のように再起動しても直らない理由で失敗しうる確認は、readiness だけに入れる。
  • readiness probe は起動完了の確認なので、一度成功すれば以後は実行されない — readiness はコンテナが動いている間ずっと実行され、途中で失敗すれば Pod はいつでも宛先から外れる。起動時だけ実行されるのは startup probe である。
  • httpGet probe は {"status":"ng"} のような本文も読んで判定してくれる — 判定に使われるのはステータスコードだけで、本文は見ない（kubelet は本文を 10KiB 以降読まない）。異常を伝えたいなら 200〜399 以外のステータスコードを返す必要がある。
📖 用語ミニ辞典
liveness probe
プロセスが自力で回復できない状態かを確かめる診断。連続失敗でコンテナを再起動する。
readiness probe
リクエストを受けられるかを確かめる診断。失敗すると Service の宛先から外れるが、プロセスは動き続ける。
startup probe
起動完了の判定専用の診断。成功するまで liveness / readiness を止め、失敗が続くと再起動する。
kubelet
各ノードで動き、Pod のコンテナの起動・監視・probe の実行を担うエージェント。
CrashLoopBackOff
再起動を繰り返すコンテナに、倍々に伸びる待ち時間（上限 300 秒）が入っている状態。
連鎖障害（cascading failure）
一部の不調が再起動や負荷集中を通じて、ほかの正常な部分まで巻き込んで広がる障害。
