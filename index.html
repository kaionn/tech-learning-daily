100 万回ずつ count++ しただけなのに、なぜ 2 つの goroutine の合計は 200 万にならないのか？

goroutine を 2 つ起動し、それぞれ共有の変数に count++ を 100 万回実行させる。終わるのを待って表示すると、出てくるのは 200 万に届かない数字で、しかも実行のたびに値が変わる。足し算を 1 回も書き間違えていないのに、カウントはどこへ消えたのだろうか。

🎯 3 行まとめ
  • count++ は 1 行だが、CPU から見ると「読む・足す・書く」の 3 手順で、その途中に別の goroutine が割り込める
  • 2 つが同じ古い値を読んで書き戻すと、片方の +1 が上書きされて消える。これがデータ競合（data race）による更新の消失である
  • sync.Mutex か sync/atomic でアクセスを直列化し、go test -race で実際に起きた競合を検出する

再現するコード：1 行も間違っていないのに数が合わない

まず問題のコードを見る。sync.WaitGroup は「起動した goroutine が全部終わるまで待つ」ためのカウンタで、Add で待つ数を増やし、各 goroutine が Done で減らし、Wait が 0 になるまでブロックする。

var count int
var wg sync.WaitGroup
for i := 0; i < 2; i++ {
	wg.Add(1)
	go func() {
		defer wg.Done()
		for j := 0; j < 1000000; j++ {
			count++
		}
	}()
}
wg.Wait()
fmt.Println(count) // 2000000 にならない

待ち合わせは正しく、ループ回数も正しい。それでも合計が足りないのは、ロジックの誤りではなく、2 つの goroutine が同じ変数を同時に触っていることが原因である。マルチコアの CPU では、2 つの goroutine は別々のコアで文字どおり同時に走りうる。

1 行に見えて 3 手順：更新が消える瞬間

count++ は 1 つの操作に見える。しかし実際は、メモリから値をレジスタ（CPU 内部の作業用の置き場）へ読み込み、1 を足し、結果をメモリへ書き戻すという 3 手順に分かれる。この「読んで・変えて・書く」の組を read-modify-write と呼ぶ。3 手順のあいだに他のコアが同じ場所を読み書きしても、CPU は通常の命令ではそれを止めない。

  メモリ上の count = 41

  goroutine A       goroutine B
  ───────────       ───────────
  ① 読む → 41
                    ② 読む → 41
  ③ 足す → 42
                    ④ 足す → 42
  ⑤ 書く → 42
                    ⑥ 書く → 42
                         │
                         ▼
  結果 count = 42（+2 のはずが +1）

図のように、A が書き戻す前に B が同じ 41 を読むと、2 人とも 42 を書き込む。2 回分の加算をしたのに値は 1 しか増えず、A の +1 は B の書き込みで上書きされて跡形もなく消える。100 万回のループではこの重なりが何十万回も起きうるため、合計は大きく欠ける。重なる回数はタイミング次第なので、実行ごとに結果が変わる。

Go のメモリモデルは、この状況をデータ競合（data race）と定義している。「あるメモリ位置への書き込みが、同じ位置への別の読み書きと並行して起きること。ただしすべてのアクセスが sync/atomic による atomic なアクセスである場合を除く」。そして並行に触られるデータを変更するプログラムは、そのアクセスを直列化（同時に 1 つずつしか触れないように）しなければならない、とも明記している。

🍱 たとえるなら

ホワイトボードに書かれた来場者数を、入口係 2 人が更新する場面に近い。それぞれ「ボードを見て数字を覚える → 頭の中で +1 → 消して書き直す」を繰り返す。2 人が同時にボードを見て 41 と覚えれば、2 人とも 42 と書き、1 人分の来場が記録から消える。防ぐ方法は、マーカーを 1 本だけにして持っている人しかボードに触れないようにすること（Mutex）か、押すと必ず 1 増える数取器に置き換えること（atomic）である。

直し方 2 つ：Mutex と atomic はどう使い分けるか

1 つ目は sync.Mutex（相互排他ロック）で、Lock から Unlock までの区間に同時に 1 つの goroutine しか入れないようにする。ほかの goroutine が保持している間に Lock を呼ぶと、解放されるまでブロックする。ゼロ値がそのまま「ロックされていない Mutex」なので初期化は不要である。

var mu sync.Mutex
// ...
mu.Lock()
count++
mu.Unlock()

2 つ目は sync/atomic で、読む・足す・書くを CPU の専用命令で不可分（途中に割り込めない 1 手順）に行う。Go 1.19 で追加された atomic.Int64 型を使うと、Add が「値に delta を atomic に足して新しい値を返す」。

var count atomic.Int64
// ...
count.Add(1)
// 読むときも count.Load() を使う

使い分けの基準は「守りたいのが 1 つの変数か、複数の値の組か」である。単一のカウンタなら atomic が軽い。しかし「残高を減らしたら履歴にも 1 行足す」のように 2 つの値をそろって変えたい場合、それぞれを atomic にしても、間の瞬間に他の goroutine が不整合な組を見る。この場合は Mutex で区間ごと守る必要がある。公式ドキュメントも sync/atomic について「正しく使うには細心の注意が要る」とし、特殊な低レベル用途以外はチャネルや sync パッケージを勧めている。

Mutex を使うときの落とし穴がもう 1 つある。sync.Mutex は「最初に使った後はコピーしてはならない」。Mutex を含む構造体を値渡しやレシーバの値コピーで扱うと、コピー先は別の錠になり、守っているつもりで何も守らない。Mutex を持つ型のメソッドはポインタレシーバで書く。

テストが通っても安心できない理由と、race detector

データ競合は毎回壊れるとは限らない。そう思える。しかし実際はもっと厄介で、ループ回数が少なかったり、たまたま goroutine が時間差で走ったりすると、正しい結果が出てしまう。ローカルのテストは緑なのに、本番の高負荷でだけ数字がずれる、という形で表に出ることが多い。

そこで使うのが Go の race detector である。go test / go run / go build に -race を付けると、メモリアクセスを監視するコードが埋め込まれ、競合が起きると WARNING: DATA RACE と、競合した 2 つのアクセスのスタックトレースを出す。公式ドキュメントによれば、典型的なプログラムでメモリ使用量が 5〜10 倍、実行時間が 2〜20 倍になるため、本番バイナリには常用せず、CI のテストや負荷をかけた検証環境で使う。

ただし race detector は「実行時に実際に起きた競合」しか見つけない。通らなかったコードパスの競合は報告されないので、-race で何も出ないことは競合がない証明にはならない。カバレッジの薄いテストより、-race 付きでビルドしたバイナリに現実的な負荷をかけた方が多く見つかる、と公式ドキュメントも書いている。

挙動は環境変数 GORACE で調整できる。既定では競合を報告しても実行を続け、終了時の終了コードが 66 になる。halt_on_error=1 にすると最初の競合を報告した時点で止まり、ログの洪水を避けられる。exitcode で終了コードを変えられるので、CI で「競合が出たら失敗」の判定に使える。

GORACE="halt_on_error=1" go test -race ./...

map では同じ問題がさらに激しく出る。Go 1.6 以降のランタイムは map の並行な誤用をベストエフォートで検出し、検出すると診断を表示してプログラムをクラッシュさせる。カウンタのように「数がずれる」では済まず、プロセスが落ちるので、共有 map への並行書き込みも Mutex で守る。

💼 実務でどう出会うか

Go の HTTP サーバーはリクエストごとに goroutine を起動するため、ハンドラから触るパッケージ変数や構造体のフィールド（アクセス数のカウンタ、メモリ上のキャッシュ用 map）は、それだけで複数 goroutine からの並行アクセスになる。ローカルで 1 リクエストずつ試すと再現せず、負荷試験や本番で初めて数字のずれや concurrent map writes のクラッシュとして現れる。同じ構造は Puma のスレッドで動く Rails でも起こりうる。クラス変数やメモ化（@cache ||= ...）を複数スレッドで共有すると、読んでから書くまでの間に別スレッドが割り込む余地がある。CI の Go テストには最初から -race を付けておくのが、もっとも手間の少ない予防になる。

⌨️ 手を動かす（5 分）

Go が入った Mac で、更新の消失と race detector の報告を自分の目で確かめる。

mkdir -p /tmp/racedemo && cd /tmp/racedemo
cat > main.go <<'EOF'
package main

import (
	"fmt"
	"sync"
)

func main() {
	var count int
	var wg sync.WaitGroup
	for i := 0; i < 2; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for j := 0; j < 1000000; j++ {
				count++
			}
		}()
	}
	wg.Wait()
	fmt.Println(count)
}
EOF
go run main.go; go run main.go; go run main.go
go run -race main.go; echo "exit=$?"

最初の 3 回は 2000000 より小さい、毎回違う数字が出るはずだ（コア数や負荷によっては近い値になることもある）。-race 付きの実行では WARNING: DATA RACE と、main.go の count++ の行を指す 2 つのアクセス（Read と Write）が表示され、exit=66 で終わる。続けて count++ を mu.Lock() / mu.Unlock() で囲む（var mu sync.Mutex を足す）と、毎回 2000000 になり、-race も何も報告しなくなる。

🙅 よくある誤解
  • count++ は 1 行だから途中で割り込まれない — ソースの 1 行と CPU の不可分な 1 手順は別物で、count++ は読む・足す・書くに分かれる。不可分にしたいなら sync/atomic を明示的に使う。
  • 読むだけの goroutine はロックしなくてよい — 別の goroutine が書いている最中の読み取りもデータ競合である。書き手がいる限り、読み手も同じ Mutex を取るか atomic の Load を使う。
  • -race で何も出なければ競合はない — race detector は実行中に実際に起きた競合だけを報告する。通らなかった経路や、テストでは重ならなかったタイミングの競合は見逃す。
📖 用語ミニ辞典
データ競合（data race）
同じメモリ位置への書き込みが、別の読み書きと同期なしに並行して起きること
read-modify-write
値を読み、変更し、書き戻す一連の操作。途中に割り込まれると更新が消える
sync.Mutex
Lock〜Unlock の区間に同時に 1 つの goroutine しか入れない相互排他ロック
sync/atomic
単一の値への読み書き・加算を割り込み不能な 1 手順で行う Go のパッケージ
race detector
-race で有効になる、実行時に起きたデータ競合を検出・報告する Go のツール
