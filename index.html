z-index: 9999 にしたのに、なぜモーダルはヘッダーの下に潜るのか？

固定ヘッダーの z-index は 10、モーダルは 9999。数字の上では圧勝のはずなのに、開いたモーダルの上端がヘッダーの裏に隠れる。焦って 99999 に増やしても何も変わらない。z-index は「ページ全体で比べる 1 本の数直線」だと思っているなら、その前提がずれている。

🎯 3 行まとめ
  • z-index は「同じスタッキングコンテキストの中の兄弟同士」でしか比べられない。
  • position + 整数の z-index、transform、opacity < 1 などは要素を新しいスタッキングコンテキストにし、中身を 1 つの塊に閉じ込める。
  • 直すときは数字を上げず、祖先の塊を探して外す・isolation: isolate で意図的に作る・Portal や <dialog> で外へ出す。

描画の順番は「スタッキングコンテキスト」単位で決まる

ブラウザは要素を重ねて描くとき、どれを後から（手前に）塗るかを決める必要がある。この重なり順を決める単位がスタッキングコンテキストだ。スタッキングコンテキストとは「中身をまとめて重ね順を計算し、計算し終えたら外からは 1 枚の板として扱われる要素」のことである。ルート要素 <html> が最初の 1 つで、条件を満たす子孫がその中に入れ子の板を作っていく。

MDN はこれを「各スタッキングコンテキストは自己完結しており、中身を重ね終えた後は要素全体が親のスタッキングコンテキストの中で 1 つの単位として扱われる」と説明している。z-index の数字はこの「親の中での板の高さ」を指定するだけで、ページ全体の絶対的な高さではない。

z-index の初期値は auto で、これは「新しいスタッキングコンテキストを作らず、今いるコンテキストでの高さは 0」を意味する。一方、position: relative や absolute の要素に整数（0 も含む）を指定すると、その要素は高さを得ると同時に自分自身が新しいスタッキングコンテキストになる。高さを付けたつもりの操作が、子孫を閉じ込める壁も同時に作っている。

9999 が 10 に負ける仕組み

冒頭の状況を DOM に落とすとこうなる。ヘッダーは position: sticky; z-index: 10。モーダルは、ホバーで浮くカード（position: relative; z-index: 1）のコンポーネント内に置かれ、自身は position: fixed; z-index: 9999 を持つ。

ルート (html) のコンテキスト
├─ header      z-index: 10
└─ .card       z-index: 1  ◀ ここが板になる
   └─ .modal   z-index: 9999
               (.card の中だけで有効)

ルートで比べられるのは header と .card
  header(10) ＞ .card(1)
  ▼
.card の板ごと header の下に描かれる
  → 中の .modal も道連れ

ルートのコンテキストで比較されるのは直接の住人である header と .card だけだ。.modal の 9999 は .card の板の中で兄弟に勝つための値にすぎず、板の外へは持ち出せない。MDN の例でも、z-index: 6 の要素が z-index: 5 の要素の下に描かれる理由を「親の値が 4 なので、4-6 は 5-0 より小さい」と説明している。だから 99999 にしても順位は変わらない。

position: fixed にすれば画面基準で自由に浮けるように思える。しかし fixed は位置の基準を変えるだけで、どの板に属するかは DOM 上の祖先で決まる。さらに祖先に transform があると、fixed の位置基準そのものがその祖先に変わり、ビューポート全体を覆うことすらできなくなる。

🍱 たとえるなら

本の章・節番号だ。「第 1 章 第 9999 節」は節番号がどれだけ大きくても「第 10 章」より前に来る。比較はまず章番号で行われ、節番号は同じ章の中でしか意味を持たない。z-index も同じで、まず属する板（章）の高さで比べ、自分の数字（節）はその板の中の順位にしか効かない。

板を作るのは z-index だけではない

厄介なのは、スタッキングコンテキストが z-index と無関係なプロパティでも生まれることだ。MDN が挙げる条件のうち、実務で出会いやすいものを並べる。

/* どれも要素を新しいスタッキングコンテキストにする */
position: relative;  z-index: 1;  /* absolute も同様。auto 以外 */
position: fixed;                   /* z-index なしでも作る */
position: sticky;                  /* 同上 */
opacity: 0.99;                     /* 1 未満なら作る */
transform: translateY(-2px);       /* none 以外 */
filter: blur(4px);                 /* backdrop-filter も同様 */
will-change: transform;            /* 作る値を予告した時点で作る */
isolation: isolate;                /* 作るためだけのプロパティ */

ホバーで transform を付けるカード、フェードイン用に opacity をアニメーションさせるラッパー、性能対策で入れた will-change。どれも見た目の調整のつもりで書かれ、重なり順を変える意図はない。それでも付いた瞬間に子孫の z-index が外で効かなくなる。ちなみに z-index 無しの transform や opacity の板は、親の中では z-index: 0 相当の位置に描かれる（CSS 2 の描画順で z-index が 0 または auto の位置指定要素と同じ段）。

また、flex アイテムと grid アイテムは position 無しでも z-index が効き、整数を指定すれば板になる。逆に、普通のブロック要素（position: static）に z-index を書いても何も起きない。「書いたのに効かない」の多くはこれだ。

板は「消す」だけでなく「わざと作る」

原因の板が見つかったら、直し方は 3 つある。1 つ目は不要な板を外すことで、冒頭の例なら .card の z-index: 1 を消すか、ホバー効果を transform 以外で表現する。ただし板は他の理由で必要なことも多く、消せないこともある。

2 つ目は、モーダルを板の外へ出すことだ。React の createPortal は、コンポーネントの位置はそのままに DOM ノードだけを document.body などへ置く。公式ドキュメントも overflow: hidden などの容器の中から呼んでもページ全体の上に浮くモーダルの用途を挙げている。ネイティブの <dialog> を showModal() で開けば、要素はブラウザが管理するトップレイヤーに置かれる。トップレイヤーは文書内の他のすべての層の上に描かれる層で、祖先の板の影響を受けない。

3 つ目は、板を意図して作り、z-index の競争範囲を閉じ込めることだ。よくある罠に、装飾用の擬似要素に z-index: -1 を付けたら親の背景の裏へ消える、というものがある。CSS 2 の描画順では、負の z-index の子は「属するスタッキングコンテキストの背景」の直後に描かれる。親が板でなければ、その子はもっと外側の板の背景の直後まで沈み、親の背景がその上に塗られてしまう。

.button {
  position: relative;
  isolation: isolate; /* ここで板を作る */
}
.button::before {
  content: "";
  position: absolute;
  inset: 0;
  z-index: -1; /* .button の背景の上・文字の下に収まる */
}

isolation の初期値は auto で、isolate にすると「スタッキングコンテキストを必ず作る」以外の副作用が無い。z-index の値を付けたり transform を足したりする方法と違い、位置や見た目を一切変えずに板だけを作れるので、コンポーネントの外へ z-index が漏れ出すのを防ぐ目的で使える。

💼 実務でどう出会うか

典型はデザインシステムやライブラリの組み合わせだ。ヘッダーやサイドバーは position: sticky / fixed で必ず板になり、その中に置いたドロップダウンは、後ろにある本文側の板との勝負に親ごと巻き込まれる。ツールチップが overflow: hidden のテーブルの中で切れる問題と同じく、「その要素の数字」ではなく「どの板に属しているか」を見るのが調査の起点になる。DevTools の Elements パネルで問題の要素から祖先を 1 つずつ選び、Computed で z-index・transform・opacity・filter・will-change・position を確認していく。条件を満たす祖先が見つかるたびに「その板が親の中で誰と比べられているか」を確かめれば、負けている板に行き着く。チームでは z-index の値を「header: 100 / dropdown: 200 / modal: 300」のように変数で一元管理しても、板の入れ子を無視すれば同じ事故が起きる点に注意したい。

⌨️ 手を動かす（5 分）

z-index: 9999 のモーダルが z-index: 10 のヘッダーに負ける状況を再現し、親の 1 行を変えるだけで結果が反転することを確かめる。

mkdir -p /tmp/zidx && cat > /tmp/zidx/index.html <<'EOF'
<!doctype html>
<style>
  body { margin: 0; font: 16px sans-serif; }
  header { position: sticky; top: 0; z-index: 10;
           height: 80px; background: tomato; }
  .card  { position: relative; z-index: 1;
           margin: 20px; padding: 20px; background: #eee; }
  .modal { position: fixed; top: 40px; left: 40px;
           z-index: 9999; width: 240px; height: 120px;
           background: royalblue; color: #fff; }
</style>
<header>header z-index: 10</header>
<div class="card">card
  <div class="modal">modal z-index: 9999</div>
</div>
EOF
open /tmp/zidx/index.html

青いモーダルの上部が赤いヘッダーの下に隠れるはずだ。DevTools で .card の z-index: 1 のチェックを外すと、.card は板でなくなり、モーダルがルートで直接ヘッダーと比べられて手前に出る。続けて .card に opacity: 0.99 を足すと再びヘッダーの下に潜る。z-index を書いていないのに板ができ、親の中で 0 相当の段に描かれるためだ（transform でも板はできるが、fixed の位置基準が .card に変わってモーダルが下へずれるので、この実験では opacity が見やすい）。最後に .modal を <body> 直下へドラッグで移すと、どの設定でも手前に出る。

🙅 よくある誤解
  • z-index を十分大きくすれば必ず最前面に出る — 比べられるのは同じスタッキングコンテキストの兄弟だけで、祖先の板が負けていれば値をいくら上げても順位は変わらない。
  • z-index はどんな要素にも効く — 効くのは position が static 以外の要素と、flex / grid のアイテムである。普通のブロック要素に書いても無視される。
  • position: fixed にすれば親から独立する — fixed は位置の基準を変えるだけで、属する板は DOM 上の祖先で決まる。祖先に transform があれば位置の基準もその祖先になる。

スタッキングコンテキスト
中身の重なり順をまとめて計算し、外からは 1 つの単位として扱われる要素。ルート要素が最初の 1 つ。
z-index
属するスタッキングコンテキストの中での重なりの高さ。整数を指定した位置指定要素は自身も新しいコンテキストになる。
isolation: isolate
他の見た目を変えずに、スタッキングコンテキストを作ることだけを行う指定。
トップレイヤー

createPortal
React のコンポーネント位置を保ったまま、DOM ノードだけを別の場所（body 直下など）に描画する API。
