ターミナルでは 1 行ずつ出るのに、なぜパイプや docker logs に通すとログがまとめて遅れて届くのか？

手元で python worker.py を動かすと進捗が 1 行ずつ流れる。ところが同じスクリプトを | grep に通したり、コンテナに入れて docker logs -f で眺めたりすると、しばらく何も出ず、ある瞬間に数十行がどっと届く。コードは 1 文字も変えていないのに、出力先が変わっただけで挙動が変わるのはなぜだろうか。

🎯 3 行まとめ
  • print や printf はすぐ OS に書き込まず、プロセス内のバッファに溜めてからまとめて write する。
  • C の stdio や Python は「出力先が端末なら行単位、パイプやファイルならバッファが一杯になるまで」と、出力先を見て溜め方を切り替える。
  • リアルタイムに流したいログは PYTHONUNBUFFERED=1・$stdout.sync = true・grep --line-buffered などで明示的に溜めない設定にする。

print は「OS に書く」命令ではない

プログラムが画面やファイルに何かを出すとき、最終的には write というシステムコール（プロセスがカーネルに処理を頼む呼び出し）が実行される。システムコールはユーザー空間からカーネルへの切り替えを伴うため、1 文字ごとに呼ぶと出力量に比例してこの切り替えコストが積み上がる。

そこで C の標準入出力ライブラリ（stdio。printf や fputs を提供する層）や Python・Ruby の I/O 層は、プロセス内のメモリに出力バッファを持つ。print はこのバッファに文字列を追記するだけで戻り、ある条件を満たしたときにバッファの中身を 1 回の write でまとめて OS に渡す。この「OS に渡す」操作を flush と呼ぶ。

  あなたのプロセス
┌──────────────────────────┐
│ print("tick 0")          │
│ print("tick 1")          │
│      │                   │
│      ▼                   │
│ ┌──────────────────────┐ │
│ │出力バッファ(未送信)  │ │
│ └──────────────────────┘ │
└──────┬───────────────────┘
       │ flush の条件を満たした時だけ
       ▼ write(2) システムコール
┌──────────────────────────┐
│ カーネル                 │
│ 端末 / パイプ / ファイル │
└──────┬───────────────────┘
       ▼
  grep / docker logs / 画面

つまり「print を実行した時刻」と「受け手がその行を受け取る時刻」は一致しない。受け手から見えるのは、バッファが flush された瞬間だけである。

flush の条件は「出力先が端末かどうか」で変わる

Linux の setbuf(3) の man ページは、ストリームのバッファリングを 3 種類に分けている。書いた瞬間に出るアンバッファ、改行が出力されるまで溜める行バッファ、一定量をまとめてブロックとして書くブロックバッファ（フルバッファとも呼ぶ）だ。そして stdout が端末を指している場合は行バッファ、stderr は既定でアンバッファだと述べている。

ここで素朴に予想すると、「stdout は行バッファなのだから、パイプに流しても改行ごとに出るはずだ」と思える。しかし実際は違う。行バッファになるのは出力先が端末のときに限られ、パイプやファイルにつながっているとブロックバッファに切り替わる。プログラムは起動時に「自分の stdout は端末か」を調べ（isatty という関数で判定できる）、その結果で溜め方を決めている。

Python の公式ドキュメントも同じ方針を明記している。対話的（端末）なら stdout は行バッファ、そうでなければ通常のテキストファイルと同じブロックバッファになる。stderr はどちらの場合も行バッファで、非対話時の stderr が行バッファになったのは Python 3.9 からだ。冒頭の現象は、端末からパイプに出力先が変わったことで、Python が改行ごとの flush をやめただけなのである。

この切り替えには理由がある。人が端末を見ているなら 1 行ごとに表示されないと困るが、ファイルやパイプの先にいるのは多くの場合プログラムで、表示の即時性よりも write の回数を減らすスループットの方が効く。出力先によって「誰が読んでいるか」を推測し、既定値を変えているわけだ。

🍱 たとえるなら

社内便の担当者だ。目の前で受け取りを待っている人（端末）がいれば、書類が 1 枚できるたびに手渡す。宛先が別フロアの郵便受け（パイプ・ファイル）だと、往復の手間を省くために箱が一杯になるまで溜めてから運ぶ。書類を書く速さは同じでも、受け取る側が書類を目にするタイミングは「運ぶ規則」で決まる。担当者が途中で倒れれば（プロセスの強制終了）、箱の中の書類は届かない。

docker logs も「パイプの先」である

コンテナで同じ現象が起きるのは、docker run を -t なしで起動すると、コンテナの stdout が端末ではなくログを収集する側につながるからだ。プロセスから見れば出力先は端末ではないので、Python はブロックバッファを選ぶ。Kubernetes の kubectl logs でも、コンテナの stdout が端末でない点は同じなので、同様の遅延が起きうる。

Docker のリファレンスによれば、-t（--tty）はコンテナに疑似端末（pseudo-TTY。プログラムからは本物の端末に見える仮想デバイス）を割り当てる。-t を付けると出力が即座に見えるようになることがあるのはこのためだが、ログの即時性のためだけに疑似端末を付けるのは筋が良くない。アプリ側で「溜めない」と宣言する方が、どの実行環境でも同じ挙動になる。

遅延よりも深刻なのが、ログの消失だ。バッファは通常、プロセスが正常に終了する際に flush される。しかし SIGKILL で強制終了された場合や、Python の os._exit() のように後始末を飛ばして終了した場合は、バッファに残った行は write されないまま消える。OOM killer に殺されたコンテナの最後のログが欠けているとき、その直前の数行はまさにバッファの中にあった可能性がある。

言語・ツールごとの「溜めない」設定

最初に触るべきは Python の設定だ。python -u か環境変数 PYTHONUNBUFFERED を設定すると、stdout と stderr の両方がアンバッファになる。Dockerfile に書いておけば、コードを変えずにコンテナ内のすべての Python プロセスに効く。個別の行だけ即座に出したいなら print(..., flush=True) を使う。

# Dockerfile
ENV PYTHONUNBUFFERED=1

# 個別に flush する場合
print("job started", flush=True)

Ruby では $stdout.sync = true を設定すると、出力が内部でバッファされずにすぐ OS に渡されるモードになる。設定しないと sync は false で、出力は内部でバッファされうる。Rails ならログを stdout に出す構成で、起動処理の早い段階に 1 行置けばよい。

# config/boot.rb などの起動時
$stdout.sync = true

Go は事情が異なる。os.Stdout は *os.File で、fmt.Println は呼ぶたびにそのまま write する。Go で溜めたいときは自分で bufio.Writer を挟むので、逆に「Flush を呼び忘れて最後の出力が消える」形でこの問題に出会う。

パイプの途中にいるコマンドも見落としやすい。tail -f app.log | grep ERROR | sed ... のように繋ぐと、grep 自身の出力先がパイプなので grep がブロックバッファで溜める。GNU grep の --line-buffered を付けると行ごとに flush する。オプションを持たない C プログラムには GNU coreutils の stdbuf -oL が使えるが、マニュアルにある通り stdio の FILE ストリームを使い、自前でバッファ設定を変えないプログラムにしか効かない。

tail -f app.log | grep --line-buffered ERROR | sed 's/^/[!] /'
stdbuf -oL ./legacy-tool | grep WARN
💼 実務でどう出会うか

典型は「ローカルでは進捗が見えるのに、ECS や Kubernetes にデプロイしたバッチのログが終わるまで出てこない」という相談だ。まず Dockerfile に PYTHONUNBUFFERED=1 があるか、Ruby なら $stdout.sync を設定しているかを確認する。もう一つは、> out.log 2>&1 でまとめたログで stdout と stderr の順番が前後して見える現象だ。stderr は行単位以下で即座に書かれ、stdout はブロック単位で後から書かれるため、ファイル上ではエラーメッセージが、それより前に print した行より先に並ぶ。ログの順序を手がかりに原因を追うときは、この並び替えを疑う。

⌨️ 手を動かす（5 分）

1 秒ごとに 1 行出す Python を、パイプ越しに受け取って「受信時刻」を付ける。-u の有無で受信時刻がどう変わるかを比べる。

python3 -c 'import time
for i in range(3):
    print("tick", i); time.sleep(1)' \
  | while read l; do echo "$(date +%T) $l"; done

python3 -u -c 'import time
for i in range(3):
    print("tick", i); time.sleep(1)' \
  | while read l; do echo "$(date +%T) $l"; done

python3 -c 'import os; print("lost?"); os._exit(0)' | cat

1 つ目は 3 秒待ったあと 3 行が同じ時刻で届き、2 つ目は 1 秒ずつ時刻がずれて届くはずだ。3 つ目は何も表示されない。os._exit() が flush を飛ばして終了し、バッファ内の行が捨てられたからだ。| cat を外して端末に直接出すと、行バッファなので lost? が表示されることも確かめてみるとよい。

🙅 よくある誤解
  • stdout は行バッファだから、改行さえ出せばすぐ届く — 行バッファになるのは出力先が端末のときだけ。パイプやファイル、コンテナのログ収集先ではブロックバッファになり、改行では flush されない。
  • ログが遅れて出るのは docker や kubectl logs の収集が遅いからだ — 多くの場合、遅れているのはアプリのプロセス内バッファで、収集側にはまだ何も write されていない。PYTHONUNBUFFERED=1 で直るなら原因はアプリ側だ。
  • print したのだから、プロセスが落ちてもその行はどこかに残っている — flush 前に SIGKILL などで終了すると、バッファの中身は OS に渡らずに消える。最後のログが欠けていても、そこまでコードが実行されなかったとは限らない。
📖 用語ミニ辞典
出力バッファ
OS に書き込む前の出力を一時的に溜めておく、プロセス内のメモリ領域。
flush
バッファに溜まった内容を write システムコールで OS に渡し、バッファを空にすること。
行バッファ
改行が出力されるまで溜め、改行のたびに flush するモード。端末向け stdout の既定。
ブロックバッファ
バッファが一杯になるか明示的に flush されるまで溜めるモード。パイプ・ファイル向けの既定。
isatty
ファイルディスクリプタが端末を指しているかを判定する関数。バッファリング方式の切り替えに使われる。
疑似端末（pseudo-TTY）
プログラムからは本物の端末に見える仮想デバイス。docker run -t で割り当てられる。
