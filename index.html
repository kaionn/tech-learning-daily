件数を 1 つ返すだけなのに、なぜ Postgres の COUNT(*) はテーブルが育つほど遅くなるのか？

管理画面の一覧に「全 1,234,567 件」と出すために、SELECT count(*) FROM orders を足した。リリース当初は一瞬だったのに、データが育つにつれてこのクエリだけがスロークエリログの常連になった。返す値はたった 1 つの整数なのに、DB はなぜそれをすぐに答えられないのだろうか。

🎯 3 行まとめ
  • Postgres はテーブルの正確な行数をどこにも保存していない。MVCC では同じ瞬間でもトランザクションごとに「見える行」が違うので、保存すべき 1 つの正解が存在しないからである。
  • そのため COUNT(*) は行を 1 つずつ読み、自分から見える行かを確かめて数える。所要時間は行数に比例し、索引だけで数える Index Only Scan も「読むページが減る」だけで、全件をなめる点は変わらない。
  • 正確な件数が要らない画面では、pg_class.reltuples の推定値、EXPLAIN の見積もり、「次のページがあるか」だけを調べる方式に切り替える。

「件数くらいどこかに持っているはず」という予想

テーブルに行を足すたびにカウンタを 1 増やしておけば、COUNT(*) はその値を返すだけで済むように思える。実際、MySQL の古いストレージエンジンである MyISAM は正確な行数を保存しており、WHERE の無い単一テーブルの COUNT(*) はすぐに返る。

しかし Postgres も、MySQL の標準エンジンである InnoDB も、行数を保存していない。MySQL の公式マニュアルは理由を「並行するトランザクションが同じ瞬間に異なる行数を『見る』可能性があるため」と説明している。この「見る」という言葉の意味は、MVCC という仕組みから来ている。

MVCC（Multi-Version Concurrency Control）とは、行を書き換えるときに古い版を残したまま新しい版を追加し、各トランザクションには「自分が開始した時点で確定していた版」だけを見せる仕組みである。読み手と書き手がお互いを待たずに済むのが利点で、代わりに「テーブルの今の行数」が見る人によって変わる。

時刻 ──────────────────────────▶

Tx A: BEGIN ─── count(*) → 100
        │
Tx B:   │ BEGIN ─ INSERT 1件 ─ COMMIT
        │                        │
Tx A:   └──────── count(*) → 100 │
                                 ▼
Tx C:                 BEGIN ─ count(*) → 101

同じ瞬間でも A には 100 件、C には 101 件
→「テーブルの行数」は 1 つに決まらない

図の A は REPEATABLE READ のように開始時点のスナップショットを見続けるトランザクションである。B のコミット後も A にとって正しい答えは 100、C にとっては 101 だ。カウンタを 1 つだけ持っても両方には答えられないし、トランザクションごとにカウンタを持つのは行を数えるのと変わらない。

Postgres は 1 行ずつ「見えるか」を確かめて数える

正解がトランザクションごとに違う以上、Postgres は問い合わせのたびに数えるしかない。どの走査方法を使うかは、実行計画を組み立てるプランナーが統計をもとに選ぶ。Postgres の行データを格納する本体のファイルを heap と呼び、heap の中の行の 1 版を tuple と呼ぶ。各 tuple には「どのトランザクションが作ったか」「どのトランザクションが消したか」の情報が付いていて、COUNT(*) はこれを自分のスナップショットと照らし合わせて、見える tuple だけを数える。

手元の Docker で 100 万行のテーブルを作り EXPLAIN (ANALYZE, BUFFERS) を取ると、計画は次の形になった。Seq Scan は heap の全ページを先頭から順に読む走査で、Buffers は読んだ 8KB ページの数である。

Aggregate
  ->  Seq Scan on items
        (actual rows=1000000)
        Buffers: shared hit=9346

件数を返すために、100 万行が入った 9,346 ページをすべて読んでいる。行が 10 倍になれば読むページもほぼ 10 倍になるので、テーブルが育つほど遅くなるのはこの設計の素直な帰結である。さらに、UPDATE や DELETE で生まれた古い版（dead tuple）も VACUUM で回収されるまでは heap に残るため、更新の多いテーブルでは「見えない行」を読み飛ばす分まで時間がかかる。

索引だけで数える Index Only Scan と visibility map

「主キーの索引は heap よりずっと小さいのだから、索引の項目を数えればよい」と考えるのは自然だ。ところが Postgres の索引には可視性の情報が入っていない。索引の項目を見つけても、その行が自分から見えるかは heap の tuple を見ないと分からないのである。

この往復を省くのが visibility map である。visibility map は heap の 1 ページにつき 2 ビットを持つ小さな地図で、そのうち all-visible ビットは「このページの行はすべて、今後のどのトランザクションからも見える」ことを表す。ビットが立っているページの行なら、Index Only Scan（索引だけを読んで答える走査）は heap を見ずに数えられる。立っていなければ heap を見に行く。この heap 参照が EXPLAIN の Heap Fetches に表れる。

ビットの扱いは非対称だ。公式ドキュメントによれば、ビットを立てるのは VACUUM だけで、ページ上の行を変更する操作はどれもビットを下ろす。同じ 100 万行のテーブルで試すと、VACUUM 直後の Index Only Scan は Heap Fetches: 0・読んだページ 2,736 だった。そこで 10 件に 1 件を UPDATE すると、更新行が全ページに散らばっていたためほぼ全ページのビットが下り、Heap Fetches は 110 万回、読んだページは延べ約 21 万になった。

そして VACUUM 直後の理想的な状態でも、Index Only Scan は索引の 100 万項目を 1 つずつ数えている。読むページが減って I/O が軽くなるだけで、行数に比例する仕事であることは変わらない。実際この実験ではデータがすべてメモリに載っていたため、所要時間は Seq Scan とほぼ同じで、プランナーは何も指定しなければ Seq Scan を選んだ。Index Only Scan は「速くなる場合がある」最適化であり、件数取得を一瞬にする仕組みではない。

🍱 たとえるなら

貸し出しの多い図書館で「いま棚にある本は何冊か」を数えるようなものだ。蔵書目録（索引）を見れば登録冊数はすぐ分かるが、貸出中や廃棄予定の本が混ざっているので、本当の冊数は棚（heap）を見ないと分からない。visibility map は棚ごとに貼る「点検済み、全冊在架」の札にあたる。札は点検係（VACUUM）しか貼れず、誰かが 1 冊借りた瞬間に剥がれる。札のある棚は目録だけで数えてよいが、それでも 1 冊ずつ数える手間は残る。

正確さを手放すという設計判断

速くする方法の多くは、正確さか即時性のどちらかを手放すことになる。最初に検討すべきは「その画面に正確な件数が本当に要るか」である。「約 120 万件」で十分なら、プランナー用の統計である pg_class.reltuples を読むのが最も軽い。値は VACUUM、ANALYZE、CREATE INDEX などで更新され、autovacuum が動いていれば大きくはずれにくい。ただし統計の更新後に大量の行が増減すると、次の更新までずれたままになる。

SELECT reltuples::bigint AS estimate
FROM pg_class
WHERE oid = 'public.orders'::regclass;

WHERE 付きの件数を見積もりたいときは、EXPLAIN の出力にある見積もり行数（rows=）を使う方法が Postgres の公式 Wiki で紹介されている。こちらも統計からの推定なので、条件が複雑になるほど誤差は大きくなりうる。

ページングのためだけに件数を取っているなら、件数そのものをやめる手もある。「次のページがあるか」は 1 ページ分より 1 件多く取得すれば分かり、取得件数は表示件数 + 1 で止まる。正確な件数がどうしても必要なら、挿入・削除のたびに更新する集計テーブルを持つ方法がある。ただし MySQL のマニュアルも注意するとおり、全トランザクションが同じカウンタ行を更新するため、書き込みが多いとその行のロック待ちが新たなボトルネックになる。

💼 実務でどう出会うか

最も多いのは、ページネーション用 gem やライブラリが一覧表示のたびに裏で COUNT(*) を発行しているケースである。一覧本体のクエリは LIMIT 20 で速いのに、総件数のクエリだけが遅く、ページ全体の応答時間を支配する。スロークエリログで SELECT COUNT(*) FROM ... が上位に来たら、まず「その件数は画面で正確に要るか」を企画側と確認し、不要なら推定値表示か「次へ」だけのページングに切り替える。必要な場合でも、EXPLAIN (ANALYZE, BUFFERS) で Heap Fetches が大きければ、そのテーブルは VACUUM が追いついていない兆候として autovacuum の状況を確認する。

⌨️ 手を動かす（5 分）

100 万行のテーブルで、VACUUM 直後と UPDATE 直後の Index Only Scan を比べ、visibility map のビットが下りると Heap Fetches が跳ね上がることを確かめる。比較のため Seq Scan と Bitmap Scan を禁止し、並列実行も切っている。

docker run -d --name pgcount -e POSTGRES_PASSWORD=pass postgres:17
sleep 8
docker exec -i pgcount psql -U postgres <<'SQL'
CREATE TABLE items (id bigserial PRIMARY KEY, body text);
INSERT INTO items (body)
  SELECT md5(i::text) FROM generate_series(1, 1000000) AS i;
SET max_parallel_workers_per_gather = 0;
SET enable_seqscan = off;
SET enable_bitmapscan = off;
VACUUM items;
EXPLAIN (ANALYZE, BUFFERS) SELECT count(*) FROM items;
UPDATE items SET body = 'x' WHERE id % 10 = 0;
EXPLAIN (ANALYZE, BUFFERS) SELECT count(*) FROM items;
VACUUM items;
EXPLAIN (ANALYZE, BUFFERS) SELECT count(*) FROM items;
SQL
docker rm -f pgcount

1 回目は Heap Fetches: 0 で、読んだページ（Buffers: shared hit）は索引の約 2,700 だけになるはずだ。UPDATE 直後の 2 回目は Heap Fetches が 100 万を超え、読んだページも桁違いに増える。更新したのは 1 割の行でも、それが全ページに散らばっているので、全ページの all-visible ビットが下りたからである。それでも 2 回目の件数は 100 万のまま変わらない。VACUUM をかけた 3 回目は Heap Fetches: 0 に戻る。3 回とも rows=1000000 を 1 件ずつ数えていることも実行計画から読み取れる。

🙅 よくある誤解
  • COUNT(1) や COUNT(id) にすれば速くなる — 遅さの原因は行を 1 つずつ見て可視性を確かめることにあり、引数の書き方を変えてもこの仕事は無くならない。MySQL のマニュアルも InnoDB では COUNT(*) と COUNT(1) を同じに扱うと明記している。なお COUNT(列) は NULL を数えないため、結果の意味が変わる場合がある。
  • 索引を貼れば COUNT(*) は一瞬になる — 索引は読むページ数を減らすだけで、件数に比例する仕事は残る。visibility map のビットが下りていれば heap も見に行くので、更新の多いテーブルでは索引の効果がほとんど出ない。
  • reltuples は「少し古い正確な件数」である — reltuples はプランナー用の推定値である。統計を更新した直後でも、実際の件数と一致する保証はない。
📖 用語ミニ辞典
MVCC
行の古い版を残したまま新しい版を足し、各トランザクションに自分のスナップショット時点の版だけを見せる同時実行制御。
heap / tuple
heap は Postgres の行データ本体を収めたファイル、tuple はその中の行の 1 版。
visibility map
heap の 1 ページごとに「全行が誰からでも見える（all-visible）」「全行が凍結済み」を記録する小さな地図。ビットを立てるのは VACUUM だけ。
Index Only Scan
索引だけを読んで結果を返す走査。visibility map のビットが立っていないページの行は heap も参照する。
Heap Fetches
Index Only Scan が可視性確認のために heap を参照した回数。EXPLAIN ANALYZE に表示される。
reltuples
pg_class にあるテーブルの推定行数。VACUUM・ANALYZE・一部の DDL で更新されるプランナー用の統計。
