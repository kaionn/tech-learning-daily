useEffect に書いた API 呼び出しが、なぜ開発中だけ 2 回飛ぶのか？

画面を開いたときにデータを取ってくる useEffect を書いた。ブラウザの Network タブを見ると、同じリクエストが 2 本並んでいる。console.log も 2 回出る。ところが本番ビルドで試すと 1 回しか呼ばれない。React はなぜ、開発中だけわざわざ処理を二重に走らせるのだろうか。

🎯 3 行まとめ
  • 2 回目の呼び出しは、<StrictMode> が開発中だけ行う「マウント直後にいったんアンマウントして、もう一度マウントする」検査の結果である
  • 目的は、cleanup 関数の書き忘れを本番より先に表に出すこと。Effect は setup → cleanup → setup と実行されても、1 回だけの場合と見分けがつかないように書くのが正解である
  • useRef のフラグで 2 回目を握りつぶすのは誤った対処で、cleanup で接続を閉じる・fetch の結果を無視する・AbortController で中止する、が正しい直し方である

2 回目を起こしているのは StrictMode である

犯人はコードのバグではなく、アプリの入り口にある <StrictMode> である。StrictMode は、囲んだコンポーネントに対して開発時だけ追加の検査を行う React の組み込みコンポーネントだ。Vite の React テンプレートで作ったプロジェクトなら、src/main.jsx に最初から書かれている。

createRoot(document.getElementById('root')).render(
  <StrictMode>
    <App />
  </StrictMode>,
)

React の公式リファレンスによれば、StrictMode の内側では「すべての Effect について、開発時に setup と cleanup をもう 1 周余分に実行する」。ここで Effect とは useEffect に渡した関数のことで、setup はその本体、cleanup は本体が return した後片付け用の関数を指す。この検査は React 18 で追加されたもので、公式ドキュメントは開発時専用であり本番ビルドには影響しないと明記している。本番で 1 回しか呼ばれないのはこのためだ。

React は何を確かめているのか

2 回実行と聞くと、単に関数を 2 度呼んでいるように思える。しかし実際は「マウント → アンマウント → 再マウント」という画面の出入りを再現している。マウントはコンポーネントが画面に現れること、アンマウントは画面から消えることだ。React 18 のリリースノートは、この流れを次の順序として示している。

開発 + StrictMode       本番
──────────────────    ──────────────
① マウント            ① マウント
   Effect setup          Effect setup
      │
      ▼
② 擬似アンマウント
   Effect cleanup
      │
      ▼
③ 再マウント
   (state は保持)
   Effect setup

正しい cleanup があれば
①〜③ の最終状態 ＝ 本番の ① の状態

2 回目のマウントでは state が前回の値のまま復元される。つまり React が試しているのは「ユーザーが別の画面へ移って戻ってきたとき、このコンポーネントは壊れないか」という状況である。cleanup を書き忘れたチャット接続のような Effect は、出入りのたびに接続が増え続ける。本番では画面遷移を何度も繰り返して初めて表面化するこの種のバグを、開発中の初回表示だけで見えるようにするのがこの検査の狙いだ。

React がここまで「出入り」にこだわるのは、state を保ったまま UI を隠したり戻したりする機能を見据えていたからである。React 18 のリリースノートは将来機能としてこれを予告しており、現在の React には <Activity> として入っている。<Activity mode="hidden"> の中のコンポーネントは state を残したまま Effect だけが cleanup され、表示に戻ると Effect が作り直される。StrictMode の二重実行は、この動き方に耐えられるかを前もって試す検査でもある。

🍱 たとえるなら

ホテルの新人研修で、チェックインの直後に一度チェックアウトさせ、すぐにもう一度チェックインさせる抜き打ち検査である。チェックアウト時にエアコンを切り、鍵を返す手順（cleanup）が抜けている新人の部屋では、2 回目のチェックインの時点でエアコンが 2 台分動き、鍵も 2 本出回っている。本物の客（本番）はこの往復をしないが、長期滞在の客が何度も出入りすれば同じことが起きる。

正しい直し方は「2 回目を止める」ではなく「cleanup を書く」

公式ドキュメントの言葉では、問うべきは「Effect を 1 回だけ実行するにはどうするか」ではなく「再マウント後も正しく動くように Effect をどう直すか」である。判定基準は、setup → cleanup → setup の結果を、ユーザーが 1 回だけの実行と区別できないことだ。購読や接続なら、cleanup で解除・切断する。

useEffect(() => {
  const conn = createConnection(roomId);
  conn.connect();
  return () => conn.disconnect(); // cleanup
}, [roomId]);

データ取得では、送ってしまったリクエストは取り消せない。そこで cleanup では「もう関係ない結果を state に反映しない」ようにする。公式の例は ignore フラグを使う。

useEffect(() => {
  let ignore = false;
  fetch(`/api/todos?user=${userId}`)
    .then(r => r.json())
    .then(json => { if (!ignore) setTodos(json); });
  return () => { ignore = true; };
}, [userId]);

開発中は Network タブにリクエストが 2 本出るが、1 本目の結果は ignore により捨てられるので画面には影響しない。この書き方は、userId が素早く切り替わったときに古いレスポンスが後から届いて新しい表示を上書きする、本番でも起きる競合も同時に防ぐ。通信自体を打ち切りたいなら AbortController を併用できるが、公式ドキュメントは中止だけでは競合対策として足りず、明示的なフラグが最も確実だと述べている。

やってはいけない対処と、二重に困る処理の扱い

よく見かけるのは、useRef で「実行済み」フラグを持って 2 回目を飛ばす書き方である。公式ドキュメントはこれを誤りとしている。ログは 1 回になるが、cleanup が無いという本当の問題は残り、画面を出入りすれば接続は増え続けるからだ。同様に、<StrictMode> を外せば 2 回目は消えるが、検査をやめただけでバグは残る。

決済の POST のように、2 回送ること自体が問題になる処理もある。こうした処理はそもそも Effect に置かない。「画面が表示されたから」ではなく「ユーザーがボタンを押したから」起きる処理なので、イベントハンドラに書くのが筋である。Effect に置くのは、画面が表示されている間ずっと同期させておきたいもの（接続・購読・表示中のデータ）に限る、と考えると判断しやすい。

💼 実務でどう出会うか

典型は「開発環境だとアクセスログやアナリティクスのイベントが 2 件ずつ入る」「WebSocket の接続数がサーバー側で 2 倍に見える」という問い合わせである。まず本番ビルドで再現するかを確かめ、再現しなければ StrictMode の検査であると判断できる。コードレビューでは、useEffect の中で接続・購読・setInterval・イベントリスナー登録をしているのに return が無い箇所を探す。これらは本番でも画面遷移のたびにリークする候補である。StrictMode はサブツリーだけを囲むこともできるので、既存アプリに後から入れる場合は一部の画面から始めてもよい。

⌨️ 手を動かす（5 分）

Vite の React テンプレートで Effect のログ順を確かめ、本番ビルドと比べる。Node.js が入っていれば Mac でそのまま動く（作成時に対話的な質問が出たら、既定値のままで進めてよい。自動で dev サーバーを起動するか聞かれたら No を選ぶ）。

npm create vite@latest strict-demo -- --template react
cd strict-demo && npm install
cat > src/App.jsx <<'EOF'
import { useEffect } from 'react'
export default function App() {
  useEffect(() => {
    console.log('setup')
    return () => console.log('cleanup')
  }, [])
  return <h1>Open DevTools console</h1>
}
EOF
npm run dev
# 確認後 Ctrl+C で止めて、本番ビルドを試す
npm run build && npm run preview

npm run dev で表示された URL を開き、DevTools の Console を見ると setup → cleanup → setup の 3 行が出る。npm run preview の URL では setup が 1 行だけになる。src/main.jsx から <StrictMode> を外して dev を再実行しても 1 行になり、2 回目の出どころが StrictMode であることを確かめられる。

🙅 よくある誤解
  • Effect が 2 回走るのは依存配列の書き方が悪いからだ — 依存配列が [] でも開発中は 2 回走る。これは StrictMode が意図して行う再マウント検査で、本番では起きない。
  • useRef で実行済みフラグを立てれば直る — ログが 1 回になるだけで、cleanup が無い問題は残る。画面の出入りや <Activity> での非表示・再表示で同じリークが起きる。
  • 開発時専用の挙動なのだから無視してよい — 2 回目で壊れるコードは、本番で画面を出入りしたときにも壊れる。検査が見せているのは本番に潜んでいる不具合である。
📖 用語ミニ辞典
StrictMode
囲んだコンポーネントに、開発時だけ二重レンダーや Effect の再実行などの検査を行う React の組み込みコンポーネント。
Effect
useEffect に渡す関数。描画後に外部システム（通信・購読・タイマーなど）と同期するために使う。
cleanup 関数
Effect が返す後片付け用の関数。次回の Effect 実行前とアンマウント時に呼ばれる。

AbortController
実行中の fetch などに中止を伝えるためのブラウザ標準 API。
