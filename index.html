CPU は半分も使っていないのに、なぜ load average は 20 もあるのか？

「サーバーが重い」と言われて top を開く。4 コアのマシンで CPU 使用率は 50% 程度なのに、右上の load average は 20 を超えている。「4 コアなら 4 が上限では？」と首をかしげたことはないだろうか。この数字は CPU の忙しさではなく、「何かを待っているタスクの数」を数えている。そして Linux は、その「待っている」の範囲が他の OS より広い。

🎯 3 行まとめ
  • load average は CPU 使用率ではなく、「CPU で動いている、または動く順番を待っている」タスクの数を時間でならした値だ。
  • Linux はこれに加えて、ディスク I/O などで割り込み不可の待ちに入っている D 状態のタスクも数える。だから CPU が空いていても load は跳ね上がる。
  • 1・5・15 分の値は単純平均ではなく、5 秒ごとのサンプルを指数的に減衰させた値で、増減の傾向を見るのに向いている。原因の切り分けには vmstat の r 列や PSI を使う。

load average は「列に並んでいる人数」である

CPU 使用率は「CPU が仕事をしていた時間の割合」なので、100% より上にはならない。一方 load average が数えるのは時間ではなく、タスクの数だ。ここでのタスクはプロセスまたはスレッドのことで、カーネルのスケジューラが CPU を割り当てる単位である。

Linux のスケジューラは、CPU で実行中のタスクと、CPU が空くのを待っているタスクを R（runnable）状態として扱う。CPU 待ちのタスクが並ぶ列をランキューと呼ぶ。4 コアのマシンで R 状態のタスクが 4 個なら全コアがちょうど埋まっている。10 個なら 6 個は列で待っている。つまり load は CPU 数を超えられ、超えた分は「待たされている仕事」を表す。

生の値は /proc/loadavg で読める。uptime や top もこのファイルを表示している。

$ cat /proc/loadavg
20.31 18.02 9.47 3/812 48211

先頭 3 つが 1・5・15 分の load average だ。4 つ目の 3/812 は「今この瞬間に実行可能なタスク数 / 存在するタスクの総数」、5 つ目は直近に作られたプロセスの PID である。ここで違和感が出る。4 つ目を見ると実行可能なタスクはたった 3 個なのに、load は 20 もある。残りの 17 はどこから来たのか。

Linux だけが「D 状態」も数える

答えは、Linux が R 状態に加えて D 状態のタスクも load に足していることにある。D 状態（uninterruptible sleep、割り込み不可の待ち）とは、ディスク I/O の完了などを待っている間、シグナルを受けても起きないタスクの状態だ。ps や top の状態列に D と表示される。sleep やソケットの受信待ちのような通常の待ちは S（割り込み可能な待ち）で、こちらは数えない。

 4 コアのマシン、ある瞬間の様子
 CPU  ┌────┬────┬────┬────┐
      │ A  │ B  │idle│idle│  R 実行中   2
      └────┴────┴────┴────┘
 ランキュー（空）            R 実行待ち 0
 ディスク待ち ▶ C D E … T    D 待ち    18
 ──────────────────────────────────────
 この瞬間の数 = 2 + 0 + 18 = 20
 CPU 使用率は 50% なのに load は 20

load average は 1973 年の RFC 546 の頃から CPU の需要を測る指標だった。Linux が D 状態を加えたのは 1993 年の Linux 0.99 patchlevel 14 で、パッチ作者の Matthias Urlichs は「スワップや割り込み不可の I/O を待っているプロセスも資源を消費している」と理由を書いている。きっかけは、速いスワップディスクを遅いものに替えたらシステムは重くなったのに load が下がった、という逆転現象だった。CPU 待ちだけを数えると、I/O が詰まってタスクが CPU を使えなくなるほど数字が下がってしまう。

その結果、Linux の load は「CPU・ディスク・一部のロックに対する需要の合計」になった。Brendan Gregg の調査によれば、D 状態に入るカーネル内のコードパスは 0.99.14 では 13 箇所だったが、Linux 4.12 では 400 箇所近くに増え、一部のロック待ちも含まれる。NFS サーバーが応答しなくなったり、ディスクが遅くなったりすると、CPU は暇なのに load だけが積み上がる。冒頭の「CPU 50% で load 20」はこの状態だ。

🍱 たとえるなら

銀行の「店内の待ち人数」表示に近い。窓口で手続き中の人と、番号札を持って順番を待つ人に加え、Linux 版は「奥で書類の取り寄せを待っている人」まで数える。窓口（CPU）が半分空いていても、書類待ちの人が 18 人いれば表示は 20 になる。ここで窓口を増やしても書類は早く届かない。

1・5・15 分は「平均」ではない

3 つの数字は、名前から「直近 1 分間の平均」のように思える。しかし実際は、カーネルが 5 秒ごとにタスク数をサンプルし、古い値ほど重みを指数的に小さくして足し込んだ値（指数減衰移動平均）だ。1・5・15 分は「どれくらいの速さで過去を忘れるか」を決める定数にすぎない。

この計算のため、値は負荷の変化に遅れて追いつく。Gregg の実験では、アイドル状態のマシンで CPU を使い切るスレッドを 1 本だけ起動すると、1 分後の 1 分値は 1.0 ではなく約 0.62 だった。負荷が 1 分続いても、1 分値はまだ 1 に届かない。

実務での読み方は、3 つの値の大小関係だ。1 分値が 15 分値より大きければ負荷は増えている途中、小さければ収まりつつある。冒頭の 20.31 18.02 9.47 なら、15 分ほど前から負荷が積み上がり、今も高止まりしていると読める。

CPU 数で割る目安と、その先の切り分け

よく言われる「load が CPU 数を超えたら危険」は目安にとどまる。CPU 待ちだけを数える OS なら load ÷ CPU 数は CPU の飽和度に近いが、Linux の値には D 状態が混ざるので、割っても CPU が足りないのかディスクが遅いのかは区別できない。Gregg も、Linux の load は同じマシンの過去の値と比べる相対的な使い方を勧めている。

load が高いと分かったら、次は内訳を見る。vmstat 1 の r 列は R 状態のタスク数、b 列は D 状態のタスク数を 1 秒ごとに表示する。r が CPU 数を大きく超えていれば CPU 不足、b が大きく wa（I/O 待ちの CPU 時間）も高ければディスクやネットワークストレージを疑う。D 状態のタスク名は ps -eo state,pid,comm | awk '$1=="D"' で列挙できる。

より直接的な指標が、Linux 4.20 で入った PSI（Pressure Stall Information）だ。タスクの数ではなく「資源待ちで止まっていた時間の割合」を CPU・メモリ・I/O 別に出す。

$ cat /proc/pressure/io
some avg10=42.10 avg60=38.55 avg300=20.07 total=912873412
full avg10=31.80 avg60=29.40 avg300=14.62 total=701223877

some は「少なくとも 1 つのタスクが I/O 待ちで止まっていた時間の割合」、full は「動けるはずの全タスクが同時に止まっていた時間の割合」で、avg10/avg60/avg300 は 10・60・300 秒の平均（%）である。上の例なら直近 10 秒の約 3 割、全タスクが I/O で止まっていた。PSI は CONFIG_PSI を有効にしたカーネルでのみ使え、ディストリビューションによっては組み込まれていても既定で無効のため、ブートパラメータ psi=1 で有効化する必要がある。

コンテナで見るときは注意がいる。/proc/loadavg はコンテナごとに分かれておらず、LXCFS のような仕組みで仮想化しない限り、コンテナ内の uptime はホスト全体の値を返す。一方 PSI は cgroup v2 ごとに cpu.pressure・memory.pressure・io.pressure を持つので、コンテナ単位の詰まりを見るならこちらを使う。

💼 実務でどう出会うか

監視ダッシュボードで「load average > CPU 数」のアラートが鳴ったのに CPU 使用率は低い、という場面が典型だ。このときスケールアウトして CPU を足しても、原因が EBS のスループット上限や NFS の遅延なら D 状態のタスクは減らず、load も下がらない。まず vmstat 1 の r と b を見て CPU 起因か I/O 起因かを分け、I/O ならストレージ側のメトリクスへ進む。Kubernetes のノードで load が高い場合、その数字はノード上の全 Pod の合算なので、どの Pod が詰まっているかは各 cgroup の PSI か Pod 単位のメトリクスで確かめる。

⌨️ 手を動かす（5 分）

Docker で CPU を使い切るループを 2 本走らせ、/proc/loadavg の 1 分値がどう追いつくかを 5 秒ごとに観察する（Mac の Docker Desktop なら、裏で動く Linux VM の値が見える）。

docker run --rm ubuntu bash -c '
echo "CPU: $(nproc)"
for i in 1 2; do (while :; do :; done) & done
for t in $(seq 1 12); do
  sleep 5
  echo "$(date +%T) $(cut -d" " -f1-4 /proc/loadavg)"
done
cat /proc/pressure/cpu 2>/dev/null || echo "PSI 無効"'

4 つ目の値（実行可能数）は最初から 2 以上になるのに、1 分値は 5 秒ごとに少しずつしか上がらず、60 秒経っても 2 に届かず 1.3 前後に留まるはずだ（VM 上の他の負荷があればその分上乗せされる）。これが指数減衰による遅れである。最後の PSI 出力では、ループ数が CPU 数を超えていれば some の値が上がっている。

🙅 よくある誤解
  • load average は CPU 使用率の別表現だ — 数えているのは時間の割合ではなくタスクの数で、Linux ではディスク I/O 待ちなどの D 状態も含む。CPU がほぼ空いていても load は高くなりうる。
  • 1 分値は直近 1 分間の平均値だ — 5 秒ごとのサンプルを指数的に減衰させて足し込んだ値で、1 分より前の負荷も少し残り、新しい負荷には遅れて追いつく。
  • load が高いなら CPU を増やせば解決する — D 状態が原因なら CPU を足しても待ちは減らない。vmstat の r と b で内訳を見てから対処を決める。
