同じ ORDER BY name なのに、なぜ手元と本番で並び順が変わるのか？

ユーザー一覧を ORDER BY name で並べ、テストも手元の画面も問題なかった。ところが本番では apple と Banana の順番が逆になっている。SQL は 1 文字も変えていないのに、結果を決めたのは誰なのだろうか。

🎯 3 行まとめ
  • 文字列の大小は「collation（照合順序）」という規則で決まり、Postgres では DB を作った瞬間の環境変数で既定値が固定される
  • C はバイト値の順、en_US.utf8 は OS の C ライブラリが持つ言語規則の順で、OS を上げると同じ名前の規則が変わることがある
  • 並び順に依存する画面は COLLATE を明示し、規則変更後は REINDEX でインデックスを並べ直す

文字列の「大小」は SQL ではなく規則表が決める

数値の 1 < 2 は誰が計算しても同じだが、文字列の 'a' < 'B' には唯一の正解が無い。文字コード上は B が 0x42、a が 0x61 なので B が先になる。一方、辞書を引く人間の感覚では大文字小文字を区別せず a が先だ。

この「文字列をどの順に並べるか」の規則を collation（照合順序）と呼ぶ。ORDER BY、< や BETWEEN による比較、そして文字列列の B-tree インデックスは、すべてこの規則を通して大小を判定している。

Postgres では collation の実装元をプロバイダと呼び、主に 3 種類ある。libc は OS の C ライブラリ（Linux なら glibc）が持つロケールデータに比較を任せる。icu は ICU というライブラリの Unicode 照合アルゴリズムを使う。Postgres 17 で追加された builtin は外部ライブラリに頼らず、コードポイント順で比較する。

既定の collation は DB を作った瞬間の環境変数で決まる

アプリ側で何も指定しなければ、列の collation は DB の default になる。公式ドキュメントによれば、initdb は実行環境のロケールでクラスタを初期化し、LC_ALL → LC_COLLATE → LANG の順に環境変数を探す。どれも設定されていなければ C になる。

つまり並び順は、SQL を書いた人ではなく「DB を作った時のシェルやコンテナに何が入っていたか」で決まる。公式 Docker イメージ postgres の Debian 版は en_US.utf8 で初期化されるので、手元の Docker では辞書順になる。一方で LANG を設定しない環境で initdb されたサーバーや、移行時に --locale=C を付けて作った DB はバイト順になる。両者で同じ SQL を流すと、冒頭の現象が起きる。

しかも LC_COLLATE は DB 作成後に変更できない。ドキュメントはその理由を「インデックスの並び順に影響するので、固定しておかないとテキスト列のインデックスが壊れる」と説明している。自分の DB がどちらかは次の SQL で分かる。

SELECT datname, datlocprovider, datcollate, datcollversion
FROM pg_database WHERE datname = current_database();
-- datlocprovider: c = libc / i = icu / b = builtin
🍱 たとえるなら

図書館の本棚だ。棚に本を差す司書は「並べ方の規則書」に従って位置を決め、利用者は同じ規則書で棚を二分探索して本を探す。B-tree インデックスはこの棚にあたる。規則書が「大文字小文字を区別しない版」か「文字コード順の版」かで棚の並びは変わるし、規則書が途中で改訂されると、すでに差した本の位置と探し方が食い違い、棚にある本が「見つからない」ことになる。

同じ en_US.utf8 でも、OS を上げると規則が変わる

ここで「では本番も手元も en_US.utf8 に揃えれば安心だ」と考えたくなる。しかし実際は、同じロケール名でも中身の規則は OS 側のデータであり、OS のアップグレードで変わることがある。libc プロバイダは比較を glibc に丸投げしているので、glibc の規則が変われば Postgres の比較結果も変わる。

実例が 2018 年の glibc 2.28 だ。Postgres の Wiki によると、このリリースでロケールデータが大きく更新され、Debian 10・RHEL 8・Ubuntu 18.10 以降がこの新データを使う。古い OS で作った DB を新しい OS で動かすと、ディスク上の B-tree は旧規則で並んだまま、検索は新規則で行われる。その結果、存在する行が検索で見つからない、ユニーク制約をすり抜けて重複行が入る、といった壊れ方をする。

Postgres は glibc や ICU のバージョンを collation の版として記録し、使用時に OS 側の版と食い違うと WARNING: ... version mismatch を出す。この警告が出たら、影響を受ける text / varchar のインデックスを REINDEX で作り直し、その後で版の記録を更新する。順序を逆にすると、壊れたインデックスを残したまま警告だけが消える。

REINDEX INDEX CONCURRENTLY users_name_idx;
-- DB の default collation の場合
ALTER DATABASE app REFRESH COLLATION VERSION;
-- 個別の collation の場合
ALTER COLLATION "en-x-icu" REFRESH VERSION;

pg_dump による論理ダンプや論理レプリケーションで移行した場合は、新しい環境でインデックスが作り直されるので、この問題は起きない。問題になるのは、データディレクトリをそのまま新 OS に持っていく物理レプリカや OS のインプレース更新である。

辞書順の DB では LIKE 'abc%' がインデックスを使えない

collation はインデックスの効き方にも影響する。ドキュメントには「C 以外のロケールでは通常のインデックスを LIKE が使えない」とある。前方一致 LIKE 'abc%' をインデックスで処理するには、内部で name >= 'abc' AND name < 'abd' という範囲検索に書き換える必要がある。この書き換えはバイト順でしか成り立たない。辞書順では文字以外の記号を後回しにして比べるなど規則が複雑で、「abc で始まる文字列」が棚の 1 区間に連続して並ぶ保証が無いからだ。

前方一致を速くしたいなら、その列だけ C の collation でインデックスを作る。表示用の並び順は DB の default のまま残し、検索用の棚だけをバイト順で作る形になる。text_pattern_ops 演算子クラスでも同じ効果が得られる。

CREATE INDEX users_name_c_idx ON users (name COLLATE "C");
-- EXPLAIN SELECT * FROM users WHERE name LIKE 'abc%';
-- → Index Cond: (name >= 'abc') AND (name < 'abd')

逆に、DB を C で作ればこの問題は起きず、比較も速い。その代わり ORDER BY name は大文字が小文字より先に並ぶので、人に見せる一覧では ORDER BY name COLLATE "en-x-icu" のように表示用の規則を明示することになる。

どの collation を選ぶか

選び方は「人間向けの並び」と「OS に依存しない安定性」のどちらを優先するかで決まる。C と Postgres 17 以降の builtin は OS や外部ライブラリに依存しないので、OS を上げても並びが変わらない。ICU は言語ごとの自然な並びを提供し、どのプラットフォームでも版情報を記録できる。libc は新規 DB で手間なく使えるが、OS 更新時の注意が最も多い。

どれを選んでも、画面の並び順を仕様として保証したい箇所は SQL で COLLATE を明示すると、環境差で結果が変わらなくなる。DB 全体の default に頼るのは、「どこで作られた DB でも同じ結果になる」と言えない書き方だからだ。

💼 実務でどう出会うか

典型は「CI では通るテストが手元で落ちる」ケースだ。CI の DB が C、手元の Docker が en_US.utf8 だと、並び順を期待値に書いたテストは片方でしか通らない。もう一つは RDB のメジャーアップグレードや OS 移行の計画時で、物理レプリカで新 OS に切り替える手順なら、文字列インデックスの REINDEX を作業に組み込む必要がある。LIKE '前方一致%' が遅いのにインデックスが効かない、という調査も、まず datcollate を確認するところから始まる。

⌨️ 手を動かす（5 分）

公式 Postgres イメージ（en_US.utf8）で、同じデータを default と C で並べ比べる。

docker run -d --name pgcol -e POSTGRES_PASSWORD=pw postgres:17
sleep 5
docker exec pgcol psql -U postgres \
  -c "SELECT datcollate, datlocprovider, datcollversion FROM pg_database WHERE datname='postgres';" \
  -c "SELECT x FROM (VALUES ('apple'),('Banana'),('cherry'),('b'),('_draft')) t(x) ORDER BY x;" \
  -c "SELECT x FROM (VALUES ('apple'),('Banana'),('cherry'),('b'),('_draft')) t(x) ORDER BY x COLLATE \"C\";" \
  -c "SELECT 'a' < 'B' AS default_rule, 'a' < 'B' COLLATE \"C\" AS c_rule;"
docker rm -f pgcol

datcollate は en_US.utf8、datcollversion には glibc の版が入っている。default では apple, b, Banana, cherry, _draft と大文字小文字を混ぜた辞書順、C では Banana, _draft, apple, b, cherry とバイト値順になり、'a' < 'B' の答えが t と f に分かれるはずだ。

🙅 よくある誤解
  • ORDER BY の結果は SQL が同じなら DB が変わっても同じ — 文字列の並びは列または DB の collation が決め、DB の default は作成時の環境変数で固定される。
  • ロケール名を en_US.utf8 に揃えれば永久に同じ並びになる — libc の規則は OS の C ライブラリのデータなので、glibc 2.28 のように OS 更新で中身が変わり、既存インデックスとずれることがある。
  • LIKE 'abc%' は前方一致なので普通のインデックスが必ず効く — 範囲検索への書き換えはバイト順でしか成り立たず、C 以外の DB では COLLATE "C" か text_pattern_ops のインデックスが要る。
📖 用語ミニ辞典
collation（照合順序）
文字列の大小・並び順を決める規則。ORDER BY・比較演算子・B-tree インデックスが従う。
C ロケール
文字列をバイト値の順に比べる規則。OS やバージョンに依存せず速いが、大文字が小文字より先に並ぶ。
プロバイダ
collation の実装元。Postgres では libc（OS の C ライブラリ）・icu・builtin がある。
glibc
多くの Linux で使われる C ライブラリ。libc プロバイダのロケール規則の出所で、2.28 で照合データが大きく変わった。
REINDEX
インデックスを現在の規則で作り直すコマンド。collation の規則が変わった後に既存インデックスを正しい並びへ戻す。
