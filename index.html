CPU limit は 2 なのに、なぜ Go のアプリは 8 コアぶん走ろうとして止められるのか？

Go の API サーバーを Kubernetes に載せ、resources.limits.cpu: "2" を付けた。CPU 使用率のグラフは平均 1 コアにも届いていないのに、p99 レイテンシだけがときどき 100ms 近く跳ねる。平均では余っている CPU に、アプリはなぜ待たされているのだろうか。

🎯 3 行まとめ
  • CPU limit は「100ms ごとに使える CPU 時間の枠」で、枠を使い切るとコンテナ全体が次の周期まで止められる（スロットリング）。
  • Go 1.24 までは GOMAXPROCS がノードの論理 CPU 数になるため、limit 2 のコンテナでも 8 本並列で走り、枠を周期の早い段階で食べ尽くす。
  • Go 1.25 以降（go.mod が go 1.25.0 以上）は cgroup の CPU limit を読んで既定値を合わせる。古い版では環境変数か automaxprocs で揃える。

GOMAXPROCS は「同時に Go コードを動かすスレッド数の上限」

GOMAXPROCS は、Go のコードを同時に実行できる OS スレッドの数の上限である。goroutine が何万個あっても、同時に CPU 上で走れるのはこの数までで、ランタイムのスケジューラがその枠に goroutine を順番に載せていく。値が 8 なら、最大 8 本のスレッドが同時に Go のコードを実行する。

Go 1.5 から 1.24 まで、この値の既定は「マシンの論理 CPU 数」だった。論理 CPU とは OS から見えるコアの数で、ハイパースレッディングがあれば物理コアの 2 倍になる。ここで落とし穴になるのは、コンテナの中から見える論理 CPU 数がコンテナに許された量ではなく、ノード（ホストマシン）全体の数だという点である。64 コアのノードに limit 2 の Pod を置けば、Go は 64 本並列で走れるつもりで起動する。

「Go が使いたがるだけで、OS が 2 コアに抑えてくれるなら問題ないのでは」と思える。しかし CPU limit は「同時に 2 コアまで」という仕組みではない。ここが今日の問いの答えにつながる。

CPU limit の正体は「100ms あたりの持ち時間」

Kubernetes の CPU limit は、Linux の cgroup の CPU 帯域制限（CFS bandwidth control）に変換される。cgroup とはプロセスのグループごとに資源を制限する Linux の仕組みで、cgroup v2 では cpu.max というファイルに「周期あたりに使える CPU 時間（クォータ）」と「周期の長さ」が書かれる。カーネルのドキュメントでは周期の既定は 100ms である。

# limit 2 の Pod の中で
$ cat /sys/fs/cgroup/cpu.max
200000 100000
# 100000µs（100ms）ごとに 200000µs まで使える

「2 コア」は、100ms の周期ごとに合計 200ms ぶんの CPU 時間を配る、という意味になる。何本のスレッドで使うかは問われない。2 本で 100ms ずつ使えば周期の最後まで走り続けられるが、8 本が同時に走れば 200ms は 25ms で尽きる。尽きた時点でカーネルはグループ内の全スレッドを止め（スロットリング）、次の周期でクォータが補充されるまで再開させない。

limit=2 → 100ms ごとに CPU 200ms の枠

GOMAXPROCS=2（limit と一致）
 0ms                         100ms
 ├─────────────────────────────┤
 │██████████ 2本で走り続ける ██│
 └─────────────────────────────┘

GOMAXPROCS=8（ノードのコア数）
 0ms   25ms                  100ms
 ├──────┼──────────────────────┤
 │██████│ 全員停止（75ms）     │
 └──────┴──────────────────────┘
  8本×25ms=200ms で枠切れ ▶ 次周期へ

平均 CPU 使用率が低くても遅くなる理由はここにある。使用率のグラフは数秒〜数十秒の平均で、周期の頭に集中して使い切り、残り 75ms 止まっている様子は平均に埋もれる。運悪くこの停止区間に入ったリクエストは、処理そのものとは無関係に数十 ms 待たされ、p99 だけが跳ねる。

🍱 たとえるなら

1 時間に 2 時間ぶんまで使えるレンタルスタジオの共用券だ。2 人で入れば 1 時間まるごと使えるが、8 人で一斉に入ると 15 分で 2 時間ぶんを使い切り、残り 45 分は全員が廊下で待たされる。入る人数（GOMAXPROCS）を券の時間（limit）に合わせない限り、合計の利用時間は同じでも「待たされる時間帯」が生まれる。

Go 1.25 から既定値が limit を読むようになった

Go 1.25 で、Linux 上の GOMAXPROCS の既定値は cgroup の CPU 帯域制限を考慮するようになった。cpu.max のクォータ ÷ 周期を「平均 CPU スループット上限」として計算し、それが論理 CPU 数より小さければそちらを既定値にする。端数は切り上げで、limit 1.5 なら 2 になる。

ただし、ランタイムのドキュメントには「論理 CPU 数や CPU アフィニティが 2 未満でない限り、2 未満には設定しない」とある。limit を 0.5 にしても GOMAXPROCS は 1 ではなく 2 になる。小さすぎる limit で並列度が 1 に落ちる事態を避けるための下限で、limit 1 未満の Pod では依然としてスロットリングが起こりうる。

もう一つの変更は定期的な更新で、limit が実行中に変わると GOMAXPROCS も追従する。更新は最大で毎秒 1 回、アイドル時はそれより少ない。一方で CPU request は参照しない。request は混雑時の配分比率として効く「最低保証」で、上限ではないためである。request だけで limit を付けない Pod では、従来どおり論理 CPU 数が既定値になる。

見落としやすいのが適用条件で、公式ブログによれば新しい既定値は go.mod の go 行が 1.25.0 以上のときに有効になる。ツールチェーンを 1.25 に上げても、go.mod が go 1.23 のままなら挙動は変わらない。

どの設定で揃えるか

最初に確認するのは go.mod の go 行と、Deployment に limit が付いているかの 2 点である。両方が当てはまれば追加設定は要らない。1.24 以前のまま運用するなら、環境変数で limit と同じ値を渡すのが最も単純で、Kubernetes の Downward API を使えば limit から自動で埋められる。

env:
- name: GOMAXPROCS
  valueFrom:
    resourceFieldRef:
      resource: limits.cpu
      divisor: "1"

limit を付け忘れると、Downward API はノードの割り当て可能な最大値を渡す。その場合はノードのコア数を渡すのと変わらないので、limit とセットで使う。また環境変数で値を固定すると、1.25 の自動更新は無効になる点には注意したい。limit を後から変えても、Pod が作り直されるまで値は古いままになる。コードで解決したい場合は go.uber.org/automaxprocs を blank import する方法が以前から広く使われてきた。

逆に旧挙動へ戻す手段もあり、GODEBUG=containermaxprocs=0 で limit の参照を、GODEBUG=updatemaxprocs=0 で定期更新を個別に止められる。アップグレード後にスループットが落ちたときの切り分けに使える。

💼 実務でどう出会うか

「CPU 使用率は低いのに p99 だけ悪い」「GC のタイミングでレイテンシが跳ねる」という相談の裏に潜んでいることが多い。GC は並列に動くため、並列度が高いほど短時間に CPU 時間を消費しやすく、枠切れの引き金になる。確認は Pod 内の /sys/fs/cgroup/cpu.stat の nr_throttled（止められた回数）と throttled_usec（止められた累計時間）が増え続けていないかを見るのが早い。cAdvisor 経由で Prometheus に集めていれば container_cpu_cfs_throttled_periods_total で同じことが追える。

⌨️ 手を動かす（5 分）

Docker の --cpus=2 で CPU 帯域制限をかけ、Go 1.24 と 1.25 のイメージで GOMAXPROCS の既定値を比べる。Docker Desktop の Mac でも、コンテナは Linux VM 上で動くので cgroup の制限が効く。

for v in 1.24 1.25; do
  docker run --rm --cpus=2 golang:$v sh -c 'cat /sys/fs/cgroup/cpu.max; mkdir /p && cd /p && go mod init p >/dev/null 2>&1 && printf "package main\nimport (\"fmt\";\"runtime\")\nfunc main(){fmt.Println(\"NumCPU:\",runtime.NumCPU(),\"GOMAXPROCS:\",runtime.GOMAXPROCS(0))}\n" > main.go && go run .'
done

両方とも cpu.max は 200000 100000 と表示されるはずだ。1.24 では GOMAXPROCS が NumCPU（Docker Desktop の VM に割り当てたコア数）と同じになり、1.25 では 2 になる。--cpus=0.5 に変えると 1.25 でも 2 のまま、-e GOMAXPROCS=1 を足すと 1 になることも確かめられる。

🙅 よくある誤解
  • CPU limit 2 なら、OS が同時実行を 2 コアに絞ってくれる — limit は周期あたりの CPU 時間の合計で、同時に走るスレッド数は制限しない。多く並列に走るほど周期の早い段階で枠を使い切り、残りの時間はまとめて止められる。
  • コンテナの中の nproc や runtime.NumCPU() は limit を反映している — 返るのはノード（または CPU アフィニティ）の論理 CPU 数で、帯域制限とは無関係である。Go 1.25 が別途 cpu.max を読みに行くのはこのためだ。
  • Go を 1.25 に上げれば自動で直る — 新しい既定値は go.mod の go 行が 1.25.0 以上のときに有効になる。また GOMAXPROCS 環境変数を設定済みなら、そちらが優先され自動更新も止まる。
📖 用語ミニ辞典
GOMAXPROCS
Go のコードを同時に実行できる OS スレッド数の上限。1.24 までの既定は論理 CPU 数。
cgroup
プロセスのグループ単位で CPU・メモリなどを制限する Linux の仕組み。コンテナの資源制限の土台。
CFS bandwidth control
周期ごとに使える CPU 時間（クォータ）を cgroup に割り当てる仕組み。v2 では cpu.max で設定する。
スロットリング
クォータを使い切った cgroup のスレッドを、次の周期まで実行させずに止めること。
論理 CPU
OS から見えるコアの数。コンテナ内でもノード全体の数が見える。
