ブラウザでは鍵マークが付くのに、なぜ curl だけ証明書エラーになるのか？

証明書を更新した翌日、外部サービスからの Webhook が全部失敗し始めた。ブラウザで開くと鍵マークは正常で、証明書も期限内だ。ところがサーバーから curl を叩くと unable to get local issuer certificate と言われる。同じ URL・同じ証明書なのに、なぜクライアントによって結果が割れるのだろうか。

🎯 3 行まとめ
  • サーバー証明書はルート CA が直接署名したものではなく、間の「中間証明書」を経由してルートに繋がる。この中間証明書はサーバーが TLS ハンドシェイクで一緒に送る決まりになっている。
  • 中間証明書を送り忘れても、ブラウザは過去に見た中間証明書のキャッシュや AIA による取得で穴を埋めてしまうことがある。OpenSSL ベースの curl や多くのアプリはそれをしないので失敗する。
  • 直し方はクライアント側ではなくサーバー側にある。nginx なら ssl_certificate に cert.pem ではなく fullchain.pem を指定し、openssl s_client で 2 枚以上届いているか確かめる。

証明書は 1 枚ではなく「鎖」で信頼される

TLS でクライアントがサーバーを信用する仕組みは、ブラウザや OS に最初から入っているルート証明書（信頼の起点として手元に保存された CA の証明書）を出発点にしている。ただし、ルート CA の秘密鍵で個々のサイトの証明書に直接署名することはまずない。ルートの鍵はオフラインで厳重に保管され、日々の発行にはルートが署名した中間証明書（ルートと個々のサイトの間に立つ CA の証明書）の鍵が使われる。

そのため、クライアントは「サイトの証明書 → それに署名した中間 CA → それに署名したルート」と、発行者（issuer）を辿って手元のルートに行き着くかを確かめる。この並びを証明書チェーンと呼ぶ。手元にあるのはルートだけなので、途中の中間証明書はどこかから手に入れなければ鎖が繋がらない。

TLS 1.3 の仕様（RFC 8446 §4.4.2）は、サーバーが送る証明書リストの先頭に自分の証明書を置き、続く各証明書は直前のものを署名した証明書であるべきだと定めている。手元にあるはずのルート自体は省略してよい。中間証明書を届けるのはサーバーの責任である。

 サーバーが送る Certificate
┌──────────────────────────┐
│ #0 *.example.com         │
│    issuer: Intermediate  │
├──────────────────────────┤
│ #1 Intermediate CA       │
│    issuer: Root CA       │
└────────────┬─────────────┘
             ▼ issuer を辿る
┌──────────────────────────┐
│ Root CA (not sent)       │
│ built into OS/browser    │
└──────────────────────────┘
🍱 たとえるなら

紹介状の束に近い。初対面の相手（サイト）が「A 社の部長の紹介です」と書いた紹介状を持ってきても、あなたが知っているのは A 社の社長だけだ。部長宛てに社長が書いた推薦状も一緒に出してもらえれば「社長 → 部長 → この人」と繋がる。部長の推薦状を持ってこなかった場合、前にその部長に会ったことがある人なら通してしまうが、初めての人は門前払いにする。

ブラウザは「送り忘れ」を黙って補ってしまう

中間証明書が欠けたら、どのクライアントでも同じように失敗しそうに思える。しかし実際はブラウザの多くが穴を自力で埋める。nginx の公式ドキュメントも、よく使われているブラウザは受け取った中間証明書を保存しておくため、チェーンを付け忘れた証明書でもエラーにならないことがあると注意している。

補う手段はほかにもある。証明書には AIA（Authority Information Access）という拡張があり、「この証明書の発行者の証明書はこの URL で取れる」という情報（CA Issuers）が入っている。Chromium にはこの URL から欠けた中間証明書を取りに行く処理が実装されている。Firefox は別の方式で、信頼された中間 CA 証明書をあらかじめ一括ダウンロードしておく（Mozilla によれば Firefox 68 で導入）。

一方、curl が Linux で使う OpenSSL は AIA を辿って取りに行かない。curl にはこれを求める機能要望（issue #2793）が立っているが、OpenSSL ビルドの curl はサーバーが送ってきた証明書と手元のルートだけでチェーンを組もうとし、繋がらなければ unable to get local issuer certificate（発行者が見つからない）で止まる。Ruby の Net::HTTP や Python の requests のように OpenSSL で検証する HTTP クライアントも同じ側にいる。これが冒頭の「ブラウザでは平気なのに Webhook が落ちる」の正体だ。

設定ミスの多くは「ファイルの選び間違い」

チェーン欠けは、証明書ファイルの選び方で起きることが多い。Let's Encrypt の certbot は 4 つのファイルを作り、公式ドキュメントによれば cert.pem はサーバー証明書単体、chain.pem は中間証明書、fullchain.pem はサーバー証明書を先頭に中間証明書を続けたもの、privkey.pem は秘密鍵である。nginx の ssl_certificate に必要なのは fullchain.pem だと明記されている。

# nginx: ssl_certificate には中間まで含むファイルを渡す
ssl_certificate     /etc/letsencrypt/live/example.com/fullchain.pem;
ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;

# ✗ cert.pem を渡すと #0 しか送られない
# ssl_certificate   /etc/letsencrypt/live/example.com/cert.pem;

cert.pem を指定しても nginx は普通に起動し、ブラウザでの確認も通ってしまうことがある。前の節のとおりブラウザが穴を埋めるからで、だから気づかれないまま本番に出る。有料 CA から証明書を受け取った場合も、サイト証明書とは別に「中間証明書バンドル」が渡されることがある。nginx のドキュメントは、サーバー証明書を先、バンドルを後に cat で 1 ファイルに連結する方法を示している。順序を逆にすると、nginx は先頭の証明書（中間 CA）と秘密鍵を組み合わせようとして key values mismatch で起動に失敗する。

Apache も同様で、certbot のドキュメントによれば 2.4.8 以降は SSLCertificateFile に fullchain.pem を渡す。それより古い版では SSLCertificateFile に cert.pem、SSLCertificateChainFile に chain.pem と分けて指定する。

クライアント側で「直す」のは筋が悪い

curl が失敗したとき、-k（--insecure）や verify: false で検証を切る手がまず目に入る。これは「繋がらない」を「誰とでも繋がる」に変えるだけで、中間者攻撃を検出する仕組みそのものを捨てる。チェーン欠けへの対処としては釣り合わない。

呼び出し側で欠けた中間証明書を CA バンドルに追加すれば一時的に通るが、これも勧めにくい。中間証明書は CA の都合で切り替わることがあり、追加した 1 枚が古くなった時点で再び壊れる。相手のサーバーを管理できない場合は先方に「チェーンが不完全です」と openssl s_client の出力を添えて連絡し、自分のサーバーならチェーンを送る設定に直すのが本来の対応だ。

💼 実務でどう出会うか

典型は「証明書を手で入れ替えた直後から、決済代行や Slack などの Webhook・モバイルアプリ・バッチだけが失敗する」という報告だ。ブラウザで確認すると正常なので、原因がアプリ側だと誤解されやすい。サーバー間通信のエラーに unable to get local issuer certificate や unable to verify the first certificate が出ていたら、まず相手（または自分）のサーバーが送っている証明書の枚数を数える。ALB や CloudFront のようなマネージドサービスに証明書をインポートする場合も、チェーン用の入力欄に中間証明書を入れ忘れると同じことが起きうる。

⌨️ 手を動かす（5 分）

badssl.com が用意している「中間証明書をわざと送らないサーバー」と、正しく送るサーバーを比べる。

# 1) チェーンが欠けたサーバー: 届く証明書の数を見る
echo | openssl s_client -connect incomplete-chain.badssl.com:443 \
  -servername incomplete-chain.badssl.com -showcerts 2>/dev/null \
  | grep -E '^ *[0-9]+ s:|Verify return code'

# 2) 正しいサーバー
echo | openssl s_client -connect badssl.com:443 \
  -servername badssl.com -showcerts 2>/dev/null \
  | grep -E '^ *[0-9]+ s:|Verify return code'

# 3) 欠けた方の証明書に書かれた AIA（発行者の取得先）
echo | openssl s_client -connect incomplete-chain.badssl.com:443 \
  -servername incomplete-chain.badssl.com 2>/dev/null \
  | openssl x509 -noout -ext authorityInfoAccess

# 4) curl で叩く
curl -sS -o /dev/null https://incomplete-chain.badssl.com/

1) では 0 s: の 1 行しか出ず、検証結果は unable to verify the first certificate になる。2) では 0・1…と中間証明書まで並び 0 (ok) になる。3) には CA Issuers - URI: として中間証明書の取得先が出る。ブラウザが辿りうるのはこの URL だ。4) は OpenSSL ビルドの curl なら証明書エラーで終わる（macOS 標準の curl はビルドが異なるため結果が違う可能性がある）。同じ URL を Chrome で開いて結果を比べるとよい。

🙅 よくある誤解
  • ブラウザで鍵マークが出ているから証明書の設定は正しい — ブラウザはキャッシュや AIA・事前ダウンロードで欠けた中間証明書を補うことがある。設定の確認は openssl s_client で届いた枚数を見て行う。
  • curl の証明書エラーは手元の CA バンドルが古いせいだ — それが原因のこともあるが、s_client で 1 枚しか届いていなければサーバー側のチェーン欠けである。CA バンドルを更新しても直らない。
  • ルート証明書まで全部送るのが一番安全だ — ルートはクライアントが手元に持っている前提で、RFC 8446 でも省略してよいとされている。送るべきは自分の証明書と中間証明書で、ルートを足しても信頼は増えない。
📖 用語ミニ辞典
ルート証明書
OS やブラウザに最初から入っている、信頼の起点となる CA の自己署名証明書。
中間証明書
ルート CA が署名し、サイトの証明書に署名する CA の証明書。サーバーが送る責任を持つ。
証明書チェーン
サイト証明書から発行者を辿ってルートに至る証明書の並び。
AIA（Authority Information Access）
発行者の証明書の取得先 URL などを記した証明書の拡張。
fullchain.pem
certbot が作る、サーバー証明書の後ろに中間証明書を続けたファイル。
