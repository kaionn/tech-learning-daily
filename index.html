サーバーは localhost で動いているのに、なぜ「ECONNREFUSED ::1」で繋がらないのか？

ローカルで DB やモックサーバーを立ち上げ、別のターミナルから localhost:3000 に繋いだら connect ECONNREFUSED ::1:3000 で落ちた。サーバーは確かに動いているし、127.0.0.1:3000 と書き直すとあっさり繋がる。同じ自分のマシンを指しているはずの 2 つの書き方が、なぜ違う結果になるのだろうか。

🎯 3 行まとめ
  • localhost は 1 つの住所ではなく、IPv4 の 127.0.0.1 と IPv6 の ::1 の 2 つに解決される名前である。
  • OS の標準の並べ方（RFC 6724）では ::1 が先に来るため、サーバーが 127.0.0.1 でしか待っていないと最初の接続は拒否される。
  • Node は v17 で OS の並び順をそのまま使うよう変わり、v20 で両方を順に試す Happy Eyeballs が既定になった。根本対策は「待つ側と繋ぐ側の住所を揃える」ことである。

localhost は「住所」ではなく「名前」である

localhost は IP アドレスではなくホスト名だ。ホスト名は接続の前に名前解決（名前から IP アドレスを引く処理）を経て IP アドレスに変換される。localhost の場合、問い合わせ先は DNS サーバーではなく、多くの OS で手元の /etc/hosts ファイルである。

macOS や多くの Linux ディストリビューションの /etc/hosts には、次のように localhost が 2 行書かれている。

127.0.0.1   localhost
::1         localhost

127.0.0.1 は IPv4 のループバックアドレス、::1 は IPv6 のループバックアドレスだ。ループバックアドレスとは、ネットワークカードの外に出ず自分自身に戻ってくる宛先を指す。どちらも「自分のマシン」を指すが、IPv4 と IPv6 は別のプロトコルなので、OS から見ると別々の宛先である。127.0.0.1:3000 で待っているサーバーに [::1]:3000 から繋ごうとしても、そこには誰もいない。

なぜ ::1 が先に選ばれるのか

名前解決の結果が 2 つあるなら、どちらを先に試すかが問題になる。アプリは通常 getaddrinfo() という OS の関数で名前を解決し、OS は RFC 6724 が定める既定のポリシー表に従って結果を並べ替えて返す。この表で ::1/128 の優先度は 50 と最も高く、IPv4 アドレスを表す ::ffff:0:0/96 は 35 である。つまり OS の標準の並べ方では ::1 が先頭に来る。

「IPv4 のほうが昔からある標準なのだから、IPv4 が優先されるはずだ」と考えたくなる。しかし実際は逆で、IPv6 が使える環境では IPv6 を優先するのが今の OS の既定だ。IPv6 への移行を進めるために、両方が使えるなら新しいほうを先に試すよう設計されている。

クライアント: connect("localhost", 3000)
        │
        ▼
 getaddrinfo("localhost")
 ┌─────────────────────────┐
 │ 1. ::1        (IPv6) 50 │
 │ 2. 127.0.0.1  (IPv4) 35 │
 └─────────────────────────┘
        │ 先頭から試す
        ▼
 [::1]:3000 ──▶ 誰も待っていない
        │       RST → ECONNREFUSED
        ▼
 127.0.0.1:3000 ──▶ サーバー（待受中）
 （2 番目を試すかはクライアント次第）

ここで決定的なのは図の最後の行だ。先頭の ::1 が拒否されたとき、2 番目の 127.0.0.1 を試すかどうかはクライアントの実装に委ねられている。先頭だけ試して諦めるクライアントでは、サーバーが生きていても ECONNREFUSED になる。

🍱 たとえるなら

同じビルに「本館受付」と「新館受付」の 2 つの窓口があり、案内板には「新館を先にどうぞ」と書いてある。来客が新館に行くと、担当者は本館にしか座っていないので門前払いになる。気の利く来客は本館に回り直すが、門前払いされた時点で帰ってしまう来客もいる。localhost は「このビル」という名前で、::1 と 127.0.0.1 が 2 つの窓口、案内板が RFC 6724 の並べ方である。

Node で突然この問題が増えた理由

Node の dns.lookup() は v17.0.0 まで、OS が返した結果をわざわざ並べ替えて IPv4 を先頭にしていた。v17.0.0 でこの既定が verbatim（OS の並び順をそのまま使う）に変わった。この変更で、それまで 127.0.0.1 に繋がっていた localhost 宛ての接続が、同じコードのまま ::1 に向かうようになった。127.0.0.1 でしか待っていない DB コンテナやモックサーバーに繋ぐ構成で、Node を上げただけで ECONNREFUSED ::1 が出始めたのはこのためだ。

v20.0.0（v18.18.0 にも反映）では、net.connect() の autoSelectFamily オプションの既定値が true になった。これは Happy Eyeballs（RFC 8305）と呼ばれる方式で、名前解決で得た IPv6 と IPv4 のアドレスを交互に並べ、一定時間内に繋がらなければ次のアドレスを試す。すべて失敗したときだけ、全試行のエラーをまとめた AggregateError を返す。RFC 8305 は次の試行までの待ち時間の既定として 250 ミリ秒を推奨している。

挙動を戻したり固定したりする設定もある。Node の起動オプションで指定する場合は次のようになる。

# 名前解決の結果を IPv4 優先に並べ替える
node --dns-result-order=ipv4first app.js

# Happy Eyeballs を無効にする（先頭だけ試す）
node --no-network-family-autoselection app.js

--dns-result-order=ipv4first を付けると v16 以前と同じく 127.0.0.1 が先頭になり、IPv4 でしか待たないサーバーにはすぐ繋がる。代わりに ::1 でしか待たないサーバーには繋がりにくくなるので、問題の向きが反転するだけである。コード中で dns.setDefaultResultOrder('ipv4first') を呼んでも同じ効果があり、こちらが起動オプションより優先される。

待つ側の住所も確認する

問題は繋ぐ側だけでなく、待つ側（サーバーがどのアドレスで listen しているか）にもある。サーバーが待受アドレスを 127.0.0.1 と明示していれば IPv4 だけ、::1 なら IPv6 だけを受け付ける。待受アドレスに localhost と書いた場合は、サーバー側でも名前解決が行われ、その結果の先頭アドレス 1 つだけで待つ実装が多い。Node 17 以降の開発サーバーが ::1 だけで待ち、curl 127.0.0.1:5173 が拒否されるという逆向きの事故はこれで起きる。

Node の server.listen() はホストを省略すると、IPv6 が使えれば未指定アドレス :: で待つ。多くの OS では :: で待つと IPv4 の接続も同時に受け付けるため、::1 と 127.0.0.1 のどちらから来ても繋がる。ただしこれは外部のマシンからの接続も受け付けることを意味するので、ローカル専用にしたいサーバーではホストを省略せず、繋ぐ側と同じアドレスを明示するほうが安全である。

どの対策を取るにしても、「サーバーが待つアドレス」と「クライアントが最初に試すアドレス」を一致させるのが根本解決だ。設定ファイルの接続先を localhost ではなく 127.0.0.1 と書くのが最も手軽で、名前解決の結果に左右されない。

💼 実務でどう出会うか

典型は、docker run -p 127.0.0.1:5432:5432 postgres のように IPv4 のループバックだけに公開したコンテナへ、Node のアプリやマイグレーションツールが DATABASE_URL=postgres://...@localhost:5432 で繋ぐ場面だ。Node 17〜19 や、Happy Eyeballs を持たない古いクライアントでは ECONNREFUSED ::1:5432 で落ちる。Node 20 以降では最終的に繋がるが、繋がる前に ::1 への試行を挟むことになる。エラーメッセージに ::1 が出たら「サーバーが落ちている」ではなく「住所の不一致」を疑い、接続先を 127.0.0.1 に書き換えるか、サーバーの待受アドレスを見直すとよい。

⌨️ 手を動かす（5 分）

IPv4 のループバックだけで待つサーバーを立て、localhost 宛ての接続が ::1 を先に試す様子を観察する。ターミナル 1 で次を実行する。

cat /etc/hosts | grep localhost
python3 -m http.server 8000 --bind 127.0.0.1

ターミナル 2 で次の 3 つを順に実行する。

curl -v http://localhost:8000/ -o /dev/null 2>&1 | grep -i -E 'trying|connected|failed'

node -e "require('dns').lookup('localhost',{all:true},(e,a)=>console.log(a))"

node --no-network-family-autoselection -e "require('net').connect(8000,'localhost').on('connect',()=>{console.log('connected');process.exit()}).on('error',e=>console.log(e.message))"

環境によるが、curl は ::1 への試行が失敗した後に 127.0.0.1 で繋がる行を表示し、dns.lookup は ::1 と 127.0.0.1 の 2 件を返すはずだ。3 つ目は Happy Eyeballs を切っているので先頭の ::1 だけを試し、connect ECONNREFUSED ::1:8000 が出る。同じコマンドから --no-network-family-autoselection を外すと connected に変わることも確かめられる。

🙅 よくある誤解
  • localhost と 127.0.0.1 は同じものの別名だ — localhost は名前で、多くの環境で 127.0.0.1 と ::1 の 2 つに解決される。127.0.0.1 は IPv4 の 1 アドレスにすぎない。
  • ECONNREFUSED が出たらサーバーは落ちている — その宛先アドレスとポートで待つプロセスがいない、という意味である。サーバーが別のアドレス（IPv4 側）で生きていても出る。
  • IPv6 を使っていないので自分には関係ない — 外向きの通信が IPv4 だけでも、ループバックの ::1 は OS が標準で持っており、/etc/hosts 経由で localhost の解決結果に入ってくる。
📖 用語ミニ辞典
ループバックアドレス
外部に出ず自分自身に戻ってくる宛先。IPv4 は 127.0.0.1、IPv6 は ::1。
getaddrinfo
ホスト名を IP アドレスの一覧に変換する OS の関数。結果の並び順も OS が決める。
RFC 6724
複数の候補アドレスをどの順に試すかの既定ポリシーを定めた規格。::1 の優先度が最も高い。
Happy Eyeballs
IPv6 と IPv4 のアドレスを交互に、一定の間隔で次々に試して最初に繋がったものを使う接続方式（RFC 8305）。
ECONNREFUSED
接続先のアドレスとポートで待つプロセスがおらず、相手 OS に接続を拒否されたことを示すエラー。
