ターミナルでは動くスクリプトなのに、なぜ cron に登録すると「command not found」で落ちるのか？

手で ./backup.sh を叩けば何度でも成功する。それを crontab -e で毎晩 3 時に登録した翌朝、届いていたのは node: not found のエラーメールだった。同じユーザー、同じマシン、同じスクリプトなのに、何が違ったのか説明できるだろうか。

🎯 3 行まとめ
  • 環境変数は「親プロセスが子プロセスに渡すコピー」で、OS 全体で共有された設定ではない。
  • ターミナルの PATH に node や bundle の場所を足しているのは .zshrc などシェルの設定ファイルで、cron が起動する /bin/sh はそれを読まない。
  • cron の既定 PATH は /usr/bin:/bin 程度しかないため、crontab に PATH= を書くか、コマンドを絶対パスで呼ぶ。

環境変数は「親から子へのコピー」でしかない

環境変数とは、プロセスごとに持つ NAME=value 形式の文字列の一覧である。Linux の environ(7) によると、fork(2) で作られた子プロセスは親の環境のコピーを受け継ぎ、execve(2) で新しいプログラムを起動するときにはその一覧が新しいプログラムに渡される。

ここから一つの性質が出てくる。環境変数はプロセスの系図に沿って上から下へ流れるだけで、横には流れない。ターミナルで export FOO=1 しても、すでに動いている別のプロセスや、別の親から生まれるプロセスには届かない。「このユーザーの環境変数」という OS 全体の置き場所は無く、どの親から起動されたかで中身が決まる。

そして node のようにスラッシュを含まないコマンド名を打ったとき、シェルは PATH に並んだディレクトリを先頭から順に探し、実行権限のあるファイルが見つかったところで止まる。PATH に node の置き場所が無ければ、ファイルがディスクに存在していても command not found になる。

ターミナルの PATH は誰が作っているのか

普段のターミナルの PATH は、OS が最初から用意したものではない。ログイン時やシェル起動時に読まれるシェルの設定ファイル（起動時に自動で実行されるスクリプト）が、少しずつ継ぎ足して作っている。Homebrew の eval "$(brew shellenv)"、nvm や rbenv の初期化行、export PATH="$HOME/bin:$PATH" といった行に見覚えがあるはずだ。

どのファイルが読まれるかは、シェルが「ログインシェルか」「対話シェルか」で変わる。対話シェルは人がプロンプトに入力するシェル、ログインシェルはログイン直後に最初に起動されるシェルを指す。zsh の公式マニュアルでは、.zshenv は常に、.zprofile と .zlogin はログインシェルだけ、.zshrc は対話シェルだけで読まれる。bash では対話の非ログインシェルが ~/.bashrc を読み、対話しない（スクリプト実行の）シェルは BASH_ENV が指すファイル以外何も読まない。

つまり .zshrc に書いた nvm の初期化は、「人が打ち込むためのシェル」が起動したときにしか実行されない。手で ./backup.sh を叩いたときに node が見つかったのは、スクリプトが自力で探したからではなく、親である対話シェルが作った PATH をコピーで受け取っていたからだ。

 手で実行した場合
┌──────────────────────────┐
│ zsh（対話・ログイン）    │
│  .zprofile/.zshrc を実行 │
│  PATH=…/nvm/…:/opt/…:…   │
└────────────┬─────────────┘
             │ fork+execve（コピー）
             ▼
┌──────────────────────────┐
│ backup.sh → node 発見 ✓  │
└──────────────────────────┘

┌──────────────────────────┐

cron の子プロセスはどんな環境で生まれるか

cron のジョブは、ターミナルの子孫ではない。システム起動時に立ち上がった cron デーモン（時刻を監視して登録コマンドを起動する常駐プロセス）の子として生まれる。ユーザーが同じなので、ログイン時と同じ環境が用意されるように思える。しかし実際は、デーモンがほぼ空の環境を自分で組み立てて渡している。

Debian の crontab(5) は、cron が自動で設定する変数を明記している。SHELL は /bin/sh、LOGNAME と HOME は /etc/passwd の所有者の行から取られる。同じ man ページの bullseye 版は「PATH は /usr/bin:/bin に設定される。別の PATH を使いたければ crontab ファイル内で設定する必要がある」と書いている（Ubuntu の一部バージョンでは既定値が変わり man ページの記述と食い違った経緯があり、実装・ディストリビューションごとに差がある）。

起動されるのは /bin/sh -c '登録したコマンド' という非対話・非ログインのシェルだ。bash マニュアルによれば、sh という名前で起動された非対話シェルは起動ファイルを一つも読まない。.zshrc に足した nvm も、Homebrew の /opt/homebrew/bin も、~/.rbenv/shims も入らないまま、PATH=/usr/bin:/bin でスクリプトが走る。これが冒頭の node: not found の正体である。

🍱 たとえるなら

自分の机で仕事をするときは、引き出しに文房具を揃えてある（設定ファイルが整えた PATH）。cron に仕事を頼むのは、夜中に代理の人を空っぽの貸し会議室に呼んで「この手順書どおりにやって」と渡すのに近い。手順書に「赤ペンを使う」とだけ書いてあれば、代理の人は赤ペンを見つけられない。手順書に置き場所（絶対パス）を書くか、会議室にも文房具を運び込む（crontab に PATH=）必要がある。

直し方: どこで PATH を与えるか

一番素直なのは、crontab の先頭に環境設定行を書くことだ。crontab(5) は name = value 形式の行を環境設定として扱う。ただし値の中の変数展開やチルダ展開は行われないと明記されているので、$HOME や ~ は使えず、全部書き下す。

# crontab -e
SHELL=/bin/bash
PATH=/opt/homebrew/bin:/usr/local/bin:/usr/bin:/bin
MAILTO=""

0 3 * * * cd /Users/me/app && ./backup.sh >> /tmp/backup.log 2>&1

各行の効果は次のとおりだ。PATH を書けば、その crontab のすべてのジョブで node などが見つかるようになる。SHELL を変えると /bin/sh の代わりに bash でコマンド行が解釈されるが、それでも非対話シェルなので .bashrc は読まれない。MAILTO="" にするとエラーメールが送られなくなる。未設定なら crontab の所有者宛てに出力がメールされるので、メールを止める場合はログをファイルに残す。

nvm や rbenv のようにバージョンごとにディレクトリが変わるツールでは、PATH の固定より絶対パス指定の方が壊れにくいことが多い。command -v node の出力をそのまま書けば、cron 側の PATH に依存しなくなる。もう一つの落とし穴は % だ。crontab のコマンド欄では、バックスラッシュでエスケープしない % は改行に変換され、最初の % 以降はコマンドの標準入力に回される。date +%Y%m%d を直書きすると、コマンドがそこで切られる。

# パスは command -v node の出力をそのまま書く
0 3 * * * /Users/me/.nvm/versions/node/v22.11.0/bin/node /Users/me/app/job.js
0 4 * * * tar czf /tmp/bk-$(date +\%Y\%m\%d).tgz /Users/me/data
💼 実務でどう出会うか

典型は「cron の bundle exec rake が bundle: not found」「Node のバッチだけ夜間に失敗する」「aws CLI が見つからない」の 3 つだ。同じ構造は cron 以外にも現れる。systemd のサービス、CI ランナー、Docker の ENTRYPOINT も、ターミナルの対話シェルを経由せず親プロセスが用意した環境でコマンドを起動するため、.zshrc に頼った設定は効かない。「手では動くのに自動実行だと動かない」と言われたら、まずジョブの先頭に env > /tmp/env.txt を仕込み、手元の env と差分を取るのが早い。

⌨️ 手を動かす（5 分）

cron と同等の最小環境を env -i（環境を空にしてから指定した変数だけ渡す）で再現し、ターミナルとの違いを見る。crontab を実際に登録する必要はない。

# 1. いつものターミナル
echo "$PATH" | tr ':' '\n' | head -5
command -v node || echo "node not found"

# 2. cron 相当の最小環境で同じことをする
env -i HOME="$HOME" LOGNAME="$USER" SHELL=/bin/sh \
  PATH=/usr/bin:/bin \
  /bin/sh -c 'echo "PATH=$PATH"; command -v node || echo "node not found"'

# 3. 渡される環境変数の数を比べる
env | wc -l
env -i PATH=/usr/bin:/bin /bin/sh -c 'env | wc -l'

1 では /opt/homebrew/bin や nvm のディレクトリが並び node のパスが出るはずだ。2 では PATH=/usr/bin:/bin となり、Homebrew や nvm で入れた node は node not found になる。3 では手元の環境変数が数十行あるのに対し、最小環境は数行しかないことが分かる。2 の PATH に command -v node の結果のディレクトリを足すと、見つかるようになる。

🙅 よくある誤解
  • 同じユーザーで動くのだから、環境変数も同じはず — 環境変数はユーザーではなくプロセスに属し、起動した親が渡したコピーで決まる。cron デーモンはシェルの設定ファイルを読まずに最小限の変数だけを渡す。
  • SHELL=/bin/bash にすれば .bashrc が読まれる — cron が起動するのは非対話シェルで、bash の非対話シェルは BASH_ENV が指すファイル以外の起動ファイルを読まない。シェルの種類を変えても PATH は増えない。
  • crontab で PATH=$HOME/bin:$PATH と書けば継ぎ足せる — crontab の環境設定行では変数展開もチルダ展開も行われない。値は文字列としてそのまま入るので、ディレクトリを全部書き下す。
