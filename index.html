ラベルを 1 つ足しただけなのに、なぜ Prometheus のメモリが溢れるのか？

「どのエンドポイントが遅いか見たい」と思い、レイテンシのメトリクスに path ラベルを 1 つ足してデプロイした。数日後、Prometheus のメモリ使用量が跳ね上がり、OOM で再起動を繰り返し始める。リクエスト数は何も変わっていないのに、たった 1 つのラベルがなぜ監視サーバーを倒すのだろうか。

🎯 3 行まとめ
  • Prometheus は「メトリクス名 + ラベルの値の組み合わせ」ごとに別々の時系列を作り、その本数（カーディナリティ）がメモリ・CPU・ディスクのコストを決める。
  • ラベルの種類数は足し算ではなく掛け算で効き、/users/123 のような生の URL やユーザー ID を値に入れると系列が際限なく増える。
  • 対策の主役は計測側でラベル値を有限に保つことで、metric_relabel_configs の labeldrop や sample_limit は取り込み側の安全網になる。

1 本の時系列は「名前 + ラベルの組」で決まる

Prometheus が保存する単位は時系列（time series。ある 1 つの対象について「時刻と値」の組を時間順に並べた列）である。http_requests_total というメトリクスがあっても、それ自体は 1 本の時系列ではない。

メトリクスにはラベル（method="GET" のように、測っている対象の性質を表すキーと値の組）を付けられる。公式ドキュメントは「キーと値のラベルの組み合わせが 1 つ異なるごとに新しい時系列になる」と明記している。つまり method="GET" と method="POST" は、同じメトリクス名でも保存上は別の 2 本である。

あるメトリクスが何本の時系列に展開されるかを、そのメトリクスのカーディナリティ（ラベル値の組み合わせの数）と呼ぶ。

http_requests_total
├─{method="GET", status="200"}  ─▶ 系列1
├─{method="GET", status="500"}  ─▶ 系列2
├─{method="POST",status="200"}  ─▶ 系列3
└─{method="POST",status="500"}  ─▶ 系列4

path ラベルを追加（値が N 種類）
        ▼
4 本 × N 種類 = 4N 本の系列

ラベルは足し算ではなく掛け算で効く

ラベルを 1 つ足すのは、表に列を 1 つ足す程度の変更に思える。しかし実際は、既存の全組み合わせがそのラベルの値の数だけ複製される。method が 4 種類、status が 5 種類なら 20 本だが、ここに値が 20 種類の path を足すと 400 本になる。

問題は path の値が有限とは限らないことだ。ルーティングのテンプレート（/users/:id）ではなく実際のリクエスト URL（/users/123）を入れると、ユーザーが増えるたび、ボットが存在しない URL を叩くたびに新しい値が生まれる。公式ドキュメントはユーザー ID やメールアドレスのような「上限のない値の集合」をラベルに入れるなと注意している。

Histogram はこの掛け算をさらに大きくする。従来型の Histogram は値の分布を数えるために、上限値ごとの区間（バケット）を 1 本ずつ系列として持つからだ。Python クライアントの既定バケットは +Inf を含めて 15 個あり、そこに合計 _sum と件数 _count が加わる。つまりラベルの組み合わせ 1 つにつき 17 本以上の系列が生える。

🍱 たとえるなら

郵便局の私書箱に近い。宛名が 1 文字でも違えば別の箱を 1 つ借りる決まりで、手紙（サンプル）自体は小さく束ねて保管できる。ところが宛名に「部屋番号」を書き足すと、同じ建物の住人ごとに箱が増える。棚を圧迫するのは届く手紙の量ではなく、箱の数のほうだ。

なぜ「本数」がメモリに直結するのか

Prometheus の保存エンジンは、取り込んだばかりのサンプルを head block（直近のデータを保持するメモリ上の領域。クラッシュに備えて WAL というログにも書く）に置く。系列 1 本ごとにラベルの組や書き込み途中のデータを持つため、系列が増えるほど常駐メモリが増える。

一方、同じ系列の中のサンプルは時刻も値も前の点と似ているので、よく圧縮される。公式のストレージ解説は 1 サンプルあたり平均 1〜2 バイトとし、負荷を下げるならサンプル数より系列数を減らすほうが効果的だとしている。スクレイプ間隔を延ばしてもメモリがあまり減らないのはこのためだ。

規模の感覚は公式ドキュメントの例が分かりやすい。1 万台のノードに数十本ずつのファイルシステム系列なら約 10 万本で問題ない。しかしそこへユーザーごとのクォータを足し、1 万ユーザー × 1 万ノードにすると数千万本になり、「現在の実装には多すぎる」と書かれている。

計測側で絞り、取り込み側で安全網を張る

対策の第一は、アプリが出すラベル値を有限に保つことだ。Rails なら request.path ではなくルート定義、Go のルーターならマッチしたパターンをラベルに入れる。公式の目安は「多くのメトリクスはラベル無し、ラベルを使うものもカーディナリティは 10 未満、100 を超えそうなら次元を減らすか監視以外の仕組みへ移す」である。ユーザー単位の分析はログやトレースの役割になる。

アプリをすぐ直せないときは、Prometheus 側の metric_relabel_configs で取り込み直前にラベルを削れる。これは取り込み前の最後の段階で各サンプルに適用され、labeldrop は正規表現に一致した名前のラベルを取り除く。ただし系列の区別に使っていたラベルを落とすと、別々だった系列が同じラベルの組になって衝突しうるので、応急処置と考えたほうがよい。

scrape_configs:
  - job_name: app
    sample_limit: 50000
    metric_relabel_configs:
      - action: labeldrop
        regex: user_id

sample_limit は 1 回のスクレイプで受け入れるサンプル数の上限で、既定値 0 は「無制限」を意味する。上限を超えると、relabel 後の数で判定したうえでそのスクレイプ全体が失敗扱いになる。データが一時的に欠けるので強い手段だが、1 つのアプリのラベル事故が Prometheus 全体を巻き込んで落とす事態は防げる。

犯人のメトリクスを見つける

メモリが増え始めたら、どのメトリクスが系列を生んでいるかを先に調べる。HTTP API の /api/v1/status/tsdb は、head block の系列数（headStats.numSeries）に加えて、メトリクス名ごとの系列数（seriesCountByMetricName）やラベル名ごとの値の種類数（labelValueCountByLabelName）を上位から返す。既定では各リスト 10 件で、limit パラメータで増やせる。

curl -s 'http://localhost:9090/api/v1/status/tsdb?limit=5' \
  | jq '.data.labelValueCountByLabelName'

path や user_id のようなラベルが値の種類数で上位に並んでいれば、それが掛け算の起点である。

💼 実務でどう出会うか

典型は「ミドルウェアで全リクエストのレイテンシを Histogram に記録し、ラベルに生の URL パスを入れた」ケースである。開発環境ではアクセスする URL が数十種類しかないので問題が見えず、本番で ID 付きの URL やクローラーのアクセスが流れ込んで初めて系列が増え続ける。Grafana のダッシュボードが遅くなる、Prometheus が OOM で再起動する、マネージド監視サービスの請求が系列数に応じて増える、といった症状で発覚することが多い。レビュー時に「このラベルの値は何種類になりうるか」を 1 つ質問するだけで、多くは事前に防げる。

⌨️ 手を動かす（5 分）

Python の公式クライアントで、パスをテンプレートにした Histogram と生の URL を入れた Histogram に 1,000 ユーザー分のリクエストを記録し、公開される系列数を比べる。

mkdir -p /tmp/card && cd /tmp/card
python3 -m venv v && v/bin/pip -q install prometheus_client
cat > card.py <<'EOF'
from prometheus_client import CollectorRegistry, Histogram, generate_latest

reg = CollectorRegistry()
good = Histogram("good_seconds", "templated", ["path"], registry=reg)
bad = Histogram("bad_seconds", "raw path", ["path"], registry=reg)

for user_id in range(1000):
    good.labels(path="/users/:id").observe(0.03)
    bad.labels(path=f"/users/{user_id}").observe(0.03)

text = generate_latest(reg).decode()
for name in ("good_seconds", "bad_seconds"):
    n = sum(1 for l in text.splitlines() if l.startswith(name))
    print(f"{name}: {n} series")
EOF
v/bin/python card.py

リクエスト数は同じ 1,000 件なのに、good_seconds は 18 本、bad_seconds は 18,000 本になるはずだ（バケット 15 本・_sum・_count に、Python クライアントが付ける作成時刻の _created 1 本を加えて 18 本）。range(1000) を range(10000) に変えると、bad_seconds だけがさらに 10 倍になることも確かめられる。

🙅 よくある誤解
  • スクレイプ間隔を延ばせばメモリは大きく減る — サンプルは系列内でよく圧縮されるため、コストを左右するのは主に系列の本数である。間隔を延ばしても系列数は変わらない。
  • ユーザーごとの状況を見たいなら user_id ラベルを足せばよい — 値に上限のないラベルは系列を際限なく増やす。個別ユーザーの追跡はログやトレースで行い、メトリクスは集計値に留める。
  • Histogram 1 つは系列 1 本である — バケットの数だけ系列があり、そこに _sum と _count が加わる。ラベルの組み合わせ 1 つごとにこの束が丸ごと複製される。
📖 用語ミニ辞典
時系列
メトリクス名とラベルの組で識別される、時刻と値の組を時間順に並べた列。
ラベル
測定対象の性質を表すキーと値の組。値の組み合わせが違えば別の時系列になる。
カーディナリティ
あるメトリクスが展開されるラベル値の組み合わせの数、すなわち時系列の本数。
head block
Prometheus が直近のサンプルをメモリ上に保持する領域。WAL でクラッシュに備える。
metric_relabel_configs
スクレイプしたサンプルに取り込み直前に適用するラベル書き換え・削除の設定。
sample_limit
1 回のスクレイプで受け入れるサンプル数の上限。超えるとスクレイプ全体が失敗扱いになる。
